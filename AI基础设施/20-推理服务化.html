20 · 推理服务化

⏱ 42 分钟 ｜ ⭐ 从"能跑"到"能上线"

🎯 一句话

前面五章讲的是怎么让单机跑得快。 这一章讲怎么把它变成一个能承诺 SLO、能扛住流量、能算清账的服务。

🧭 一、先选引擎：按模型、硬件与服务负载比较

第 15 章把推理优化的第一步写成了"用专门的推理引擎，别拿 generate() 上生产，光这一步常常 5-10 倍"， 但没说换成哪个。这一节补上。

⚠️ 先说时效：推理框架半年一变，功能互相抄，性能榜半年就翻篇。 所以下面只写定位和取舍判据，不写版本号、不写 API、不写 benchmark 数字。 记结构，别记名字。

七个常见选项，各自的位置

引擎 一句话定位 最擅长 部署代价
vLLM ⭐ 通用的默认选项，覆盖多种模型与量化格式，具体支持应核对版本 通用在线服务 低：装上给一条命令，直接是 OpenAI 兼容接口
SGLang ⭐ 面向复杂调用结构的引擎，核心是 RadixAttention 前缀高度重复的负载：Agent、多轮、多候选、约束解码 低，和 vLLM 同量级
TensorRT-LLM NVIDIA 官方的极致性能路线，可使用不同执行路线，预构建 engine 不是所有后端的共同前提 单一模型、形状稳定、把最后一滴性能榨出来 ⚠️ 需核对版本、执行后端、模型兼容性与准备成本；不能把所有路线都概括成换配置必重建 engine
TGI HuggingFace 的服务化方案，和 HF 生态贴得最紧 模型来源、权限、工具链都已经在 HF 那一套里的团队 低
LMDeploy 国内团队做的引擎，提供模型部署与量化路径，具体兼容性按版本核对 主力模型是国内开源系列时 低
llama.cpp ⭐ C++ 路线，没有 NVIDIA 卡也能跑（CPU / Apple Silicon / 各种边缘设备），GGUF 格式的发源地 本地、离线、消费级硬件 低，提供 server，仍需补齐部署侧鉴权、配额与运维
Ollama llama.cpp 之上的一层"能用就行"的包装，一条命令拉模型就跑 ⭐ 本地开发、demo、个人使用 极低

其实只有四个问题要问

流程图

① 你要的是"跑起来"，还是"扛住流量"？
跑起来→Ollama（或 LM Studio）→⭐ 到此为止，别往下看了
② 有 NVIDIA 卡吗？
没有（CPU / Mac / 边缘）→llama.cpp + GGUF 路线
③ 模型和硬件会变吗？
不变，而且延迟/成本已经是核心 KPI→TensorRT-LLM
（⚠️ 需核对具体版本/后端的准备、加载与预热代价）
会变（还在选模型、还在调）→别碰编译型的
④ 你的请求之间前缀重合度高吗？
高（Agent、多轮、大量共享 few-shot）→SGLang
一般→vLLM ⭐ 默认答案

⭐ TGI 和 LMDeploy 属于"生态贴合"型的选择： 不是因为它们更快，而是因为你已经在那套生态里了，接起来省事。 选型的时候，"团队已经会什么"是一个合法的、而且经常被低估的判据。

⚠️ 一个反直觉但很重要的建议：先别去挑性能最高的那个。 主流引擎之间的差距通常在 20-50% 这个量级； 而你有没有开对连续批处理、前缀缓存、量化（第 17、16、18 章），差的是几倍。 💥 大部分"框架 A 比 B 快 3 倍"的评测，拆开看都是配置没对齐 —— 一边开了连续批处理一边没开，那测的不是引擎。

顺序：先把配置调对，再考虑换引擎。

再分清谁负责哪一层：调用外部 API、自行部署已有引擎、扩展已有引擎、自研核心运行时，是四种不同投入；自己部署 vLLM 不等于自研引擎。先列必须的模型、硬件、调度与服务能力，核对具体版本并测出差距，再评估现有方案及扩展是否可行；例如自定义模型注册可能只需扩展，不能预设某项能力今天仍不受支持。只有确认关键缺口后，才给自研原型预算，同时核算正确性、版本兼容、升级维护与运维成本。比较时固定模型、精度与质量要求、输入/输出长度分布、硬件、并发及到达模式、SLO；没有统一的 QPS 或收入门槛，也不能先许诺提速倍数。

🌳 RadixAttention：把前缀共享从"一条"推进到"一棵树"

这个机制值得单独讲，因为它和你已经学过的东西是同一条线上的下一步。

第 16 章的前缀缓存解决的是"所有请求共享同一个系统提示词"， 第 17 章的块共享让这件事在实现上几乎免费。 但它们的匹配方式是线性的：从头比对，命中一条前缀。

而真实的 Agent 负载长这样：

RadixAttention 做的就是：把 KV Cache 的索引组织成一棵基数树（radix tree，也就是压缩过的前缀树）。

算一算

· 树上每条边 = 一段 token 序列，对应一批 KV 块

· 新请求来了，沿树往下走，能匹配多远就复用多远

→ 只有【分叉之后】的那部分才需要重新 Prefill

· 缓存满了按 LRU 淘汰【叶子】

⭐ 只淘汰叶子，因为父节点还被别的分支用着

线性前缀缓存（第 16、17 章） RadixAttention
匹配结构 线性：从头比对，命中一条前缀 树：分叉点自动被发现
淘汰 按块 LRU 按叶子 LRU，感知父子依赖
收益最大的场景 固定的系统提示词 多轮 + 分叉：Agent、多候选生成、树搜索、共享 few-shot ⭐

⭐ 两者不是互斥的，思路完全一样（"算过的 KV 别重算"）， RadixAttention 是它在数据结构上的推进，而且各家引擎都在往这个方向收敛。

⚠️ 所以真正的判断依据不是"哪个框架有这个功能"， 而是【你的请求之间到底有多少共享前缀】 —— 一点都不共享，两者都白搭。 这件事你可以在换引擎之前就自己统计出来。

💡 顺带一条容易漏掉的能力：如果你要在一个基座上热挂多个 LoRA 适配器 （多租户各自微调一份），主流引擎大多支持这类"多 LoRA 服务" —— 它省的是"每个租户开一份完整实例"的显存。有这个需求的话，选型时要单独确认。

📏 二、先定 SLO，再谈优化

三个词别混用：SLI 是有口径和统计窗口的观测量；SLO 是给它设定的目标；SLA 是服务约定及未达约定时的后果，须由具体业务确定，不能拿教程示意值代替。下列延迟/可用性数字是目标示例，不是统一标准；还要说明请求范围、输入/输出长度、分位数或成功比例及统计窗口。

操作步骤

⚠️ 最常见的错误：不定目标就开始调优
你不知道调到什么程度算够，也不知道该牺牲什么
⭐ 一个推理服务的 SLO 至少要包含：
· TTFT P95 < 500ms （首字延迟）
· TPOT P95 < 50ms （每字延迟→20 tok/s，比阅读速度快）
· 可用性 99.9%
· 吞吐 ≥ X tokens/秒

不同场景的教学目标示例（须按实际需求验证）：

场景 TTFT TPOT 吞吐
代码补全 < 200ms ⭐ < 30ms 中
聊天机器人 < 1s < 50ms 中
Agent / 长推理 宽松 < 30ms ⭐（输出很长） 中
批量处理 无所谓 无所谓 最大化 ⭐
语音对话 < 300ms < 40ms 低

🔑 定 SLO 的意义：它把"越快越好"变成一个可以做取舍的工程问题。 知道 TPOT 只要 < 50ms，你就可以放心地把 batch 调大去换吞吐 —— 在不定 SLO 的情况下，你会盲目地优化延迟到远超需求的程度，白白损失吞吐。

🏗️ 四、部署架构

可选：Redis 租约怎样给路由器提供成员？

限定 Redis 7.2 单实例：每服务/稳定实例号一个 key，值含 endpoint、模型版本、phase、每次启动唯一且不复用的 incarnation/token，key 自身带 TTL。用 SET key value NX PX ttl_ms 原子注册，已有 key 不覆盖；租约内身份绑定不变，同 token 不能改 endpoint/版本。注册存在、TCP 可达、模型 ready 是三件事，新流量还须通过本页已有就绪检查。

同一稳定实例号的协议状态例，A/B 是不同启动 token
情形条件与结果
① A 注册先以 loading 建租约；未变为 ready 或模型版本不匹配，不进入新流量集合。
② A 续约/更新阶段在一个 Lua 脚本内读取并比较 token 和绑定身份，匹配才 PEXPIRE；续约只延 TTL。phase 更新也须同一原子条件检查，仅改阶段并保留到期时间，不能借机换身份。
③ 后台发现取值并核有效租约、ready 与目标模型版本；loading/draining 排除。注册记录只是发现候选，不能代替模型就绪证据。
④ A 过期后 B 接替B 用新 token 注册同 key。主动摘除也须同一 Lua 脚本原子比较 token/身份后才 DEL；旧 A 的续约和摘除均不能改动 B。不能先 GET 检查、再裸 DEL/PEXPIRE。

发现端在后台限量、限时续扫；SCAN 返回 cursor=0 才结束一轮，空批次不代表结束，结果须去重，并发变化仍非快照。原子读取值与剩余 TTL，缓存上限与剩余 TTL 取短、从刷新发起时刻计时；刷新失败或到期后，停止给未重新确认的成员新流量，不延长旧缓存。不能每请求 KEYS 全库，也不能只靠过期通知维护集合；排空沿用下方流程。

TTL 过期只表示租约失效，不证明旧进程已停。暂停、网络分区和缓存延迟仍可能留下陈旧判断；Redis 故障、异步复制切换也不能保证强一致成员视图或外部工作独占。原子比较只约束本 Redis 实例的记录操作，不能升级为全局共识。此表是协议例，未运行 Redis 服务、故障切换或压测。

路由策略的选择（比想象中重要）：

策略 说明
轮询 实现简单，可作基线；请求成本相近、到达较均匀时较合适，但不看实例当前积压
最少请求数 按未完成请求数分配，适合请求成本相近的情况；A 只有 1 个长请求、B 有 2 个短请求时，A 未必更空闲
最少待处理 token ⭐ 用排队及执行中请求的剩余 token 估计工作量，能反映长度差异；输出长度未知，Prefill/Decode 每 token 成本也不同，估计仍需校准
前缀感知路由 ⭐ 尽量把可复用前缀送到同一实例，增加缓存复用机会；还要看缓存容量与实例负载，热门前缀的黏性可能造成倾斜

⭐ 多租户各有长系统提示词时，黏性路由可能提高复用，也可能把热点挤到少数实例。不能只看命中率：在相同模型、提示分布、到达负载与副本资源下，对照待处理工作量、排队延迟和 SLO，再权衡复用与负载均衡；不能因命中更多就断言整体更快。这里没有执行路由压测，不给通用收益率。

实例数够不够，先数就绪的：扩容目标不等于已经可服务；新副本完成准备/加载、预热和就绪检查后才放流量。缩容先停止接新请求、排空再回收。把这些状态与排队、尾延迟和错误一起看，就能衔接上面的部署图；完整闭环可选读。

深入：把监控、扩缩与就绪串起来（可跳过）

先划清责任：模型选型、开放权重与自建责任见 导论 07b；托管 API 的超时、重试与配额见 AI 全栈 04。只有在自己负责模型服务实例时，才直接管理下面的模型副本；不能把供应商的约定当作本地服务已验收。

环节证据与动作容易误判的边界
① 观测按固定窗口汇总待处理 token/请求、排队时间、TTFT/TPOT 分位数、错误/取消和 KV/资源占用；保留输入/输出长度分布。不只盯 GPU 或一个 KV 百分比。先区分负载增长、长请求与引擎故障，再选限流、降级、扩容或修故障。
② 提出扩缩目标根据相同模型与负载下的容量证据、成本预算、最小/最大副本数和资源可用性提出 desired；设置观察/稳定窗口及变化速率。阈值、迟滞和冷却依控制器/业务设计；不能把教程值直接上线，也不能瞬间按 desired 记可用容量。
③ 加载与就绪新副本准备运行环境与必要算子/后端，加载正确版本，预热并通过约定的功能/就绪检查后才进入路由。进程启动或健康端点返回不一定证明模型已满足服务目标；具体加载/编译步骤按版本和执行后端核对。
④ 排空与回收缩容先摘除新流量，处理在途请求；按已定超时/取消策略结束，再清理请求/KV与回收资源。直接杀掉活跃副本会影响长请求。取消信号到达不等于清理已经完成，需按实现确认生命周期。
⑤ 回看用户目标新副本 ready 或缩容后，继续按同一窗口比较尾延迟、排队、错误、质量约束和成本；异常时按预案限流、降级或回退。扩容不保证消除故障或提高质量。故障重启、过载降级和按负载扩缩是不同动作，不能互相代替验收。

未执行的教学状态记录：假设每个模型副本内部 TP=2，以下只演示状态，不是流量或吞吐实测。

  1. t0：ready=2，排队在观察窗口内持续上升；策略提出 desired=3。
  2. t1：第 3 个副本仍 loading/warming，ready 仍为 2；此时不能宣称容量已经增长 50%。
  3. t2：第 3 个副本通过 ready 检查后才接新流量，继续看同口径尾延迟/错误。新增这个 TP=2 副本还需要相应资源，不是把原副本 TP 改成 3。
  4. t3：缩容时选中一个副本进入 draining，不再给它新请求；在途请求按约定完成或超时/取消，确认清理后才回收。desired、ready、draining 要分别记录。

系统/数据/模型三层监控已有 监控章，不在这里重讲。若使用 Kubernetes，HPA 的自定义指标、readiness 与稳定窗口可作为一种实现；也可以采用其他控制器，不要求安装集群。用 vLLM 等引擎时核对实际版本暴露的指标和含义，不能只复制名字。

依据：Google SRE · SLI/SLO/SLA、HPA 控制与就绪条件、vLLM 指标说明、TensorRT-LLM 执行后端说明。这里没有部署服务、运行压测或证明任何 SLA 已达成。

💰 五、算清成本

算一算

每百万 token 成本 = GPU 小时单价 ÷ (吞吐 tok/s × 3600) × 1e6

例：A100 按 $2/小时，实测吞吐 5000 tok/s

→ 2 / (5000 × 3600) × 1e6 = $0.11 / 百万 token

def cost_per_million(gpu_hourly, tokens_per_sec, n_gpus=1, utilization=0.6):
    """utilization: 平均负载率——⭐ 这个数字最容易被忽略"""
    effective = tokens_per_sec * utilization
    return gpu_hourly * n_gpus / (effective * 3600) * 1e6

print(f"${cost_per_million(2.0, 5000):.3f} / 百万 token")   # $0.185

⭐ 注意 utilization 那一项： 大部分服务的平均负载只有峰值的 30-60%（夜间几乎没流量）。 按峰值算容量、按平均算成本 —— 这两个数不能混。

💡 降成本的三个方向： ① 提高吞吐（前面五章） ② 提高利用率（把离线批量任务填到低峰期）⭐ ③ 用更便宜的卡（量化后可能装得下）

事项 做法
限流 按租户/API key 限 QPS 和 token 速率 ⭐
超时与取消 客户端断开要立刻停止生成并释放 KV Cache ⭐
优雅关闭 停止接新请求，等在跑的完成再退出
健康检查 不只是 ping，要真跑一次推理
降级 过载时切到小模型 / 降低 max_tokens / 排队

💥 "客户端断开不取消"是一个真实且昂贵的 bug： 用户关掉页面后，服务器还在为他生成 2000 个 token， 占着 KV Cache 槽位不放 —— 高并发下这会显著吃掉容量。 确认你的框架真的处理了 disconnect。

对照

⭐ 必须有的指标：

【延迟】TTFT / TPOT 的 P50、P95、P99；同窗口看分布，不只看平均

【吞吐】tokens/秒（输入和输出分开统计）⭐

【业务】每租户的 token 消耗

⭐ KV Cache 使用率是容量相关信号之一： 持续高占用提示风险，但 90% 不是通用抢占阈值。是否抢占/重算及延迟变化还取决于引擎、缓存策略和请求分布；与排队、错误、实际抢占次数一起核对，不能只据一个百分比决定扩容。

👀 答案
  1. ①要"跑起来"还是"扛住流量"（跑起来 → Ollama，到此为止）②有没有 NVIDIA 卡（没有 → llama.cpp + GGUF）③模型和硬件会不会变（不变且性能是 KPI → TensorRT-LLM）④请求之间前缀重合度高不高（高 → SGLang）。默认答案是 vLLM。TGI / LMDeploy 是"生态贴合"型的选择——"团队已经会什么"是一个合法且常被低估的判据。
  2. 需按具体版本、后端和模型核对支持、准备、加载及预热成本；预构建 engine 不是所有执行路线的共同前提。模型/硬件稳定且延迟或成本重要时值得与其他候选同口径比较，不能把更换配置一概写成必须重编。
  3. 因为主流引擎之间的差距通常只有 20-50%，而你有没有开对连续批处理、前缀缓存、量化，差的是几倍。💥 大部分"快 3 倍"的评测拆开看都是配置没对齐（一边开了连续批处理一边没开）。顺序：先把配置调对，再考虑换引擎。
  4. 普通前缀缓存的匹配是线性的（从头比对，命中一条前缀）；RadixAttention 把 KV Cache 的索引组织成一棵基数树，分叉点是自动被发现的，沿树往下能匹配多远就复用多远，只有分叉之后的部分才重新 Prefill。只淘汰叶子是因为父节点还被别的分支用着。
  5. 看你的请求之间到底有多少共享前缀——不是"哪个框架有这个功能"。一点都不共享，两者都白搭；而这件事在换引擎之前就能自己统计出来。
  6. 因为不定目标就不知道调到什么程度算够、该牺牲什么。不定 SLO 会盲目优化延迟到远超需求的程度，白白损失吞吐。
  7. 代码补全 TTFT 极敏感（<200ms，用户等不了）；Agent 输出很长，TPOT 是决定性的，TTFT 反而宽松。
  8. 用固定长度的输入输出。真实流量长度方差极大，固定长度会让连续批处理的收益被严重高估。要用 ShareGPT 这类真实分布或线上日志回放。
  9. 在固定模型/硬件/配置和请求长度分布下，延迟-吞吐曲线支持一个容量候选；64 只是示例，还需核对其他目标和余量。ceil(峰值并发/候选容量) 只是静态起点，扩缩要另看排队、就绪副本与冷启动时间。
  10. 前缀感知路由——把可复用前缀尽量送到同一实例，增加复用机会；也要防止黏性热点造成负载倾斜，按同负载的排队延迟与 SLO 验证，不预设命中率或提速幅度。
  11. 因为大部分服务的平均负载只有峰值的 30-60%（夜间几乎没流量）。按峰值算容量、按平均算成本，两个数不能混。
  12. 用户关掉页面后服务器还在生成 2000 个 token，占着 KV Cache 槽位不放——高并发下会显著吃掉容量。
  13. 结合待处理请求/token、排队时间、TTFT/TPOT 分位数、错误与实际抢占/重算、KV 和资源余量；要保持相同窗口和负载口径。90% 不是通用抢占阈值，一个百分比或 GPU 利用率都不能单独决定扩容。
  14. 平均值可能掩盖长请求、抢占和排队的尾部影响。30ms/800ms 只是教学示意；同时看分位数、分布、窗口和失败请求，按业务目标判定，不能用一个 P99 代替全部体验。
  15. SLI 是带口径/窗口的观测，SLO 是目标，SLA 是服务约定及后果。desired 是目标而非已可服务的副本；新副本加载/预热/就绪后才放流量。缩容先摘除新请求并按超时/取消策略排空与清理，再回收。模型副本和副本内 TP 度数也不是同一个扩容维度。

⚡ 走神救援

扩缩闭环只记三步：观测负载与用户目标→新副本就绪后放流→旧副本排空后回收。desired 不等于 ready；SLI、SLO、SLA 不混用。2/3 副本与 64 并发都是示意，没有替代实际压测或服务验收。

⭐ 选引擎只要四个问题：跑起来还是扛流量 → 有没有 N 卡 → 模型和硬件会不会变 → 请求之间前缀重合度高不高。vLLM 是默认答案；SGLang 适合前缀重合度高的负载；TensorRT-LLM 的支持与准备成本需按具体版本/后端核对，不能一概写成更换配置必重编；llama.cpp 管没有 N 卡的场景。

⚠️⭐ 反直觉但最重要：先别挑性能最高的。 引擎之间通常只差两三成，而有没有开对连续批处理、前缀缓存、量化差的是几倍——💥 大部分「框架 A 快 3 倍」的评测拆开看都是配置没对齐。

⭐ RadixAttention 该不该在意，看的不是「哪个框架有这功能」，而是你的请求之间到底有多少共享前缀——不共享就都白搭。

⭐ 先定 SLO 再优化：不定目标就会盲目把延迟压到远超需求、白白损失吞吐。同负载与配置下的「并发→吞吐→延迟」曲线支持容量候选，还须核对资源、错误和启动余量，⚠️ 最常见的错误是用固定长度输入输出——真实流量方差极大，固定长度会严重高估连续批处理的收益。

路由用前缀感知（同租户固定到同一实例，命中率能从三成提到九成）。⭐ 算成本别忘了利用率：按峰值算容量、按平均算成本。

生产五件事里最贵的一条：💥 客户端断开不取消是真实且昂贵的 bug——用户关了页面，你还在生成并占着 KV Cache 槽位。⭐ 监控把 KV、排队、实际抢占/重算、错误与尾延迟一起看；百分比和分位数要有负载口径/窗口，不能把 90% 或一个 P99 当通用通过标准。
