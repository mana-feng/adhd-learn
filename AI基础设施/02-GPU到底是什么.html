02 · GPU 到底是什么

⏱ 26 分钟 ｜ ⭐ 不需要写 CUDA，但要知道它长什么样

🎯 一句话

GPU 擅长让大量数据一起做相似的运算；它不保证把任何程序都加速。

例如，神经网络的一层要做很多乘加。这些运算能成批安排给 GPU，而不是一项项等 CPU 做完。

本章只抓三件事：谁在算、数据放哪、为什么有时算不快。 先看图和结论；规格表与访存算账可以需要时再回来。

🆚 一、CPU vs GPU

比较什么 CPU 的侧重点 GPU 的侧重点
设计目标 尽快完成一条复杂任务 提高大量任务的总吞吐
常见优势 分支复杂、依赖强、任务较小 规模较大的并行运算
“核心”口径 能独立处理复杂指令流的 CPU 核 CUDA Core 等算术单元，不能与 CPU 核一对一比较
等待数据时 缓存、乱序执行等机制减少等待 缓存、数据复用与调度其他就绪 warp 配合

不要用“博士生和小学生”理解两者。 它们是不同的硬件组织方式，不是智能程度不同。CPU 也能并行，GPU 也能处理分支。

深度学习中的矩阵运算适合 GPU 的并行组织，专用矩阵单元和软件库也很重要。但小任务、频繁搬运数据或串行依赖，都可能抵消加速收益。

🏗️ 二、GPU 的层次结构

看图时，从内向外分三层就够了：

  • 一个 SM 内有什么？ SM 是流多处理器，包含执行单元、寄存器及局部存储。CUDA Core 处理通用算术；Tensor Core 处理特定矩阵运算。
  • 多个 SM 共享什么？ 它们通过 L2 缓存访问显存。寄存器和 Shared Memory（共享内存）可以保存局部数据，减少重复读取。
  • 哪些数字不能背成通则？ SM 数量、寄存器、L1 / Shared Memory、L2 和显存容量都随型号变化。例如 A100 有 108 个 SM、40 MB L2；不是所有 GPU 都有“100 多个 SM”。

为什么这里提 FlashAttention？ 它会分块复用片上存储，减少中间结果往返显存；并不是整张注意力矩阵都能装进 Shared Memory。见第 8 章。

架构与示例数字依据：NVIDIA GPU 性能背景指南。

⭐ Tensor Core：为什么它改变了一切

Tensor Core 把一组矩阵乘加交给专用硬件，合适的运算可以有更高吞吐。

CUDA Core 可以参与普通乘加；Tensor Core 执行矩阵乘加 D = A×B + C。常见教学图里的 4×4 是早期硬件示例，不是所有代际、所有指令的固定大小。

以 A100 为例，以下是非稀疏理论峰值，不是一段训练程序的实测速度：

运算路径 峰值 怎么读
FP32 普通算术 19.5 TFLOPS 本表比较基准
TF32 Tensor Core 156 TFLOPS 峰值是上行的 8 倍，输入计算精度不同
BF16 / FP16 Tensor Core 312 TFLOPS 峰值是基准的 16 倍，不代表训练快 16 倍
INT8 Tensor Core 624 TOPS 整数运算，用 TOPS；不与浮点精度混为一谈

数字来源：NVIDIA A100 规格。带“稀疏”标记的峰值另有使用条件，本表没有使用它们。

混合精度为什么可能更快？ 一方面，较小的数据类型减少显存占用与搬运；另一方面，合适的矩阵运算能使用高吞吐路径。它不是无条件的“免费午餐”，仍要检查数值稳定性与实际耗时，见第 6 章。

不是只有半精度才能用 Tensor Core。 TF32 也是例子；Ada 架构的 Tensor Core 还支持 FP8，但硬件支持不等于当前框架和算子已启用。

维度对齐是效率建议，不是统一的准入门槛。 NVIDIA 文档说明：cuBLAS 11.0、cuDNN 7.6.3 起，Tensor Core 不再要求所有相关维度必须对齐才能使用。对齐仍可能更高效，具体要求取决于数据类型、硬件和库版本；不能仅凭 4095 而不是 4096 就断定“退回 CUDA Core”。矩阵乘性能指南、Ada 调优指南。

🧵 三、执行模型：warp 和它的两个坑

warp 是 NVIDIA CUDA 执行模型中一组 32 个线程。 多个 warp 组成 block，多个 block 组成 grid。

一个 block 的线程在同一个 SM 上执行；一个 SM 可以同时容纳多个 block，但数量受寄存器、共享内存等资源限制。

SIMT 可以先理解为：向一组活跃线程发出同一条指令，各线程处理各自的数据。 线程可以走不同分支；此时不是 32 个线程永远一起执行每一步。较新架构还有独立线程调度，不能自行假定线程之间已经同步。

坑 ① warp divergence（分支发散）

同一个 warp 走不同分支，可能让部分执行通道暂时闲着。慢多少要看分支里的工作。

假设偶数编号线程做 A，奇数编号线程做 B：

当前执行的分支 哪些线程参与 另一些线程
A 偶数编号线程 不执行 A 的结果写入
B 奇数编号线程 不执行 B 的结果写入

如果 A、B 工作量相近，分别执行两条路径会比所有线程一起做其中一条更贵。但不能直接得出“耗时翻倍”：路径长度、编译器是否用谓词化指令，以及访存等待都会影响开销。

下一步不是删掉所有 if，而是用性能分析工具确认分支分歧是否真是瓶颈。

坑 ② 非合并访存（uncoalesced access）

同一组线程要的数据越分散，可能需要搬入越多用不上的数据。

用一个有明确条件的例子算账：在以 32 字节扇区处理请求的现代 CUDA 设备上，一个 warp 的 32 个线程各读一个 4 字节数，共需 128 字节。

地址分布 覆盖的 32 字节扇区 请求覆盖的数据量
连续，起点按 32 字节对齐 4 个 128 字节
每个线程落到不同扇区 最多 32 个 最多 1024 字节

第二行只有 128 字节是本次真正需要的，按这个例子计算利用率是 128 / 1024 = 1/8，不是 1/32。

这也不是程序必然慢 8 倍：缓存命中、相邻 warp 的复用、对齐与其他瓶颈都会影响时间。NVIDIA 全局内存访问说明。

它和 PyTorch 的关系：先区分“布局”与“访问方式”。 转置通常只改变 stride（相邻元素的地址步长），不搬数据；contiguous() 可以复制成连续布局。但访问能否合并，还取决于算子怎样把数据分配给线程。

下面只观察布局与形状，不测 GPU 性能。安装 PyTorch 后可在 CPU 运行；有 CUDA 时使用 GPU。矩阵缩小是为了方便观察，原理不依赖 4096 这一大小。

import torch

device = 'cuda' if torch.cuda.is_available() else 'cpu'
x = torch.arange(16, dtype=torch.float32, device=device).reshape(4, 4)
w = torch.ones(4, 2, device=device)
y = x.t()                      # 转置视图：没有重排底层数据
y_contiguous = y.contiguous()  # 复制为连续布局

z = y @ w                      # 矩阵乘可以接受这个非连续输入
z_contiguous = y_contiguous @ w

print("device:", device)
print("stride:", y.stride(), y_contiguous.stride())
print("contiguous:", y.is_contiguous(), y_contiguous.is_contiguous())
print("shape:", tuple(z.shape))
print("same result:", torch.equal(z, z_contiguous))

你应看到什么？ stride 分别为 (1, 4)、(4, 1)，连续性分别为 False、True；两个输出形状均为 (4, 2)，本例的整数值可精确表示，结果相同。

不要因此到处补 contiguous()。 矩阵乘库可能直接支持转置布局；一次额外复制反而会增加时间。性能比较要包含复制成本，并按第 4 章的方法测量。

为什么调度其他 warp 能掩盖延迟？ 当一个 warp 等数据时，SM 可以执行另一个已经就绪的 warp。但驻留数量多（occupancy 高）不等于就绪任务足够，也不保证更快。

小 batch 有时不能提供足够并行工作；有时瓶颈却是访存、启动开销或形状。不要仅凭 batch 小就确定原因。

📊 四、几张主流卡的关键数字

这里保留 A100、H100、RTX 4090 三个代际示例，用于学习读规格，不是当前购买推荐。

比较项 A100 80GB SXM H100 SXM RTX 4090
BF16 Tensor Core，FP32 累加 312 TFLOPS 约 989 TFLOPS 约 165 TFLOPS
FP8 Tensor Core 不支持 约 1979 TFLOPS 支持；须区分累加精度与软件支持
显存 80 GB HBM2e 80 GB HBM3 24 GB GDDR6X
显存带宽 约 2.04 TB/s 3.35 TB/s 约 1.01 TB/s
NVLink 标称双向汇总带宽 600 GB/s 900 GB/s 无 NVLink

表内算力均按非稀疏峰值理解。RTX 4090 的约 165 是 FP32 累加口径；不能拿其他累加精度或稀疏峰值混比。来源：A100、H100、RTX 4090、Ada 架构规格附录。

卡间通信要另算。 RTX 4090 走 PCIe 4.0；x16 链路理论上约 31.5 GB/s 单向、63 GB/s 双向合计，不能把“双向约 64”当成单向 GPU 间有效速度。实际还受主板拓扑、通道宽度、驱动及点对点传输支持影响。

这不等于多卡训练“基本不可用”。 数据并行与张量并行的通信需求不同；24 GB 容量可能先成为限制，也可能是频繁通信限制扩展。应实测目标任务，再看第 12 章如何分析通信。

FP8 也不是切个开关就稳。 它对表示范围和精度的取舍更激进，需要合适的缩放与数值验证；缩放粒度依实现而定，不只一种 per-tensor 方案。

🧰 五、你实际会碰到的抽象层

先写框架运算，再定位具体实现；不要把所有库当成每次都会依次经过的步骤。

  • 你写的接口： 例如 PyTorch 的 torch.matmul。
  • 后端的实现选择： 可能调用 cuBLAS、cuDNN 等库，也可能使用编译生成或自定义 kernel。CUTLASS 是构建高性能矩阵运算的模板库，并非每个算子的必经一站。
  • 执行依赖： 运行时和驱动把工作提交给硬件。

先使用现有实现。确认瓶颈在某个算子后，再考虑 CUDA 或 Triton；Triton 使用 Python 风格接口，但仍需要理解并行与访存，见第 7 章。

下面的命令用于已安装 NVIDIA 驱动的环境；部分监控功能受操作系统和设备支持限制。

# 三个你一定会用到的命令
nvidia-smi                    # 看显存占用、利用率、温度、功耗
nvidia-smi topo -m            # ⭐ 看卡间互联拓扑（NVLink 还是 PCIe）
nvidia-smi dmon -s pucm       # 持续监控

GPU-Util 100% 不等于算力用满。 它描述采样期间 GPU 执行 kernel 的时间占比，一个受访存限制的 kernel 持续运行，也能让该值很高。

✅ 检查点

  1. CPU 和 GPU 的设计目标有什么侧重？为什么不能直接比“核心数”？
  2. GPU 靠什么掩盖内存延迟？小 batch 一定是 warp 不够吗？
  3. Tensor Core 做什么？A100 上的“16 倍”是什么口径？
  4. 混合精度为什么可能快？矩阵维度不对齐就一定不能用 Tensor Core 吗？
  5. 什么是 warp？分支发散为什么可能变慢，而不固定慢两倍？
  6. 本章连续与分散访存各覆盖多少个扇区？contiguous 能保证算子访问合并吗？
  7. 比较 RTX 4090 与数据中心卡，除算力还要看什么？
  8. 为什么 GPU-Util 100% 不能证明没有优化空间？
👀 答案
  1. CPU 偏重复杂任务的响应，GPU 偏重大量运算的吞吐。CPU 核与 CUDA Core 的功能口径不同，不能一对一比较。
  2. 缓存、数据复用及调度就绪 warp 配合。小 batch 可能并行度不足，也可能受访存、形状或启动开销限制，需要测量。
  3. Tensor Core 处理特定矩阵乘加。312 / 19.5 = 16 比的是 A100 的 BF16 Tensor Core 与 FP32 普通算术理论峰值，精度不同，不是训练加速承诺。
  4. 数据更小可减少搬运，合适的矩阵运算也可走高吞吐路径。TF32 同样能用 Tensor Core；现代库中对齐常是效率因素，不是统一的硬性门槛。
  5. CUDA warp 通常包含 32 个线程；分歧会使一部分线程不参与当前路径。实际代价随路径长度、编译和其他等待变化。
  6. 在本章对齐、每线程读 4 字节的例子中，连续覆盖 4 个扇区，完全分散可覆盖 32 个；后者有效字节比例是 1/8。张量连续性和线程访问方式是两件事，不能仅看 contiguous 判断速度。
  7. 显存容量、显存带宽、互联与软件支持。PCIe 的单双向口径要分清；多卡效率取决于并行方案和通信量，不是“没有 NVLink 就不能训练”。
  8. GPU-Util 主要描述 kernel 活跃时间；仍可能受访存或低效算子限制。应结合吞吐、延迟和性能分析，训练时再看 MFU 等指标。

⚡ 走神救援

先记住这几件事

  • GPU 通过大量并行任务提高吞吐；先认清 SM、缓存和显存。
  • Tensor Core 面向矩阵运算，收益受精度、形状与实现影响，规格峰值不是实测速度。
  • 分支和访存的代价要测；不要把“慢两倍”“带宽 1/32”当成定律。
