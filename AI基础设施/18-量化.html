18 · 量化

⏱ 32 分钟（参考，可分次读） ｜ ⭐ 少存、少搬，但要实际验证速度与质量

🎯 一句话

量化用更少的位数表示数值，可以减少权重或缓存的存储；是否更快，要看当前瓶颈和执行它的算子。

不要先背“INT4 快四倍”。先问：量化的是权重、激活还是 KV Cache？推理引擎是否真的用上低精度格式？你的任务质量能否接受？

📉 一、为什么小批量解码值得先看量化

在小批量、逐 token 解码、权重读取占主要时间时，减少权重搬运量可能很有效。大批量、长上下文、prefill、通信或调度开销占主导时，瓶颈会不同。见 第 15 章。

下面沿用 第 4 章 的心算模型，但把假设写在数字旁边：

  • 模型恰好有 70 亿个参数，所有权重使用同一位宽。
  • 有效带宽理想化取 2000 GB/s，GB 按十进制计算。
  • 每生成一个 token 读取一遍全部权重；忽略缓存复用、KV、计算、反量化、元数据和其他开销。
权重格式 纯权重字节数 2000 GB/s ÷ 纯权重大小
BF16，2 字节/参数 14 GB 约 143 token/s
INT8，1 字节/参数 7 GB 约 286 token/s
INT4，半字节/参数 3.5 GB 约 571 token/s

看最后一列的比例，不把它当实测吞吐。 理想权重读取时间依次减半，但实际解码不保证按 2 倍、4 倍提速，甚至可能因算子或反量化开销变慢。

量化的三个潜在收益：

  1. 权重读取更省，可能降低单 token 延迟。
  2. 腾出显存，可能容纳更多请求或更长上下文。
  3. 降低部署容量要求，但换硬件后仍需重新核对速度、质量和成本。

训练同样可能受益于低精度计算、通信或存储。不能把“训练最多 BF16/FP8”写成技术上限；QLoRA 等路线使用低比特冻结基座，QAT 则让权重适应量化误差，两者都不等于所有训练状态以相同低位宽计算。

🔢 二、量化的基本原理

先把实数映射到有限整数格子，再用比例尺近似还原：

$$\begin{aligned} q&=\operatorname{clip}\big(\operatorname{round}(x/s)+z,\ q_{\min},q_{\max}\big)\\ \hat{x}&=s(q-z) \end{aligned}$$

  • s 是正的 scale（比例尺）：每一格对应多大的实数变化。
  • z 是整数 zero point（零点）：实数 0 对应哪个整数。
  • round 负责舍入；clip 把超出范围的整数截到端点。
  • x̂ 是还原值，通常不等于原来的 x。

一个口径一致的对称 INT8 例子： 使用整数范围 −127～127，z=0，实数参考范围 −0.5～0.5，因此 s=0.5/127≈0.003937。

步骤 对 x=0.3 的计算
除以 scale 0.3 ÷ (0.5/127)=76.2
舍入与截断 q=76，仍在范围内
还原 x̂=76×0.5/127≈0.299213
误差 x̂−x≈−0.000787

这里特意不用 −128 这个编码来保持对称。非对称量化可以利用不对称范围，但要相应计算和约束零点，不能把不同方案的 scale 混在同一个例子里。

选择 含义 代价与边界
对称 / 非对称 本例 z=0；其他方案允许偏移 非对称范围可能减少误差；是否更准、更快取决于分布与算子
per-tensor 整个张量共用 scale 元数据少，但跨度差异较大的位置可能互相牵制
per-channel 不同通道分别定 scale 通道轴要按当前运算定义
per-group 如每 128 个权重一组 128 只是候选；组越细通常有更多尺度信息，也增加存储和执行开销

粒度更细不自动保证端到端质量更好。比较时还要一致地计算 scale、zero point、分组方式和实际内核支持。

😖 三、离群值：LLM 量化的核心难题

如果少数值把量程拉得很宽，常见的小值会挤在很少几个格子里。 不是所有模型都固定存在“100 倍离群值”，也不是有离群值就必然失效。

以这一组人工数值为例：

位置 0 1 2 3 1024 4096
值 0.3 0.2 −0.4 0.5 87.2 0.1

若按最大绝对值做对称 INT8 量化，s=87.2/127≈0.687。于是 0.3/s≈0.437、0.2/s≈0.291，舍入后都变成 0；它们原来的区别丢了。

这个例子解释的是量化误差的来源，不是实际模型精度下降的测量。

方法 它在处理什么
LLM.int8() 对某些离群激活维度使用较高精度的混合计算，其他部分使用 INT8
SmoothQuant 对匹配通道做缩放：激活除以一个因子，权重乘以它；量化前乘积不变，尝试让激活更易量化
AWQ 利用激活信息识别对量化更敏感的权重/通道，通过尺度选择减小误差

“保护约 1% 的显著权重有效”是 AWQ 的实验观察，不是“剩下 99% 权重不重要”。 它也不等于直接把这一小部分全部保留成 FP16。对照 AWQ 原论文。

SmoothQuant 的等价性发生在量化前；量化后仍有误差与权重/激活之间的折中。见 SmoothQuant 原论文。

🧰 四、主流方法怎么选

先分清两条路：PTQ 和 QAT

PTQ 不通过常规量化感知训练来适应权重；QAT 则在训练中模拟或引入量化效应。 两条路线都可能用于 LLM，不能说 QAT 已经没有用处。

比较 PTQ（训练后量化） QAT（量化感知训练）
起点 已训练模型，应用选定量化方法 已有模型微调或训练流程中加入量化模拟
数据需求 因方法而异；静态校准常需代表性样本，某些动态方法不需预先校准集 需要适配任务的数据、训练目标与更新流程，不必拿到原始预训练全集
计算成本 取决于模型大小、方法与设备，不保证一张卡或几十分钟 增加训练成本，但不等于必须从头预训练整个模型
质量判断 INT4 不保证无损 可能恢复部分量化损失，低比特下也不保证成功

可对照 PyTorch 的 LLM QAT 流程。先试较低成本路线合理，但不能用“PTQ 绝对主流”代替自己的质量验证。

校准集不是测试集。 校准数据可能用于估计范围、选择尺度、衡量输入相关性或重建层输出，不同方法不只是在统计 min/max。

英文百科校准与中文客服流量差异大时，质量可能受影响；但掉分也可能来自位宽、模型结构、实现、提示模板或实际任务，不应未经调查就归因于校准集。

几百条只是一些方法的实验起点，不是充分性保证。使用有权使用、适当脱敏的代表性样本，覆盖语言、长度和关键场景；再用独立评测集验收，不能直接把所有线上日志当可用数据。

权重量化方法与格式

名称 是什么 需要核对什么
GPTQ 用层输入的二阶近似信息重建量化权重 校准数据、分组、位宽及推理内核
AWQ 激活感知的权重量化方法，常见 4bit 配置 当前模型、实现、格式与质量
GGUF / llama.cpp GGUF 是文件格式，llama.cpp 是执行工具，不是同一种量化算法 文件实际采用的量化类型、混合位宽和目标后端
bitsandbytes NF4 非均匀的 4bit 数值格式，见 QLoRA NF4 不等于均匀 INT4；冻结基座与可训练适配器的 dtype 要分别看

量化类型对比

类型 权重 / 激活 潜在收益与限制
W8A16 8bit 权重、16bit 激活 纯权重字节数约为 16bit 的一半；速度仍取决于低精度或反量化内核
W4A16 4bit 权重、16bit 激活 纯权重字节数约为四分之一，另有 scale 等开销；不等于完整服务显存减为四分之一
INT8 W8A8 权重与激活均为 INT8 可利用支持的整数矩阵算子，但还要处理尺度、离群值和质量
FP8 W8A8 权重与激活使用 FP8 格式 原生支持的设备可利用对应算子；精度、格式、粒度及引擎版本仍需匹配

W/A 说明位宽，不完整指定格式；W8A16 的“8”可能是不同整数或浮点方案。

H100 可以把 FP8 纳入候选；A100 也有多种 INT8/INT4 等路径；CPU 可考虑 llama.cpp 支持的格式。机型不是唯一选型条件，也不能由机型直接推出“首选且无损”。 实际支持以 vLLM 量化兼容表 和所用版本为准。

下面只示范参数的区别：三个选项互斥，一次调用只加载一个模型。 需要已安装 vLLM、匹配设备，以及你有权使用且格式匹配的模型路径。定义函数不会下载模型；调用才会加载。

from vllm import LLM

def load_one_quantized_model(model_path, mode):
    # 🧩 配置骨架：model_path 和硬件/版本兼容性由调用者确认
    if mode == "awq":       # model_path 须指向匹配的 AWQ 检查点
        return LLM(model=model_path, quantization="awq")
    if mode == "fp8":       # 核对当前版本支持的 FP8 在线量化路径
        return LLM(model=model_path, quantization="fp8")
    if mode == "fp8_kv":    # 只指定缓存格式，不等于把权重也量化
        return LLM(model=model_path, kv_cache_dtype="fp8")
    raise ValueError("mode 必须是 awq、fp8 或 fp8_kv")

代码中的 FP8 参数和缓存参数不能互相替代；缓存 scale 及 attention 后端另需核对。不要只凭模型名称包含“AWQ”就假定与当前引擎兼容，还要查实际格式和版本支持。

⚠️ 五、质量评估：这一步不能省

能加载、能输出，不代表量化后的质量合格。 不兼容的格式或算子也可能直接报错；“没有报错”只排除了部分实现故障。

按三层检查，并保留相同提示模板、分词、解码参数与评测口径：

  1. 困惑度（PPL）：对同一数据和分词口径检查语言建模损失，不代替任务效果。
  2. 下游能力：如数学、代码、问答，用与实际用途相关的基准及分组。
  3. 业务验收：关注关键人群、失败类型、输出约束，并同时测时延、吞吐和显存。

损伤可能因任务而异，但没有“闲聊总不变、数学与代码必然先坏”的排序。PPL 只涨 0.1 也没有统一的通过含义。

# 🧩 评测骨架：模型对象、evaluate 函数和独立测试集由调用者提供
def compare_quality(base, quant, evaluate, my_business_testset):
    results = {}
    for name, model in [("fp16", base), ("awq", quant)]:
        results[name] = evaluate(model, my_business_testset)
        print(name, results[name])
    return results

这里的名字使用 FP16/AWQ 对照，使用其他方案时同步改标签。

200 条评测、人工看 20 条可以是一次初步排查，不是验收门槛。样本量应服务于要检测的差异、风险分组及不确定性。

🧊 六、别忘了 KV Cache 量化

权重量化主要减少与参数规模有关的存储；KV Cache 还随着活动请求数、各请求缓存长度、层数与 KV 头数增长。

不是每个高并发服务都由 KV 占大头，也不是权重与缓存必须一起量化。先量出哪一部分占用较大，再分别评估。

算一次单请求的缓存大小。 假设普通多头注意力，各层尺寸一致，不共享前缀：

$$M_{\mathrm{KV}}=2LH_{\mathrm{KV}}dSb$$

  • M 是这一个请求的 KV 元素字节数；开头的 2 表示 K 和 V。
  • L=32 层，H_KV=32 个 KV 头，每头 d=128 维。
  • S=2048 个已缓存 token；FP16 每元素 b=2 字节。

先数元素：2×32×32×128×2048=536,870,912 个。

再乘每元素 2 字节：共 1,073,741,824 字节，即 1 GiB，约 1.074 GB。FP8 的元素存储理想减半，尚未计尺度与缓存管理开销。

理想容量示意 权重 单请求 KV 按总容量 80×10⁹ 字节计算的上限
7B FP16 权重 + FP16 KV 14 GB 1.073741824 GB floor((80−14)/1.073741824)=61
7B INT4 权重 + FP8 KV 3.5 GB 0.536870912 GB floor((80−3.5)/0.536870912)=142

这是忽略其他占用的容量上界，不是可承诺的并发数。 使用未舍入的字节数计算，本例为 61 与 142，约 2.33 倍；不能直接拿它安排线上容量。

实际要留出运行工作区、激活、内存管理和调度余量，并满足延迟目标。使用 GQA/MQA 时，KV 头数不同，不能只看到“7B”就套用同一缓存大小。

FP8 KV 的尺度与支持的 attention 后端需要匹配；是否同时降低 attention 计算精度也与后端有关。见 vLLM 的缓存量化说明。

✅ 检查点

  1. 哪些条件下，量化可能明显改善解码？为什么不能泛指全部推理？
  2. BF16→INT4 的 4 倍是什么模型下的比例，不是什么保证？
  3. 量化的三个潜在收益是什么？
  4. 离群值怎样让小值挤进同一个格子？
  5. SmoothQuant 与 AWQ 各在做什么？“1% 显著权重”不能推出什么？
  6. PTQ/QAT、校准集/评测集各有什么区别？
  7. W4A16、INT8 W8A8、FP8 W8A8 有什么不同？选型只看 GPU 够吗？
  8. 为什么没有报错也要评测？
  9. 如何核对不同任务和人群的质量？
  10. 权重与 KV 分别怎样占空间？为何不能只看“7B”算并发？
👀 答案
  1. 小批量逐 token 解码、权重读取为主要瓶颈且有合适内核时可能受益；prefill、大批量、长上下文或通信开销可能改变瓶颈。
  2. 是理想纯权重字节数的 1/4、对应权重读取模型下 4 倍速率，不是端到端实测。
  3. 减少权重读取、腾出容量、降低设备容量要求；都需要质量与服务指标验收。
  4. 量程变宽使 scale 变大，几个不同的小值舍入后可能相同。
  5. SmoothQuant 在量化前做等价的通道缩放；AWQ 用激活信息选择保护尺度。不能说剩余 99% 没用。
  6. PTQ 在训练后应用量化，QAT 用训练适应量化效应；校准帮助定方案，独立评测验证是否可用。
  7. 位宽不等于完整格式；还要看算子、模型、版本、任务、质量与实际负载。
  8. 加载成功和文本通顺不证明任务能力没变；实现故障也可能报错。
  9. 固定评测口径，检查独立样本、关键分组与不确定性，不采用通用“200 条就够”门槛。
  10. 权重依赖参数与格式；KV 依赖层数、KV 头数、缓存长度和活动请求等。本例忽略其他占用的上限是 61/142，不是部署承诺。
