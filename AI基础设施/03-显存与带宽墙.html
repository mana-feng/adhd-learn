03 · 显存与带宽墙

⏱ 主线约 30 分钟（不含折叠选读） ｜ ⭐ 理解这一章，后面十几章都会变简单

🎯 一句话

有些 GPU 工作负载受数据搬运限制，有些受计算、启动或同步限制。 这一章讲清楚数据存在哪、搬一次要多久， 之后 FlashAttention、量化、KV Cache、算子融合 —— 全都会变成"当然应该这么做"。

🏔️ 一、内存层次：一张必须记住的表

层级 容量 / 到哪 速度 带宽
寄存器 ~256 KB/SM 极快 （几乎免费）
Shared Memory / L1 ~228 KB/SM 很快 ~10 TB/s
L2 Cache ~50 MB 快 ~5 TB/s
HBM 显存 80 GB ⚠️ 慢 ~2–3 TB/s
—— 以下出卡了 ——
NVLink 到另一张卡 很慢 ~900 GB/s
PCIe 到 CPU 内存 非常慢 ~64 GB/s
网络 到另一台机器 极慢 ~50 GB/s

⬇︎ 这张表和上图是跨设备、跨层级的量级地图；片上聚合、单向与双向带宽不能直接相除，当作应用实测速度。

容量和带宽分两笔账：更多存储位回答“能装多少”；更多独立数据位或更高每引脚数据率，才提高接口的标称搬运上限。

只把每颗密度翻倍：在全容量可用、仍为 256 bit 与 16 Gbit/s 的假设下，总容量变成 16 GiB，标称带宽仍为 512 GB/s。

再深入一点：为什么不再乘 DDR 或通道数？

这里的 16 Gbit/s 已是每数据引脚的数据率，不能再因“双倍数据率”乘 2。若 x32 内部分成两个 x16 通道，32 已包含 16 + 16，再乘 2 会重复计算。同一组数据线被多颗器件轮流使用，也不能把容量数量直接当独立位宽。HBM 的宽接口同样要按确切封装与控制器连接核算，不能照搬本例颗数。

512 GB/s 是接口标称上限，尚未扣除刷新、方向切换、排队等影响；程序的有效带宽还取决于访问、缓存和计时边界。它不是这次测得的 GPU 吞吐。

🔑 用层级判断优化方向：片上复用有机会减少 HBM 流量；减少 .cpu() 往返有机会节省设备与主机之间的传输；并行策略需要检查真实互联路径。上图表的比值只提醒量级差异，不能据此承诺 FlashAttention、拷贝或通信的加速比。

⚖️ 二、算术强度：判断计算与搬运上限的起点

$$\text{算术强度} = \frac{\text{计算量（FLOP）}}{\text{数据搬运量（字节）}}$$

💡 人话：每从显存搬一个字节，能顺带做多少次运算。

先对齐同一任务、同一层级、同一执行路径。下面的 Q 和 F 必须属于同一个 kernel；若 Q 数的是 HBM 流量，B 就用 HBM 带宽，P 则匹配该 kernel 的运算精度与指令路径。

156 只是一个有条件的标定例：A100 80GB SXM 的稠密 BF16/FP16 Tensor Core 矩阵峰值为 312 TFLOP/s，HBM 标称 2,039 GB/s；课堂将带宽取整为 2.0 TB/s，得 312 ÷ 2.0 ≈ 156 FLOP/B。这条屋顶不能直接用于普通逐元素加法。参见 NVIDIA A100 规格表，第 1 页；稀疏峰值另列。

📊 常见操作的算术强度（先作排查线索）

下表是特定形状、精度与理想读写下的粗估，不是一张通用实测排名；融合、分块和缓存会改变 Q，启动与并行度也可能先限制性能。

操作 算术强度 瓶颈
大矩阵乘（4096³） ~1365 有足够复用时可能接近计算上限
卷积（大通道数） 几百 可能受计算限制，需核形状与实现
矩阵乘（batch=1，即向量×矩阵） ~1（BF16、权重主导） 权重完整流经 HBM 时常受带宽限制
逐元素操作（ReLU、加法） 低；FP16 加法为 1/6 大工作集常受带宽限制；小任务还可能受启动限制
LayerNorm / Softmax ~1 可能受带宽限制，须结合实现与流量层级
Attention（长序列，朴素实现） 低 可能受带宽限制，须结合实现与流量层级
📐 3 分钟手算：FP16 加法的时间下界（想看再点）

c = a + b，每个元素 FP16（2 字节），每元素一次加法记 1 FLOP。假设 n = 1,000,000，无复用，两个输入从 HBM 读、一个输出写回 HBM，忽略额外事务：

  • F = n = 1 MFLOP；Q = 6n = 6 MB（2 + 2 + 2 byte）。
  • I = F/Q = 1/6 ≈ 0.17 FLOP/B。若缓存或事务改变实际 HBM 字节数，就要重算 Q。

另设纯教学参数：此层级 B = 100 GB/s，此加法路径 P = 1 TFLOP/s。Q/B = 60 μs，F/P = 1 μs，所以理想下界是 max(60, 1) = 60 μs，性能上界约 16.7 GFLOP/s。没有实测运行时间，也不能把这两个假设速率当作 A100 参数。

普通加法通常不走矩阵 Tensor Core 指令，不能拿 312 TFLOP/s 相除，推断“99.9% 的硬件单元闲置”。低算术强度说明搬运上限可能更紧，实际瓶颈仍要测。

算子融合的一个动机是让中间值留在寄存器或片上、少往返 HBM；它也可能减少 kernel 启动。能否减少流量取决于数据依赖、复用与输出是否必须落存储；寄存器压力、并行度和数值语义也可能限制收益，不能保证 N 个操作只搬一次或快 N 倍。

再深入一点：命中 80%，片外流量就剩 20% 吗？

不一定。自定模型有 100 次、每次 32 byte 的读需求，80 次由缓存满足，其余 20 次各触发独立的 128 byte 下层读，无合并、预取或写回。应用需求是 3,200 byte，片外读是 20 × 128 = 2,560 byte，不是 20% × 3,200 = 640 byte。

32/128 byte 是教学参数，不是 GPU 通用事务大小。真实 Q 要按测量层级、事务、对齐及热/冷缓存条件核对；缓存有效带宽也不能与 HBM 引脚带宽相加。

🔑 注意表里第三行：batch=1 的矩阵乘算术强度约 1 FLOP/字节（BF16）。 这就是第 15 章的核心 —— 自回归解码每次只生成 1 个 token，就是 batch=1 的矩阵乘， 小批量 decode 常受带宽限制；prefill 与大批量 decode 要另算。

💾 三、训练显存到底花在哪

四大块（以 7B 模型、BF16 混合精度、Adam 为例）：

项目 计算方式 7B 模型
模型参数 P × 2 字节（BF16） 14 GB
梯度 P × 2 字节 14 GB
优化器状态 ⭐ P × 12 字节 84 GB
激活值 取决于 batch/序列 几 GB ~ 几十 GB
📐 优化器状态为什么是 12 字节/参数（想看再点）

本例采用的 BF16 混合精度存储方案（第 6 章）需要维护：

内容 精度 字节/参数
FP32 主权重副本 FP32 4
Adam 一阶动量 m FP32 4
Adam 二阶动量 v FP32 4
合计 12 ⭐

加上 BF16 的参数（2）和梯度（2），总共 16 字节/参数。

💡 一个好记的经验公式： $$\text{训练显存(GB)} \approx 16 \times \text{参数量(B)} + \text{激活}$$

  • 7B → 112 GB（一张 80G 卡装不下）
  • 70B → 1120 GB（静态状态至少按 14 张 80G 卡的总容量核算，还没算激活）

⚠️ 用 SGD 而不是 Adam 的话会小很多（没有 m、v），但大模型基本都用 Adam。

激活值：主要随 batch 变化的持久部分

算一算

Transformer 每层每个 token 的激活 ≈ 十几到几十倍的 hidden_size

总激活 ≈ batch × 序列长度 × hidden × 层数 × 常数

⭐ 关键性质：它和 batch【成正比】

→ 减小 batch 主要影响激活，也可能影响临时工作区与通信缓冲

→ 其他三块和 batch 完全无关 ⭐

🔑 这解释了第 1 章那个错误直觉： "OOM 就调小 batch"只对激活有用。 如果你的 OOM 是因为优化器状态装不下，调 batch 到 1 也没用 —— 那时候需要的是 ZeRO 或量化。

🧮 四、动手：估算你的模型要多少显存

def estimate_training_memory(params_B, batch, seq_len, hidden, layers,
                             optimizer="adam", grad_ckpt=False):
    """返回 GB。粗估，用于判断量级和选并行策略。"""
    P = params_B * 1e9
    weights = P * 2 / 1e9                       # BF16 参数
    grads   = P * 2 / 1e9                       # BF16 梯度
    opt     = P * (12 if optimizer == "adam" else 4) / 1e9

    # 激活：不开检查点约 ~34 倍 hidden/层/token（Megatron 的经验系数）
    per_layer = batch * seq_len * hidden * 34 * 2 / 1e9
    acts = per_layer * (layers ** 0.5 if grad_ckpt else layers)
    #                    ↑ 检查点后约降到 √层数 量级

    total = weights + grads + opt + acts
    print(f"参数 {weights:6.1f} GB | 梯度 {grads:6.1f} GB | "
          f"优化器 {opt:6.1f} GB | 激活 {acts:6.1f} GB")
    print(f"合计 ≈ {total:.1f} GB")
    return total

# 7B，batch=4，seq=2048
estimate_training_memory(7, 4, 2048, 4096, 32)
# 参数   14.0 GB | 梯度   14.0 GB | 优化器   84.0 GB | 激活   73.0 GB
# 合计 ≈ 185.0 GB；本例公式给出激活约 73.0 GB，尚未含工作区

⚠️ 这是粗估，实际还要加：显存碎片（5–10%）、 通信缓冲区、CUDA context（几百 MB）、临时工作区。 留 15% 余量是常见做法。

🚧 五、"带宽墙"这个词的含义

关键信息

固定同一任务、精度、执行路径与流量层级
若 P 的增长快于 B → 参考拐点 P/B 升高
若任务的 I 不变 → 带宽上界可能变成更紧的约束
不能把不同年代的 FP32 与 Tensor Core 峰值直接比较，推出每种任务都更受带宽限制
这类计算能力与搬运能力不匹配，就是这里讨论的“带宽墙”

🔑 一个重要的推论： 在同一任务的计算峰值增长快于带宽时，减少远距离搬运会更值得关注。 这并不保证下一代硬件上每个操作都从 compute-bound 变成 memory-bound；要用新的 P、B 和实际 Q 再算一次。

💡 这也解释了为什么 FP8、KV Cache 量化、算子融合这些技术 越来越受重视 —— 它们都是在直接对抗带宽墙。

✅ 检查点

  1. 密度翻倍但独立位宽、数据率不变，容量和标称带宽分别怎么变？
  2. 算术强度怎么定义？156 FLOP/B 这个参考拐点有哪些条件？
  3. FP16 加法的 Q、F 与算术强度是多少？怎样求时间下界，融合可能改变哪笔账？
  4. batch=1 的矩阵乘算术强度是多少？这对推理意味着什么？
  5. 训练显存的四大块是什么？7B 模型各占多少？
  6. 优化器状态为什么是 12 字节/参数？训练显存的经验公式是什么？
  7. 四大块里哪一块和 batch 有关？这修正了什么错误直觉？
  8. 什么是“带宽墙”？在什么条件下，硬件迭代会让带宽约束更突出？
👀 答案
  1. 在全容量可用的假设下，容量翻倍；独立位宽与每引脚数据率没变，标称带宽不变。8 颗从每颗 1 GiB 变成 2 GiB 时，总量由 8 变为 16 GiB，仍为 512 GB/s。
  2. I = F/Q，Q 要注明存储层级；B 与 Q 同层，P 与 F 的精度和执行路径匹配。156 是 A100 稠密 BF16/FP16 Tensor Core 矩阵峰值 312 TFLOP/s ÷ 取整 HBM 带宽 2.0 TB/s 的课堂参考，不适用于所有 kernel。
  3. 理想读写下 Q = 6n byte、F = n FLOP，I = 1/6 ≈ 0.17 FLOP/B；t ≥ max(Q/B, F/P)。本例 n=100 万、B=100 GB/s、加法路径 P=1 TFLOP/s，得 60 μs 理想下界，不能当实测。融合有机会减少中间值流量与启动，收益受依赖、资源和数值条件约束，不能据 Tensor Core 峰值算普通加法的单元闲置率。
  4. 约 1 FLOP/字节（BF16、忽略其他读写），可能受带宽限制。小批量稠密 decode 在权重完整流经 HBM 时常受带宽限制；批量、缓存、KV 与实现改变后须重新核算。
  5. 参数（14GB）、梯度（14GB）、优化器状态（84GB，最大）、激活（几 GB~几十 GB）。
  6. FP32 主权重副本 4 + Adam 的 m 4 + v 4 = 12。加上 BF16 参数 2 和梯度 2 共 16。经验公式：训练显存(GB) ≈ 16 × 参数量(B) + 激活。
  7. 激活主要随 batch 增长，临时工作区也可能变化，其他三块完全无关。修正了"OOM 就调小 batch"——如果 OOM 来自优化器状态，batch 调到 1 也没用，那时需要 ZeRO 或量化。
  8. 在同任务、精度、执行路径与流量层级下，若 P 增长快于 B，P/B 升高，I 不变的任务可能更受带宽限制。不能混用 FP32 与 Tensor Core 峰值推出普遍代际结论；复用、缓存和实现变化后仍须重算。

⚡ 走神救援

先记住这几件事

  • 计算前先问数据在哪：不同存储和互联的容量、带宽差别很大。
  • 容量与带宽分账；算术强度 F/Q 要对齐流量层级与计算路径，再用 max(Q/B, F/P) 算理想时间下界。
  • 显存分别核算参数、梯度、优化器状态和激活；减小 batch 不能解决所有 OOM。
