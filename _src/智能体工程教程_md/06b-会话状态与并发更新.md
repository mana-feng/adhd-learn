# 06b｜会话状态与并发更新：两条消息同时到达怎么办？

> 本章保留教学代码、路径说明与历史验证结论；完整实验工程和运行记录未随本站及公开仓库分发。命令用于说明调用方式，复现需自行准备对应实现、数据与环境。

**一句话：把身份、版本和操作编号放进同一笔事务，历史才能既接得上，也不被重复写入或旧请求覆盖。**

上一节 [工作流还是 Agent](06-工作流还是Agent.html) 讨论谁决定下一步。这里先处理更基础的问题：两条消息同时到达，或者服务写成功后响应丢了，下一次该从哪条历史继续？

**停止点：**读完第三节，能在版本表里解释“一个成功，一个冲突”，就可以停。跑完整个实验后，再确认重放没有新增轮次或续期。

**走神救援：**回来时找三个词：身份、版本、重放。身份决定历史归谁；版本决定更新能否提交；重放决定同一次操作是否已经提交。

## 1. 会话记住上下文，权限仍来自当前请求

用户先问“XR-200 的额定功率”，随后问“它呢”，服务需要少量历史解释代词。历史里出现设备编号，并不意味着用户获准读取该设备的所有资料。当前检索仍要经过 core.retrieve 的权限检查。

SessionStore 接收服务端提供的 core.Identity。这是一个信任接口，调用者必须先完成认证；实验没有登录、真实身份提供商或 token 校验入口。文字、模型输出和上传文档都不能给自己构造可信身份。

会话的键是 tenant、subject、session_id 三项。相同会话编号可以属于不同用户，但每条读写都使用完整的三项定位。换成另一个用户或租户时，看不到原会话；错误只返回 session_not_found，原用户的文字不会进入演示报告。

身份字段与会话编号限定为一到八十个 ASCII 字母、数字、连字符、下划线或点。所有操作都需要 knowledge:read。会话库不保存 scopes，也不保存或发放业务批准；当前 Identity 缺少读取权限时，旧历史不能替它补回来。

<details>
<summary>检查点 1｜用户在文字中写 tenant=admin，会换身份吗？</summary>

不会。append_user_turn 只接收用户文字，没有租户、角色或来源补丁参数。身份由服务端独立传入。role=system、approve 等字符串仍作为 user 文字保留，不能转换成系统消息或批准记录。

</details>

## 2. 版本表示“我基于哪次读取提出更新”

新会话从 version=1 开始。每次成功 append、reset 或 close 都加一，读取不加。调用者提交 expected_version，表示自己基于哪个版本提出修改。数据库中的当前版本必须相同，才允许新增操作。

这种比较并交换简称 CAS，防止旧视图覆盖已提交结果。版本须为正整数，拒绝 True、浮点数及超出 SQLite 范围的值。

设两个请求都读到版本一。第一个添加了一个用户轮次，提交后版本变为二。第二个仍携带 expected_version=1，得到 version_conflict。服务可以重新读取、让调用者理解新上下文，再决定是否提交一个新操作；实验不会自动用新版本替旧请求重试。

## 3. 事务让检查和写入成为一件事

只在 Python 中先读取版本、过几行再写入，并不能阻止两个进程同时通过检查。BEGIN IMMEDIATE 把写事务的开始放在检查之前；拿到写入位置后，再检查状态、版本、轮次数与回执数，最后写入并提交。

并发测试用 barrier 同步两只真实连接，争取同一个版本，不靠 sleep。检查一成功一冲突、最终版本与轮次数。

读取也开启事务。版本、状态与轮次属于同一快照，避免得到“新版本配旧轮次”的拼接。额外测试用 event 暂停读者，在它的两条查询之间让另一连接提交；读者仍得到旧版的一致视图，下一次读取才见到新版本。

<details>
<summary>检查点 3｜加了事务，两个请求都会成功吗？</summary>

不会。事务保证检查和修改一致，并不取消 CAS 的拒绝条件。后进入的请求会看到已提交的新版本，再发现自己的 expected_version 过时，明确返回 version_conflict。

</details>

## 4. 重放返回原回执，不重复写，也不伪装当前状态

客户端可能遇到“请求超时，但数据库已提交”。operation_id 用来识别同一次操作。回执记录保存操作编号、动作与文字及旧版本的摘要、成功后的版本；不保存旧文字的第二份副本。

完全相同的 action、text、expected_version 再次到达，返回 replayed=true 的原回执，不再加轮次、不增版本、不延长 TTL。同编号改了任意负载，返回 idempotency_conflict；不能把 append 的编号拿来 reset 或 close。

第一次操作的回执可能是 version=2，而当前会话已到 version=3。重放证明原操作成功；当前快照另调用 read。

查回执之前，先检查会话是否过期或关闭。终态不能被“这是重放”绕过。close 的响应即使丢失，再次 close 也会得到 session_closed；调用者可以读取空墓碑核对关闭状态。

<details>
<summary>检查点 4｜收到旧回执，可以用它继续当最新版本吗？</summary>

不能。回执有自己提交时的版本，当前快照要单独读取。演示 old-receipt-not-snapshot 同时报告 receipt_version=2、current_version=3，让这两个事实可见。

</details>

## 5. TTL、重置和关闭分别解决不同问题

TTL 是一到八万六千四百秒的有限数值，默认三十分钟。布尔值、NaN、无穷大和巨大整数都拒绝。clock 必须返回有限非负时间，低于会话上次成功更新的时间时返回 clock_rollback。

成功 append 或 reset 才刷新 expires_at。读取与重放都不续期；now 等于到期时间就已过期。演示把可控时钟推进到精确边界，观察 session_expired，而非等待真实时间碰运气。确认到期后提交独立过期标记，再返回拒绝。重开并回拨到到期之前，read、history、重放与新修改仍拒绝，旧完整键不能重新 create。

reset 删除保留的用户轮次，版本仍继续增加，已有操作摘要继续保留。版本不能回到一，否则旧请求可能再次通过，形成 ABA 问题。

close 同样删除原文，保留 closed 墓碑与单调版本。读取墓碑只得到空 turns；追加、重置和所有重放都拒绝。关闭不会执行 workflow；审批见 [持久化审批与故障恢复](12b-持久化审批与故障恢复.html)。

SQLite secure_delete 不证明旧备份或系统副本已擦除。没有请求观察过期时，时间判断仍依赖传入 clock；实验不能证明真实时间永不回拨。

<details>
<summary>检查点 5｜reset 之后，旧请求为什么仍然不能成功？</summary>

版本没有回到初始值；新操作携带旧版本会冲突。若编号与负载完全等同于已提交操作，则只返回原回执，不恢复已删轮次、不重新续期。终态检查仍在回执检查之前。

</details>

## 6. 少量可信历史如何接上当前检索

history 把本身份的最近三条用户轮次转换为 query_lab.TrustedUserTurn。它不输出系统指令，不把助手回答当用户输入，也不从模型或文档文字推断身份与来源。

本章用临时原创资料，实际调用 [查询改写与多轮检索实验](11f-查询改写与多轮检索实验.html) 中的 resolve_history。只有一个明确设备编号、并且历史处于该解析器的三十分钟窗口时，“它”才补上 XR-200。会话 TTL 不改变解析器时间窗口。

历史若比较过 XR-200 与 XR-300，代词可能指向任一设备，返回 clarification_required。最近提到哪台，并不能证明用户现在指哪台；实验保留澄清，不擅自挑设备。

demo 调用真实 core.retrieve，报告是否找到 XR-200 与证据数量。另一用户得到零条可见证据；报告不保存正文或会话全文。

<details>
<summary>检查点 6｜代词解析成功，可以跳过检索权限吗？</summary>

不能。解析只增加一个设备标识，当前检索仍以当前 Identity 查询可见知识。历史中的旧权限没有保存在会话里，旧轮次也不能授权新请求。

</details>

## 7. 容量、独立数据库与固定错误

每个会话最多保留二十轮用户文字，每轮非空且最多两千字符。超过轮次数返回 turn_limit；已有轮次和版本不变。reset 可以释放轮次容量，但成功操作的回执仍保留。

每个会话最多一百条成功修改回执。读取与去重不计数，失败不消耗配额；第一百零一次新修改返回 receipt_limit。达到限额后，调用者显式创建新会话编号，程序不会悄悄替它换号或删回执绕过限制。

会话库独立于知识库。初始化检查 application_id、schema version 和表结构：空白数据库才创建表，已有无关数据库拒绝，不把个人文件或知识库“迁移”成会话库。标识只防误用，真正的目录访问控制仍由服务端承担。

参数先校验再访问数据库。路径、SQL 与 I/O 异常用 storage_error 等固定类别公开，不把底层异常全文或数据库路径返回给用户。读取同时限制轮次数与文字字节，防止意外读取无限历史。

<details>
<summary>检查点 7｜二十轮限制和一百条回执限制是同一个数吗？</summary>

不是。reset 后轮次可为零，但历史成功操作仍有回执。一百次 reset 一样会达到回执上限；相同操作重放仍可以去重，新的修改拒绝。

</details>

## 8. 运行一次，核对三项证据

原示例学习环境中的命令为：

```powershell
examples/knowledge-assistant/.venv/Scripts/python.exe -X utf8 examples/knowledge-assistant/session_lab.py
```

同一命令在示例目录内可简写为：

```powershell
python -X utf8 session_lab.py
python -X utf8 -m unittest -v test_session_lab
```

默认输出在脚本旁的 .runtime/session-UTC时间目录。指定 --output 时必须提供不存在的新目录，父目录需已存在。已有目录返回 exit=2 与 output_exists；父路径失败返回 output_error，不覆盖上次报告，不输出 traceback。

本轮复审修复后，限定测试二十九项通过，真实 demo 三十五个场景符合预期。summary.json 保存每项 id、expected、actual、passed，以及 Python、SQLite、代码与旧语料摘要。临时数据库已删除。结果只支持本地一致性，不证明生产吞吐、云同步、真实模型或身份认证。

先看 two-real-connections-cas：一成功、一冲突，版本二、轮次一。再看 replay-no-write-no-refresh：重放仍是版本二、轮次一、原到期时间。最后看 ambiguous-models：保留 clarification_required。
