22 · 数据管线与存储

⏱ 24 分钟 ｜ 🎁 最容易被忽略的瓶颈

🎯 一句话

你花了几个月优化模型和并行策略，结果 GPU 有 30% 的时间在等数据。 第 4 章那个"把 dataloader 换成随机张量"的实验之所以排第一位， 就是因为这个问题极其常见，而且极其容易被误诊成"模型慢"。

🔧 二、DataLoader 的六个参数

# 🧩 骨架：`DataLoader` 来自你自己的代码，这一段只看写法
loader = DataLoader(
    dataset,
    batch_size=32,
    num_workers=8,          # ⭐ 通常设为 CPU 核数 / GPU 数
    pin_memory=True,        # ⭐ 锁页内存，让 H2D 拷贝能异步
    prefetch_factor=4,      # 每个 worker 预取几个 batch
    persistent_workers=True,# ⭐ 别每个 epoch 重建 worker（重建很贵）
    drop_last=True,         # 避免最后一个不完整 batch（分布式下尤其重要）
)
参数 常见错误
num_workers=0 主进程加载 → 必然阻塞 ⭐
num_workers 太大 内存爆、CPU 争抢，反而更慢
pin_memory=False H2D 拷贝无法异步重叠
persistent_workers=False 每个 epoch 重建 worker，小数据集上开销巨大 ⭐

⭐ 让 H2D 拷贝也重叠起来

# 🧩 骨架：`batch` 来自你自己的代码，这一段只看写法
# ❌ 同步拷贝，GPU 干等
import torch
batch = batch.cuda()

# ✅ 异步 + 预取下一个 batch
batch = batch.cuda(non_blocking=True)      # ⭐ 需要 pin_memory=True

# ⭐ 更进一步：手动双缓冲预取
class Prefetcher:
    def __init__(self, loader):
        self.it, self.stream = iter(loader), torch.cuda.Stream()
        self._preload()
    def _preload(self):
        try: self.next = next(self.it)
        except StopIteration: self.next = None; return
        with torch.cuda.stream(self.stream):
            self.next = {k: v.cuda(non_blocking=True) for k, v in self.next.items()}
    def __next__(self):
        torch.cuda.current_stream().wait_stream(self.stream)
        batch = self.next
        if batch is None: raise StopIteration
        self._preload()                     # ⭐ 立刻开始加载下一个
        return batch

📦 三、存储格式：小文件是灾难

先分清在等什么：训练读文件既有查路径/元数据的成本，也有搬数据、解码和转成张量的成本。打包可减少重复小文件操作，memmap 可按需访问大数组；它们都不能让存储访问变成零开销。先按这个顺序定位，再选格式即可。

深入：从文件路径走到 token 切片（可跳过）
  1. 文件系统做什么：用目录/文件名组织数据，记录大小、权限等元数据，管理文件内容的存放与访问，并按相应语义处理持久化。Linux VFS 把路径查找及文件操作接到具体文件系统；路径/元数据命中缓存与否会改变成本，不是每次切片都要重新打开文件。
  2. mmap 做什么：把文件的一段关联到进程虚拟地址范围，之后用普通内存访问读取。在 Linux 常规文件映射中，首次访问可能建立页映射或触发缺页取数；数据已在页缓存中时可不必再读设备。映射整个大文件不等于立刻把它全部读进 RAM，也不保证随机访问快。
  3. 切片手算：假设原始 token 文件从字节 0 开始，每个元素是写入/读取端一致的 uint16、字节序也一致。tokens[100:104] 对应 4 个元素、8 字节，字节范围为 200–207。只有相关内容可用后才能读出值；这个下标例不能证明没有 I/O。
  4. 使用边界：原代码 mode="r" 只读已有文件；dtype、字节序、offset 和形状须与生成端一致。uint16 只能表示 0–65535，较大 token ID 要换匹配格式。映射期间避免其他进程截断/替换正在使用的数据；越过文件末尾等访问可失败，Linux 某些情况会触发 SIGBUS。
  5. 写模式不能混用：NumPy 的 r+ 可写已有文件，w+ 会创建/覆盖，c 的更改不保存到文件。flush 不是多写者同步协议，也不能单凭调用它就声称已满足断电持久化要求；本章训练读取优先使用版本固定的只读数据。

小文件优化先测形状：固定样本/字节数、worker 数、存储和训练配置，对比小文件随机读与分片顺序读；分别记录路径/打开耗时、读取尾延迟、解码时间、供给吞吐和训练等待。冷缓存与暖缓存分开标注，不能拿缓存命中对比设备冷读。

若元数据耗时突出，可打包/复用已打开文件；若读取请求太碎，可增大顺序块和合理预取；若解码占满 CPU，先处理解码。worker/预取并发要逐步调整，过高也可能争抢存储、网络和内存。这些是定位候选，没有固定最优 worker 数或保证提速。

依据：Linux VFS、页缓存与内存概念、Linux mmap 的映射/错误边界、NumPy memmap 模式与布局。以上仅机制说明和下标手算，未运行存储或规模训练实验。

读得快，还要看分片怎样生成：读、查元数据和写入可能卡在不同环节。预读、复用打开的文件、合批写与增加并发都有代价；写侧比较还要保持相同的持久化承诺。生成训练分片时可选读下面的对照，主线也可继续看原有格式。

深入：文件性能的读、元数据与写取舍（可跳过）
  1. 读侧：顺序消费分片时，合并零碎读、合理预读可减少等待。随机跳读或只用少量内容时，过度预读会多读无用数据、挤占缓存/带宽；不应只把预读窗口调大。
  2. 元数据侧：反复 path/open/stat 或海量小文件成为瓶颈时，可打包、复用已打开文件。句柄/元数据缓存占资源，打包也可能增加随机定位、解包成本；目录命名操作、空间分配/extent 布局须按具体 FS/设备验证，不在此展开实现算法。
  3. 写侧：预处理生成分片时，缓冲和合批可摊薄调用/小写开销；批次更大也会增加等待、占用内存，并可能扩大尚未确认持久化的数据窗口。可重算的临时数据与已承诺可恢复的产物，应采用各自的完成标准。
  4. 并发与队列：适度并发能重叠 I/O；超过 CPU、内存、句柄、设备或网络服务能力后，排队与 p95 可能变差。逐步设并发/队列上限并测量，不能把 worker 越多或队列越深当通用优化。

写快返回，可能只到了缓冲：Linux 缓冲写会产生脏页，由后台回写；脏数据积压时，写进程也可能参与回写或等待。因此只看短时 write 吞吐，会把延后支付的 I/O 成本藏起来；未经约定同步确认的数据还存在崩溃窗口。

先定 durability，再定 sync 频率：每条、每批或每个分片同步，会改变延迟及可丢失窗口；不能把关闭 fsync/flush 当无代价提速。Linux fsync(fd) 同步文件数据/元数据并等待设备报告完成，须检查错误；新建/重命名后的目录项持久化还要核对目录同步。它不自动提供多文件事务或所有故障模型下的保证。

映射写也要分清调用：文件 MAP_SHARED 的更改可回写，MAP_PRIVATE 的私有修改不写回原文件；msync(MS_SYNC) 请求映射范围回写并等待，不是多写者同步协议。库的 flush、文件同步与目录同步不能只凭名字互换；原来的只读 memmap 路径保持不变。

对比计划，尚未执行：

  1. 固定样本与有效字节数、内核/FS/挂载和设备条件，格式额外字节另记；冷/暖缓存分组。每次只改访问形状、打包、批次或并发之一，标明统计区间。
  2. 记录元数据操作数/秒，path/open、读、写及 sync 各自的 p95、有效吞吐、CPU 与 I/O 等待、队列和内存。写侧计时须包含约定同步与待完成工作，区分提交速率和已确认持久化速率。
  3. 先写明同步策略、可接受丢失窗口、错误处理与确认规则，再在隔离副本验证同步失败/进程崩溃后的样本数、校验和及目录可见性。进程崩溃不等于断电测试；两者不能互相代签，也不在真实训练数据上试故障。

自测：B 批 write 已返回但约定的 sync 尚未成功，可以仅凭它返回快就把 B 计为已承诺持久化吗？不可以，性能比较与故障检查都须沿同一完成标准。

依据版本：Linux 6.12 文档集的 VFS 路径查找与回写、readahead、脏页/后台回写边界；Linux man-pages 6.19 的 fsync、mmap、msync。以上为机制与验证计划，未运行本机文件系统、故障或训练实验。

关键信息

  • ❌ 一百万个小文件（每个 4KB）
  • → 每次读都是一次文件系统操作
  • → 小文件/冷缓存场景中，路径与元数据操作可能比传输内容更耗时，须分开测
  • ✅ 打包成大文件：
  • WebDataset（tar 包） ⭐ 流式、支持分片、云存储友好
  • Parquet / Arrow ⭐ 列式，适合表格和文本
  • TFRecord / MDS 顺序读友好
  • 内存映射（np.memmap） ⭐ 预处理好的 token 序列首选

⭐ 对 LLM 预训练：一种可选做法是提前 tokenize 成匹配 dtype 的数组，用 np.memmap 按需读。 这可减少训练时重复解析；首次访存、缺页、随机 I/O、类型转换和搬运仍有成本。

⭐ 三个必须处理对的问题：
① 【不重不漏】：每个 rank 拿到不同的数据
DistributedSampler（第 10 章）
② 【每轮重新洗牌】：sampler.set_epoch(epoch)
漏了等于没 shuffle ⭐

drop_last=True，或补齐
否则某个 rank 提前结束→AllReduce 挂死（第 21 章）💀

⭐ 流式数据集的洗牌难题

流程图

问题：数据太大无法全部载入，只能流式读
但流式读的顺序是固定的→没有随机性
✅ 解法：【缓冲区洗牌】（shuffle buffer）
维护一个 N 条样本的缓冲区，每次随机取一条，再补一条进来
⚠️ 缓冲区太小→随机性不够（相邻样本仍然相关）
⭐ 经验：缓冲区 ≥ 10000 条，或者【先在文件层面 shuffle 分片顺序】

✂️ 五、序列打包：一个常被忽略的大优化

信息关系

⚠️ 变长文本 + padding 的浪费：
样本长度: [120, 2048, 340, 89, 1500]
padding 到 2048→有效 token 只占 40%
【60% 的算力在算 padding】💀

因果链

✅ 序列打包（packing）：
把多条短样本【拼成】一条满长度的序列
[样本A][样本B][样本C][样本D] ← 拼满 2048
↑ 用分块 attention mask 或匹配变长内核隔离样本；仅重置 position_ids 不能阻止跨样本注意 ⭐
有效 token 占比从 40% 提到 95%+
等于【训练速度翻倍】⭐

⚠️ 打包必须正确隔离： 如果不隔离，样本 B 会 attend 到样本 A 的内容 —— 模型会学到错误的关联。 FlashAttention 支持 cu_seqlens（变长序列）， 这是正确且高效的做法（第 8 章提过：别用 padding mask）。

💽 六、存储层次

延迟和带宽回答不同问题：DRAM 访问走内存控制器；HDD 冷随机读还受机械寻道/旋转影响，SSD 去掉机械运动但仍有介质、控制器与接口开销，应用文件 I/O 又有队列、文件系统和可能的网络等待。因此大文件的 GB/s 不能直接代表一次小随机读要等多久。下面速率仅作背景示意，不是本机测量或设备排名。

深入：把数量级与训练等待分开算（可跳过）

只做单位换算：假设两次可比读取的延迟分别为 100 ns 与 100 μs，则后者为 100000 ns，是前者的 1000 倍，即 3 个数量级。这是设定值的算术，不是所有 DRAM/SSD 的规格；缓存命中、块大小、队列深度、读写方式和设备都会改变观测。

延迟可重叠，成本仍存在：顺序批量读与并发预取能摊薄每次请求开销；若平均供给不足以覆盖训练消耗，再多缓冲也只能暂时延后等待。只有预取及时完成且资源/缓冲充足，才可能把这部分等待隐藏在计算后面，还需看尾延迟和实际 GPU 等待。

分片还要写出来：上面的 读／元数据／写对照 补充预处理生成分片的代价；仅比较读吞吐，不能代表已确认持久化的生成速率。

来源示例：Seagate 的 HDD 随机/顺序访问模型、Intel 对介质与软件栈延迟的历史示例。它们用于解释机制，不能作为当前机型通用时延表。本页没有测设备、网络或训练速度。

信息关系

本地 NVMe：吞吐示意 ~5 GB/s，非通用最快排名
本地 SSD ~1 GB/s
网络存储(NFS) ~1-10 GB/s 取决于网络和并发
对象存储(S3) ~几百 MB/s 但可以【高并发】
⭐ 常见架构：
S3（全量数据）→预取到本地 NVMe（当前 epoch 用的分片）→训练

💡 一个实用技巧：训练前先把下一个 epoch 的数据分片预取到本地盘。 后台预取可尝试与训练重叠；只有按时完成且带宽/缓冲充足，才能隐藏相应等待，不能保证完全重叠。

👀 答案
  1. ①把 dataloader 换成固定随机张量看 MFU 是否上升 ②只跑 dataloader 不训练测吞吐。判据：数据管线吞吐必须 ≥ 训练吞吐的 1.2 倍。
  2. GPU 时间轴上有规律的空隙，且空隙出现在每个 step 的开头。
  3. num_workers=0（主进程加载必然阻塞）、num_workers 太大（内存爆+CPU 争抢）、pin_memory=False（H2D 无法异步）、persistent_workers=False（每个 epoch 重建 worker）。
  4. non_blocking=True 需要 pin_memory=True 才生效——只有锁页内存才能做异步 DMA 拷贝。
  5. 因为大量 worker 同时读取小文件可能使元数据服务成为瓶颈，其他节点也可能受影响；要比较元数据、内容传输和解码耗时，不能仅凭文件数定因。
  6. 提前 tokenize 成一个巨大的 uint16/uint32 数组，用 np.memmap 读。这可减少重复解析，但仍要测首次访存/缺页、随机 I/O、转换与搬运成本。
  7. ①不重不漏（DistributedSampler）②每轮重新洗牌（set_epoch）③各 rank 步数一致（drop_last=True，否则 AllReduce 挂死）。
  8. 缓冲区洗牌：维护 N 条样本的缓冲区，每次随机取一条再补一条。太小则随机性不够，相邻样本仍然相关。经验：≥10000 条，或先在文件层面 shuffle 分片顺序。
  9. 有效 token 占比从 40% 提到 95%+，等于训练速度翻倍。必须隔离是因为不隔离的话样本 B 会 attend 到样本 A，模型学到错误关联。正确做法是用 FlashAttention 的 cu_seqlens。

⭐ 最容易被忽略的瓶颈，也最容易被误诊成「模型慢」。

⭐⭐ 五分钟确诊两步：把数据加载换成固定的随机张量，看利用率是不是上去了；再单独跑数据管线测吞吐。⭐ 判据：数据管线的吞吐必须明显高于训练吞吐；profiler 上的信号是每个 step 开头都有一段有规律的空隙。

加载器参数里最容易漏的两个：⭐ 异步拷贝只有配上锁页内存才真的生效；⭐ 不开持久化 worker，每个 epoch 都要重建一次。

存储格式：⚠️⭐ 小文件是灾难——大量 worker 同读小文件可能压满元数据服务，需测量确认；✅ 打包成整块。⭐ 可选预处理路线是提前切词，按正确 dtype 存数组后用内存映射读——切片不等于零 I/O；冷/暖缓存、读取形状与转换搬运都影响成本。

分布式三件事：不重不漏、每轮重设种子、⭐ 各个 rank 的步数必须一致——⚠️ 否则同步操作会直接挂死。 流式数据要用足够大的缓冲区洗牌，⚠️ 缓冲区太小的话相邻样本仍然相关。

⭐⭐ 序列打包是最常被忽略的大优化：变长文本补齐到固定长度时，有效 token 可能只占四成——也就是说大半算力在算填充；打包之后接近全满，等于训练速度翻倍。⚠️ 但必须正确隔离边界，否则后一个样本会看到前一个样本的内容，模型学到错误关联。

⭐ 存储层次的实用技巧：后台预取下一轮分片到本地盘；核对供给速率、缓冲和尾延迟，才知道隐藏了多少等待。
