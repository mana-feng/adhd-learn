04 · Roofline 与 MFU

⏱ 主线约 30 分钟（不含折叠选读） ｜ ⭐ 估计性能上限与检查运行口径的工具

🎯 一句话

MFU 与 Roofline 提供两种参考，还需结合时间线、吞吐和质量判断优化。 这一章给你两个工具：Roofline 给出匹配口径下的资源上界，MFU 衡量有效模型运算相对所选峰值的比例。

📈 一、Roofline 模型

横轴是算术强度 I = F/Q（FLOP/byte），纵轴是性能 F/t（FLOP/s）。斜坡给出 I × B 的带宽上界，水平屋顶给出 P 的计算上界，拐点是 P/B。Q 与 B 必须在同一存储层级，F 与 P 必须匹配运算精度和执行路径。上面的原图使用自定参数 8 TFLOP/s 与 2 TB/s，不是 A100 测量。

若用 A100 80GB SXM 稠密 BF16/FP16 Tensor Core 矩阵峰值 312 TFLOP/s、把 2,039 GB/s HBM 标称带宽取整为 2.0 TB/s，参考拐点约 156 FLOP/B；普通逐元素加法不能直接套这条 Tensor Core 屋顶。参见 NVIDIA A100 规格表，第 1 页。先看第 3 章同任务 Q/F/B/P 账本与 FP16 加法手算，再把测得的 F/t 放到匹配的图上。

你的 kernel 落在哪 说明 该优化什么
⭐ 斜坡上 在当前 B、P 与流量口径下接近带宽上界 优化【搬运】
⭐ 平台区但低于上界 可能受计算、调度、通信或实现限制，需结合时间线 检查执行路径、并行度、依赖与时间线；适用的矩阵运算再考虑 Tensor Core
⭐ 越过当前上界 观测与当前模型不一致 复核峰值路径、时钟、FLOP、流量层级及计时范围

$$\text{理想性能上界} = \min(\text{峰值算力},\; \text{算术强度} \times \text{带宽})$$

💡 同一账本的另一面：t ≥ max(Q/B, F/P) 是理想时间下界；把 F 除以它，就得到上面的性能上界。启动、同步和数据依赖可以让观测值更低。缓存降低 HBM 流量时，应更新 HBM 的 Q，不能把逻辑请求字节数配上 HBM 屋顶就宣布超规格。

依据：Nsight Compute §2.9.1–2.9.2区分屋顶边界与被分析 kernel 的观测点，并要求核对 Tensor Core 等执行路径及 L1/L2/DRAM 流量层级。

🔨 三步用起来

流程图

① 算这个 kernel 的 FLOP 和字节数→得到算术强度
② 在图上找到它的位置→知道理论上限是多少
③ 和实测对比：
· 接近理论上限→这个 kernel 接近本模型上界，先核对口径再找其他热点，去优化别的
· 远低于理论上限→先查调度、依赖、并行度与统计范围，不能仅凭差距判 bug ⭐

🔑 Roofline 最大的价值不是"告诉你能快多少"， 而是"告诉你【不能】快多少" —— 若 Q 的计数层级不变、I 仍为 2 FLOP/B、该层 B 为 2 TB/s，则带宽上界为 4 TFLOP/s；改变复用、Q 或执行路径后，需要重画边界。 知道这个，你就不会在错误的地方浪费一周。

📊 二、MFU：最重要的一个指标

$$\text{MFU} = \frac{\text{实际有效算力}}{\text{硬件峰值算力}}$$

怎么算（这是你真正会用到的）：

算一算

① 算出一次前向+反向的 FLOP：

⭐ Transformer 的经验公式：

每个 token 的训练 FLOP ≈ 6 × 参数量

（前向 2N，反向 4N —— 反向要算两组梯度：

对输入的和对权重的，所以是前向的 2 倍）

② 实测吞吐（tokens/秒）

③ MFU = (6 × N × tokens/秒) / (GPU数 × 峰值FLOPS)

def mfu(params_B, tokens_per_sec, n_gpus, peak_tflops=312):
    """Transformer 训练的 MFU。peak_tflops: A100 BF16 = 312"""
    flops_per_token = 6 * params_B * 1e9
    achieved = flops_per_token * tokens_per_sec
    peak = n_gpus * peak_tflops * 1e12
    return achieved / peak

# 例：7B 模型，8 卡 A100，实测 12000 tokens/秒
print(f"MFU = {mfu(7, 12000, 8):.1%}")     # MFU = 20.2%   教学算例；需对照同口径基线判断
📐 为什么是 6N（想看再点）

对一个权重矩阵 $W \in \mathbb{R}^{m\times n}$，处理一个 token：

  • 前向：$y = Wx$ → $2mn$ FLOP（一次乘一次加）
  • 反向对输入的梯度：$\partial x = W^\top \partial y$ → $2mn$
  • 反向对权重的梯度：$\partial W = \partial y\, x^\top$ → $2mn$

合计 $6mn$，而 $mn$ 就是这个矩阵的参数量 → 6 × 参数量 ⭐

⚠️ 这个公式忽略了 attention 的 $O(n^2)$ 部分。 计入该项时，本页近似写作：$\text{每 token} \approx 6N + 12 \cdot L \cdot h \cdot s$ （L=层数，h=hidden，s=序列长度）。 是否需要计入，要看它与 6N 的比值 $2Lhs/N$ 是否超过本次可接受的近似误差；没有统一的 8K 阈值。

📏 MFU 怎么判断（对照同口径基线）

比较前先对齐模型、序列与 batch、精度、硬件与卡数、FLOP 约定及计时范围，并记录实现和检查点策略的差异。下表是排查思路，不是实测基准或通用成绩线；单凭 45%、55% 或 60% 不能给任意训练任务判好坏。

同口径下的观测 能说明什么 该干什么
明显低于已有基线 值得定位回退原因，不能仅凭 MFU 判配置出错 先查数据等待，再看通信、形状、同步与实现
略低于已有基线 可能有测量波动或配置差异 先重复测量，再核对检查点、通信与融合
接近已有基线 与该任务已记录的实现水平相近 结合吞吐、时间线与质量寻找下一处热点
稳定高于已有基线 可能是该任务的效率改善 核对输入、质量与 FLOP 口径，复测后再确认收益
MFU 升高，吞吐却没升 工作量或计数口径可能改变 核对每 token FLOP、有效 token 数与计时范围
换硬件、精度或模型后数值不同 不再是同一个比较条件 重新核对峰值与 FLOP 定义并建立基线，不按固定百分比排序

🔑 为什么 MFU 不会简单达到 100%，而 60% 也不是固定上限： 存在无法消除的开销 —— 通信、非矩阵乘操作（LayerNorm/Softmax/激活函数）、 数据加载、kernel 启动、优化器更新。这些都不算进"有效 FLOP"但要占时间。

🔍 三、MFU 低了怎么查（按顺序）

流程图

① GPU 有没有在跑？→nvidia-smi 看利用率，长期低于 90% = 没喂饱
② 数据管线跟得上吗？→把 dataloader 换成随机张量，MFU 变了吗？⭐
③ 通信占多少？→单卡 vs 多卡的 MFU 差多少
④ 非矩阵乘操作占多少？→profiler 看 kernel 时间分布
⑤ 有没有用上 Tensor Core？→精度对不对、维度对齐了吗
⑥ 激活检查点是不是开太狠？→全量重算会掉 30% 以上

⭐ 第 ② 步是最值得先做的诊断：

# 把真实数据换成固定的随机张量，其他不变
batch = torch.randint(0, vocab, (B, S), device='cuda')
# 如果 MFU 显著上升 → 瓶颈在数据管线，不在模型（第 22 章）

这一个实验能在 5 分钟内排除掉一整类问题。

💰 四、另外两个你该会算的数

① 训练一个模型要多久

$$\text{训练时间} \approx \frac{6 \times N \times D}{\text{GPU数} \times \text{峰值FLOPS} \times \text{MFU}}$$

（N = 参数量，D = 训练 token 数）

算一算

例：7B 模型，1T tokens，64 张 A100，MFU 45%

6 × 7e9 × 1e12 / (64 × 312e12 × 0.45)

= 4.2e22 / 8.98e15

≈ 4.7e6 秒 ≈ 54 天

⭐ 如果 MFU 只有 25%：97 天 —— 差了 43 天的机时

💡 这个公式的实用价值：在开始训练之前就能估算成本。 MFU 从 25% 提到 45%，在这个例子里省下的机时价值几十万元。

② 推理成本

算一算

小批量稠密自回归 decode 的权重相关前向 FLOP ≈ 2 × 参数量 / token

条件：batch=1，每一步完整权重都从选定 HBM 流过；给定可用有效带宽，忽略 KV、通信、计算及调度等其他开销

在此模型中，每个输出 token 的权重流量 = 全部权重字节数；权重搬运可能先限制速度，不能只用 FLOP 估时

→ 权重流量给出的理想速度上界 = 给定有效 HBM 带宽 / 权重字节数

教学例：7B 模型 BF16（14GB），假设有效 HBM 带宽为 2TB/s（借 A100 规格量级标定，非本次实测）

2000 / 14 ≈ 143 tokens/秒 ← 上述 batch=1 模型的权重流量上界

🔑 这个"带宽除以模型大小"是推理领域最有用的心算公式： 在上述权重流量主导条件下，量化有机会通过减少权重读取而提速（端到端收益仍需实测）， 也解释了为什么批处理可摊薄权重读取，但仍增加计算、KV 与调度开销（读一遍权重服务多个请求）。 🔗 第 15、16、18 章全建立在这上面。

✅ 检查点

  1. Roofline 模型的两条线分别代表什么？拐点在哪？
  2. Roofline 最大的价值是什么？（不是"能快多少"）
  3. MFU 怎么算？Transformer 每 token 的训练 FLOP 是多少？
  4. 为什么是 6N？这个公式什么时候会失准？
  5. 判断 MFU 前要对齐哪些比较条件？为什么 60% 不是通用好坏线或固定上限？
  6. MFU 低了，最值得先做的一个诊断实验是什么？
  7. 读 profiler trace 时，"GPU 时间轴有空隙"说明什么？
  8. 推理领域最有用的心算公式是什么？它解释了哪两件事？
👀 答案
  1. 斜坡是带宽上限（斜率=显存带宽），屋顶是算力上限。拐点 I = P/B；P 匹配计算路径、B 匹配 Q 的层级。156 只对应正文的 A100 稠密 Tensor Core 与取整带宽参考；原图自定参数的拐点为 4 FLOP/B。
  2. 告诉你"不能"快多少。在 I = 2 FLOP/B、同层 B = 2 TB/s 且口径不变时，带宽上界为 4 TFLOP/s。若改变复用或字节数，要重新核算；观测值低于它仍需检查其他开销。
  3. MFU = (6 × 参数量 × tokens/秒) / (GPU数 × 峰值FLOPS)。每 token 训练 FLOP ≈ 6 × 参数量。
  4. 前向 2mn + 反向对输入 2mn + 反向对权重 2mn = 6mn，而 mn 就是参数量。忽略了 attention 的 O(n²) 部分；按本页近似，其相对 6N 的比例是 2Lhs/N，是否要加 12·L·h·s 取决于模型尺寸、序列长度与可接受误差，没有统一 8K 阈值。
  5. 先与同口径基线比较：对齐模型、序列与 batch、精度、硬件与卡数、FLOP 约定及计时范围，并记录实现和检查点策略差异。通信、非矩阵乘操作、数据加载、启动和优化器更新会占时间；相同百分比在不同任务里意义不同，不能用 45–60% 作为通用成绩线或固定上限。
  6. 把 dataloader 换成固定的随机张量，其他不变。如果 MFU 显著上升 → 瓶颈在数据管线不在模型。5 分钟排除一整类问题。
  7. GPU 在等 CPU 或等数据 → 数据管线或 CPU 开销有问题。
  8. 在 batch=1 的稠密自回归 decode、每步完整权重从选定 HBM 流过的模型中，权重流量上界 = 给定有效 HBM 带宽 ÷ 权重字节数。忽略 KV、通信、计算和调度等开销，教学假设 2TB/s ÷ 14GB ≈ 143 tokens/秒。量化有机会减少权重读取；批处理可摊薄权重读取，但会改变计算、KV 与调度开销，端到端速度仍需实测。

⚡ 走神救援

先记住这几件事

  • Roofline 用同任务、同流量层级和匹配的执行峰值给出性能上界；实际观测可能更低。
  • MFU 的计算口径要对应模型、精度和硬件，不能拿 GPU-Util 代替。
  • 先保留基线，再从时间线检查数据等待、通信与算子开销，一次只改一个因素。
