01 / 完整解释

相同种子，不等于相同运行状态。

🎯 一句话

假设四个任务要给四份订单数据随机抽样。你在每个任务开头都写了 np.random.seed(42)，四份结果却从同一个数开始。把实验重跑一次，这个现象又出现了。要解释它，先看程序怎样一边出数，一边记住自己走到了哪一步。

🧩 一、从种子和状态开始

伪随机数（pseudorandom numbers）由确定的计算规则生成。种子（seed）是用来初始化的输入。状态（state）是生成器继续计算时要用的内部记录。重新用同样的配置和种子初始化，会回到同一个起点。继续用已经抽过数的生成器，则从它当时的状态向前走。

初始化用种子建立起始状态
→
抽一次按规则返回数值，同时更新状态
→
接着抽下一次使用刚更新的状态

教学用状态模型。为了看清重开和续跑的差别，假设内部只存一个整数。每一步把它乘 3、加 1，再取除以 7 的余数，余数也作为本步的输出。

s(t+1) = (3 × s(t) + 1) mod 7

t 是已经完成的步数，从 0 开始。s(t) 是第 t 步后的状态，取 0 到 6 的整数。mod 7 就是取余数。演示里直接令种子和初始状态都等于 2。

种子取 2 时的前三次抽样
第几次抽样代入与取余（粗体为输出）
第 1 次3 × 2 + 1 = 7，7 = 1 × 7 + 0
第 2 次3 × 0 + 1 = 1，1 = 0 × 7 + 1
第 3 次3 × 1 + 1 = 4，4 = 0 × 7 + 4

第二次抽完时存下状态 1，恢复后下一次得到 4。用种子 2 重开，下一次又得到 0。这条短规则只用来演示状态怎样更新，循环很短，实际采样使用 NumPy 的生成器。

def draw(state, count):
    values = []
    for _ in range(count):
        state = (3 * state + 1) % 7  # % 表示取余数
        values.append(state)
    return state, values

saved_state, first_two = draw(state=2, count=2)
_, continued = draw(state=saved_state, count=1)
_, restarted = draw(state=2, count=1)
print(first_two, saved_state)  # [0, 1] 1
print(continued, restarted)   # [4] [0]

draw 接收起始状态和抽样次数，同时返回结束时的状态和包含抽样结果的列表。保存 saved_state 后，只需用它作为下一次调用的起点。

本章聚焦 NumPy 的随机流。训练调试手册继续处理多库随机源与计算确定性，版本回溯与可复现还要记录代码、数据和环境。Kaggle 工程实践中记录种子的做法也依赖这些条件。

🧩 二、两代 API：同一个种子，给的数不一样

实际的 NumPy 还分两层。比特生成器（BitGenerator）管理内部状态并产生随机比特。随机数生成器（Generator）用这些比特构造你要的样本，例如 0 到 99 的整数。先预测下面三次比较的真假。randint(0, 100, 5) 和 integers(0, 100, 5) 都取 5 个整数，包含 0，排除 100。array_equal 比较数组形状和每个元素。

import numpy as np

np.random.seed(42); a1 = np.random.randint(0, 100, 5)
np.random.seed(42); a2 = np.random.randint(0, 100, 5)
print("legacy seed(42) 两次 ->", a1, "/", a2, " 一致:", np.array_equal(a1, a2))

b1 = np.random.default_rng(42).integers(0, 100, 5)
b2 = np.random.default_rng(42).integers(0, 100, 5)
print("default_rng(42) 两次 ->", b1, "/", b2, " 一致:", np.array_equal(b1, b2))

print("同一个种子 42，两代 API 给的数一样吗:", np.array_equal(a1, b1))

关键信息

legacy seed(42) 两次 -> [51 92 14 71 60] / [51 92 14 71 60] 一致: True
default_rng(42) 两次 -> [ 8 77 65 43 43] / [ 8 77 65 43 43] 一致: True
同一个种子 42，两代 API 给的数一样吗: False

两组各自复跑都得 True，交叉比较得 False。遗留模块级接口使用 RandomState 的梅森旋转算法（Mersenne Twister，MT19937）。default_rng(42) 会另建一个 Generator，这里用的默认比特生成器是 PCG64。换了初始化、底层生成与采样路径，种子 42 仍可在各自配置内重放。

np.random.seed(42) 只会重置遗留模块的共享状态，后面新建的 default_rng(42) 由括号里的 42 初始化。省略后者的种子时，default_rng() 从操作系统取得新的随机输入。复跑应同时记录 NumPy 的版本和构建、比特生成器、调用顺序和参数（包括输出大小），并保留运行环境和机器配置。NumPy 随机流兼容政策列出了这些条件。

🧩 三、💀 全局状态：任何人都能动它

假设你正在用遗留 API 抽三条订单，另一段代码也调用同一个模块级接口。下面用相同的整数抽样模拟它提前取走一条。现代生成器的对照组则在中途调用一次遗留接口。

import numpy as np

np.random.seed(42)
direct = np.random.randint(0, 100, 3)
np.random.seed(42)
discarded = np.random.randint(0, 100)
shifted = np.random.randint(0, 100, 3)
print(direct, discarded, shifted)  # [51 92 14] 51 [92 14 71]

rng = np.random.default_rng(42)
baseline = rng.integers(0, 100, 3)
rng = np.random.default_rng(42)
np.random.rand()  # 这次抽样只使用遗留模块的共享状态
isolated = rng.integers(0, 100, 3)
print(isolated, np.array_equal(baseline, isolated))  # [ 8 77 65] True

相同的整数抽样先取走了 51，所以后面的三个整数变成 [92 14 71]。换成别的分布或参数，消耗的底层比特数也可能变，不能把这个观测套成「任何调用都只跳过一个整数」。

rng 持有自己的比特生成器，因此遗留接口的调用不影响它。若两个函数拿的是同一个 rng，它们还是会轮流推进同一份状态。通常在调用方建好 rng，再传入负责抽样的函数。要让额外的调试抽样不扰动主流程，就为调试单独分配生成器。

02 / 完整解释

给 worker 分配各自的子流。

🧩 四、💀💀 招牌坑：四个任务，同一个种子

工作进程（worker）是并行执行任务的子进程。下面把四个抽样任务交给进程池。map 按输入顺序收集结果，某个进程可能处理多个任务，因此这里的四项输出表示四个逻辑任务，不用于判断哪个进程执行了它们。

先预测第一组。每个任务都把遗留状态重置为 42，接着抽一个 0 到 9999 的整数。把代码保存为 rng_workers.py，运行 python rng_workers.py。入口判断保护创建进程池的代码，避免子进程导入文件时又创建一组进程。

第三组先用 np.random.SeedSequence(42).spawn(4) 给四个任务派生各自的起点，下一节会拆解这一步。这里有两个叫 spawn 的操作。进程池用它来启动子进程，NumPy 用它来派生随机子流。

import numpy as np
from multiprocessing import get_context

def fixed_seed(task_id):
    np.random.seed(42)
    return int(np.random.randint(0, 10000))

def no_seed(task_id):
    return int(np.random.randint(0, 10000))

def child_seed(seed_seq):
    rng = np.random.default_rng(seed_seq)
    return int(rng.integers(0, 10000))

if __name__ == "__main__":
    context = get_context("spawn")
    with context.Pool(4) as pool:
        print("每个任务都重置成 42", pool.map(fixed_seed, range(4)))
    for run in (1, 2):
        with context.Pool(4) as pool:
            print("未记录种子", run, pool.map(no_seed, range(4)))
    for run in (1, 2):
        children = np.random.SeedSequence(42).spawn(4)
        with context.Pool(4) as pool:
            print("按任务分配子序列", run, pool.map(child_seed, children))
四个任务如何得到各自的随机输入
任务的起点本次可观察的结果重跑需要什么
各自重置成 42四项都为 7270。给同样的输入、执行同样的抽样，随机选择也会重复。记录 42 和抽样配置。
未管理遗留状态两次输出通常不同，进程启动方式与任务调度都会影响结果。这段代码没有保存重跑需要的随机输入和分配信息。
为任务派生子流示例两轮都是 [4974, 746, 7031, 8994]。记录根种子 42、子流与任务的对应关系，以及各任务的抽样调用。

这里显式使用 spawn（子进程重新启动并导入脚本）。每个任务主动重置同样的种子，换成别的启动方式也会重复。使用 fork（从父进程复制起始状态）时，遗留状态还可能在没有显式重置的情况下被继承。某次看到几个输出不同，仍无法凭一次观测判断各流独立。

如果四个任务对同一张样本执行同一套随机裁剪，重复的随机流会让四次裁剪采用同样的选择。训练可能照常运行，单看损失值无法发现这类重复。

🧩 五、用 SeedSequence 派生可复跑的子流

想让第 0 个任务和第 1 个任务下次各自复跑，得给它们可追踪的不同起点。种子序列（SeedSequence）把根种子与子节点在派生树中的位置一起混入初始化数据。根种子 42 的前四个子节点位置是 (0,) 到 (3,)。用这些子节点初始化的随机子流以极高概率相互独立，单次抽到相同的整数仍然可能。

import numpy as np

parent = np.random.default_rng(42)
kids = parent.spawn(3)                       # ⭐ Generator 自己就有 spawn
print("parent.spawn(3) 各抽一个:", [int(k.integers(0, 10000)) for k in kids])

ss = np.random.SeedSequence(42)              # 也可以直接从 SeedSequence 出发
print("SeedSequence(42).spawn(3):",
      [int(np.random.default_rng(c).integers(0, 10000)) for c in ss.spawn(3)])

要点

parent.spawn(3) 各抽一个: [4974, 746, 7031]

SeedSequence(42).spawn(3): [4974, 746, 7031]

上面两种写法都从刚初始化的根开始，得到同样的前三个结果。parent.spawn(3) 需要 NumPy 1.25 或更高版本。在这个实验中，从同一个新根派生 4 个孩子时，前三个仍处于相同位置。若在同一个 ss 上先调用 spawn(3)，再调用 spawn(1)，新孩子的位置是 (3,)，接着已有编号往后排。

从根种子到第 i 个任务
步骤代码位置
建立根ss = np.random.SeedSequence(42)主进程
派生四个子节点children = ss.spawn(4)主进程
任务 i 初始化自己的流rng = np.random.default_rng(children[i])执行该任务的 worker

这里让任务编号 i 在 0 到 3 之间，决定任务用哪条子流。改变调度顺序时，只要任务仍拿到同一个子节点，并用同样的顺序调用生成器，结果就能对上。增加任务、换分片方法或用会变的进程号当标识时，要重新核对子流分配。若一个任务需要抽很多次，就在任务开始时建一次 rng，随后一直复用。

NumPy 并行随机数指南还介绍了其他划分随机流的方法。PyTorch 的 DataLoader 有自己的 worker 初始化机制，详情见 AI 基础设施第 22 章。

🧩 六、Generator 的 API：改了名字的和改了行为的

订单例子里常用两种操作。抽样可以从候选里挑若干项。洗牌保留全部项目，只调整顺序。integers(0, 10, 5) 返回 5 个 0 到 9 的整数，加上 endpoint=True 后 10 也在候选范围内。choice(10, 4, replace=False) 从编号 0 到 9 中抽 4 个，抽过的编号不放回。

下面每行用同一个 rng，按执行顺序推进状态。random(3) 抽 3 个大于等于 0、小于 1 的均匀浮点数。normal(0, 1, 3) 从中心为 0、标准差为 1 的正态分布抽 3 个数。标准差描述数值围绕中心的分散程度。表里的小数只为阅读做了四舍五入。

import numpy as np

rng = np.random.default_rng(42)
print("integers (右端默认不含)", rng.integers(0, 10, 5))
print("integers endpoint=True ", rng.integers(0, 10, 5, endpoint=True))
print("random   [0,1)         ", np.round(rng.random(3), 4))
print("normal                 ", np.round(rng.normal(0, 1, 3), 4))
print("choice 无放回          ", rng.choice(10, 4, replace=False))
print("permutation (返回新的) ", rng.permutation(8))
a = np.arange(8)
rng.shuffle(a); print("shuffle (原地改)       ", a)

import numpy as np

X = np.array([[8], [23], [15], [30]])
y = np.array([0, 1, 0, 1])

rng = np.random.default_rng(0)
idx = rng.permutation(len(X))
X_shuffled = X[idx]
y_shuffled = y[idx]

print(idx.tolist())                  # [2, 0, 1, 3]
print(X_shuffled[:, 0].tolist())      # [15, 8, 23, 30]
print(y_shuffled.tolist())           # [0, 0, 1, 1]
assert np.array_equal(y_shuffled, X_shuffled[:, 0] > 20)

len(X) 是行数 4。permutation(4) 把 0 到 3 各用一次。X[idx] 和 y[idx] 都沿第 0 轴选出同一批原位置，X_shuffled[:, 0] 则取出全部耗时用于检查标签。若保留原标签顺序，23 分钟会和原位置 2 的标签 0 配对。分别调用两次 shuffle 也可能错位，因为两次调用各抽一次排列，形状检查无法发现配错。

🧩 七、存档读档：把「随机到哪儿了」存下来

回到手算例子。存下第二步的状态 1 才能接着得到 4。实际程序要保存比特生成器的状态快照。下面固定使用 PCG64，比对不中断时的下一批数字和新对象从快照恢复后得到的数字。

import json
import numpy as np

rng = np.random.Generator(np.random.PCG64(0))
rng.random(100)
checkpoint = json.dumps(rng.bit_generator.state)
expected = rng.random(3)

restored = np.random.Generator(np.random.PCG64(0))
restored.bit_generator.state = json.loads(checkpoint)
actual = restored.random(3)

print(np.round(actual, 6))  # [0.479988 0.232373 0.801881]
print(np.array_equal(expected, actual))  # True

先抽 100 个数推进状态，json.dumps 把这一刻的 PCG64 状态字典转成文本。接着抽 3 个作参照。新建的 restored 起初在起点，赋回 json.loads 还原的字典后就能从第 100 次抽样之后继续。代码比较的是原始浮点数组，打印时才取六位小数。

这个 JSON 写法适用于例子里的 PCG64。别的比特生成器的状态字典可能含 NumPy 数组，序列化时要保留形状和类型，并用同类比特生成器恢复。在第 30 轮训练结束后要精确续跑，还应保存其他随机源、数据读取位置、模型和优化器等状态。如果恢复后还要派生新的子流，还得记录派生进度或完整的子流分配方案。系统级的检查点记录见 模型上线之后第 17 章。

固定同一套随机输入有助于排查代码改动。评估一个改动是否稳定时，还要看它在多次实验中的变化和原本就存在的波动。

✅ 检查点

先在纸上预测结果，再跑相应的代码块核对。可以按小节分几次做。

  1. 教学模型的第三步得到 4。存下 4 后读档，第四步是多少？用种子 2 重开又是多少？
  2. 同样传入 42，遗留和现代整数抽样示例为什么各自能重放，却得出不同的数组？
  3. 只调用 np.random.seed(42)，能否控制后面的 default_rng()？两个函数共享同一个 rng 时，额外抽样会怎样？
  4. 在第三节的遗留实验中先取走哪个整数？随后的三个数是什么？
  5. 四个任务都主动重置同样的种子，为什么在 spawn 下也会重复？如果省去重置，能凭四个值不同就确认独立吗？
  6. 同一个 ss 执行 spawn(3) 后再 spawn(1)，最后一个孩子的位置是什么？怎样让任务换到另一个 worker 执行时仍抽到同一组数？
  7. 将 integers(0, 10) 改成 integers(0, 10, endpoint=True)，候选范围变在哪里？
  8. 二维数组中，permutation(m, axis=1)、permuted(m, axis=1) 与 shuffle(m, axis=1) 怎样搬列？哪一个就地改动原数组？
  9. 用下标 [2, 0, 1, 3] 打乱订单，若只移动 X，23 分钟会对应哪个错误标签？
  10. 训练第 30 轮结束后想继续抽数，为什么只存种子不够？
  11. 同一组种子下，新旧模型的指标差为 +0.3、−0.1、+0.1 个百分点。平均差是多少？每次都改善了吗？
👀 答案
  1. 第四步是 (3 × 4 + 1) mod 7 = 13 mod 7 = 6，因为 13 = 1 × 7 + 6。重开则从 2 算起，第一步输出 0。
  2. 在相同的版本、环境、比特生成器和调用条件下，各自重放。示例的遗留接口基于 MT19937，现代接口默认用 PCG64，两条生成与采样路径给出不同结果。
  3. 模块级 seed 只重置遗留共享状态。default_rng() 从系统取随机输入。两个函数共享同一对象时，先执行的抽样会推进状态，影响后续结果。
  4. 先取走 51，接着得到 [92 14 71]。这里两处调用抽的是同一范围的整数。
  5. 子进程重新启动后，任务代码仍会把状态重置到同一个起点。省去重置后，观察到的不同值也无法证明独立，尤其还要考虑 fork 可能继承状态。
  6. 最后一个位置是 (3,)。保存逻辑任务到子节点的映射，换进程时给它同一子节点，并保持抽样配置和顺序。
  7. 右端点 10 加入候选，整数范围由 0 到 9 变为 0 到 10。
  8. permutation 和 shuffle 用同一排列移动整列，其中 shuffle 就地修改。permuted 对每一行分别抽排列，默认返回新数组。
  9. 23 分钟被移到新位置 2，原标签序列在位置 2 是 0。用同一个 idx 同时索引 X 和 y 会得到正确标签 1。
  10. 种子用于初始化。续跑要存下当时的比特生成器状态，用匹配的类型恢复。完整训练还要恢复数据读取位置等其他进度。
  11. 三次差值相加为 0.3 − 0.1 + 0.1 = 0.3 个百分点，再除以 3 得 +0.1 个百分点。第二次下降。这三次的均值和逐次结果可以一并报告，观察是否有稳定改善还需结合实验的波动。
