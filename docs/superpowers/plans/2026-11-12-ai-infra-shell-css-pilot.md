## 实施

1. 冻结两课及 09 的源和输出，核对工作区与正式映射。验证 07、08 的规则块逐字节相同，并记录 CSS 规则数、旧页和生成页大小。先运行抽取检查，预期共享文件与接线尚未存在。
2. 将原规则块直接写入共享 CSS。在原规则块处结束第一个 style，链接 CSS，再开启第二个 style。保留前后声明、既有资源 URL 与样式先后顺序。保留页面主题、移动端、模块覆写和代码 palette 的原有归属。
3. 通过 `maintenance/polished-pages.json` 选中且只选中这两条 recovered_html 条目，调用现有构建器定向生成。验收时把每页共享引用反向展开，要求能逐字节重建旧页面，并核对每对源／输出、09 指纹、内部链接与 ID。
4. 用本地 Chromium 对照旧页和候选页。覆盖 1440 与 390 像素、浅深主题、相反系统偏好和已保存主题重载、无 JavaScript、离线本地打开。比较截图及计算样式，检查滚动进度、目录和前后章链接、双打卡按钮与旧键。复验原书签及浏览器历史恢复。若页面没有专用续读控件，记录适用性。
5. 复验本批代码块、复制／换行／放大及原有固定深黑样式，记录计算背景和对比度。测试阻断新 CSS 时原生内容、静态导航和既有状态控件仍可用。记录控制台错误、截图、测试数量、对照页和未覆盖项。
6. 单一提交纳入本计划、共享 CSS 和两对页面。使用仓库配置的 author 与 committer。追加一次 `Co-authored-by: Codex <codex@openai.com>`，提交后用 `git show` 确认身份、文件边界和 trailer。保持本地提交。

## 回滚

若资源 404、顶栏滚动行为或布局偏离基线，从本次提交的父版本恢复两份维护源的内联规则，按映射定向生成两份输出，再移除没有消费者的共享 CSS。提交后可用一次反向提交回滚整批。通过逐字节对照确认原样恢复，并复核旧进度键与 09。
