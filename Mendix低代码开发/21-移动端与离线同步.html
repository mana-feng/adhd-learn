21 · 移动端与离线同步

⏱ 阅读约 12 分钟 ｜ Studio Pro 11.12 LTS，动手时间另计

🎯 一句话

离线保存只说明数据已留在设备上；同步成功后，服务端还要决定哪些业务操作可以发生。 本章先做离线报修笔记，不把审批和接单强行搬到断网设备。

起点：在线工单应用可运行。先在分支增加 offline-first PWA navigation profile，保留原响应式入口；native 同样需要离线设计，但本章先用 PWA 减少原生打包依赖。

🧩 一、先区分手机布局与离线能力

类型 数据与网络 本例选择
响应式在线页面 手机能排版，操作依赖服务端 继续用于审批和维修
Offline-first PWA 设备数据库，可同步 新建离线报修笔记
Native mobile 原生运行与设备能力，也有同步设计 有原生需求时再扩展

第一次启动与登录通常需要联网。Mendix 会根据离线 profile 使用的页面和逻辑分析同步实体，仍要检查实际同步范围。Navigation 文档

🛠️ 二、给离线输入独立的数据模型

新增持久化 OfflineNote：ClientKey String80、Title String120、Body String无限制、RecordedAt DateTime、ResultText String80，以及 Note_Author 到 System.User、Note_WorkOrder 到 WorkOrder 的单值关联；后者只由服务端确认时设置。

把它当成“待整理笔记”，不等同于已提交工单。Author 关联及创建权限需让当前用户只能建立和同步自己的笔记；服务端提交事件核验作者与当前身份，拒绝伪造归属。访问规则只返回自己笔记；上传后的业务结果字段不允许客户端任意修改。

ClientKey 为设备创建的请求标识，后续确认转工单用于去重；真正跨设备去重需服务端约束和冲突处理。不要用标题当唯一键。

本章 PWA 可沿用第 20 章的扩展方式，建立无参数、返回 String 的 JavaScript action GenerateClientKey，在 USER CODE 区使用 return crypto.randomUUID();。通过 Nanoflow 调用，将结果保存到 ClientKey，重试时复用已保存的值。该浏览器能力要求安全上下文与兼容浏览器；正式 PWA 使用 HTTPS，本机按浏览器支持的可信本地来源测试，详见 randomUUID 文档。不要把这一浏览器实现原样当成所有 native 环境都可用。

为离线 profile 建立 OfflineNote_Overview 和编辑页，数据源使用设备可用实体；Nanoflow 创建对象、赋当前作者和 ClientKey、设置时间，保存时 Commit 到本地数据库。第一次先联网登录并加载所需身份数据，再断网操作。

🛠️ 三、给“本地保存”和“同步”不同反馈

保存按钮只写“已保存到此设备”。增加同步按钮，Nanoflow 先确保编辑内容已 Commit，再使用 Synchronize 动作；成功才提示“同步已完成”，失败保留本地数据并提示重试。

同步基于数据库里的提交值，未 Commit 的编辑不应被当成已经上传。一次上传成功而下载失败时，服务端可能已有更改，设备仍需恢复同步；不能简单宣布“所有步骤全部回滚”。同步机制

在 profile 的 Synchronization Configuration 检查 OfflineNote 的下载范围，只取当前人的必要笔记，避免把全公司工单和附件下载到设备。同步配置减少下载量，实体权限仍是服务端边界。

中途停靠： 断网创建笔记、刷新后仍在、联网后服务端可见，就完成离线数据主线；此时还没有提交业务工单。

🧭 四、联网后才转为受控工单

在原在线响应式入口建立“我的已同步笔记”页。ACT_OfflineNote_CreateWorkOrder 服务端按笔记 ID 查库、核验作者和输入，按 ClientKey 检查是否已创建，再调用受控草稿创建逻辑填 Title、Description；记录生成工单关联或业务标识。

新建仍是 Draft，用户补部门、费用后执行原提交与审批操作。笔记同步不会自动批准、接单或关闭。确认入口重复调用时返回已有结果，真正并发下还须补齐唯一性与竞争处理。

离线 profile 中调用服务端 Microflow 需要网络，并有参数限制，不能照搬在线传持久化对象的方法。本例通过联网后的在线入口确认，避免把客户端临时状态当权威业务对象。离线限制与冲突说明

⚔️ 五、用两台设备亲眼看冲突

同一测试账号在两台设备同步同一笔记，断网分别编辑 Title 与 Body，先同步 A 再同步 B，检查服务端最终值，再交换顺序重测。不要假设平台会逐字段智能合并。

默认离线冲突可能表现为后同步覆盖对象内容，不能拿在线乐观锁能力直接推断离线安全。业务若要求保留双方修改，可以改成只新增的 NoteRevision，附原版本和作者；冲突交给用户选择，再写入正式工单。规则要在服务端验证。

最简单的主线约束是每条离线笔记只由一个设备创建者编辑，转工单后停止修改原笔记。即使如此，换设备和重试仍需纳入测试。

🔎 六、验收断网、撤权与升级

操作 核对内容
断网新建再刷新 本地已提交内容仍在
保存后同步失败 不显示业务提交成功，不丢本地笔记
两设备编辑同对象 记录覆盖或冲突的实际规则
服务端撤销权限再同步 新请求按最新权限处理
模型升级再打开旧设备 笔记、文件和同步状态可解释

已经缓存到设备的数据不会因为服务器撤权就隔空消失。减少本地敏感数据、遵守设备锁定与退出策略，结合实际数据清理机制验证。离线数据安全

升级前先备份并检查 11.12 补丁与模块已知问题，尤其 native 的模块更新方式。离线验收要使用真实断网及设备数据，手机宽度截图不能证明具备离线能力。

✅ 检查点

  1. 本地 Commit 是否等于服务器已收到？
  2. 笔记上传会自动审批吗？
  3. 两设备改不同字段必然合并吗？
  4. 撤权会立刻抹掉设备缓存吗？
查看答案
  1. 不等于，离线先保存设备数据库，再同步。
  2. 不会，联网后受控创建草稿，再走原提交流程。
  3. 不保证，必须验证冲突策略，可能覆盖对象内容。
  4. 不会，服务端新请求和已有本地副本是不同边界。
