08 · 谁可以看到和修改什么

⏱ 阅读约 15 分钟 ｜ 先配置账号，再逐条验证权限

🎯 一句话

页面入口、可执行的操作和可读取的数据都要分别授权。 “没有显示编辑按钮”不是阻止越权修改的充分条件。

起点： 第 04 章三条 WorkOrder 关联、第 05 章提交 Microflow，以及第 07 章列表。此前使用的无身份演示数据可以保留给管理员查看；本章用登录后的账号新建测试工单，不把旧记录随意归给当前用户。

👥 一、先定义角色，再创建测试账号

在 App > Security 把 Security level 设为 Production。这里的 Production 是安全检查级别，不是点击后就把应用发布到生产环境。关闭匿名访问，按 Errors 补齐缺失的权限配置。

在 Helpdesk 模块的 Security 中创建 Requester、Technician、Manager、Administrator 四个模块角色。在 App Security 的 User roles 中创建或配置同名应用角色，映射到对应 Helpdesk 模块角色。

应用角色 Helpdesk 模块角色 本教程职责
Requester Requester 创建、修改和提交自己的草稿，查看自己的工单
Technician Technician 查看待接单工单，处理分给自己的工单
Manager Manager 查看演示范围内的工单，参加费用审批
Administrator Administrator 管理演示部门、账号和排查配置

应用角色还要按模板要求映射到 Administration、Atlas 等模块中的普通使用角色。只有管理员获得账号管理权限；不要为了清除错误给所有人添加所有模块的 Administrator。配置入口和角色关系参见模块安全。

建立两名 Requester 测试用户、一名 Technician、一名 Manager，以及管理员。可以使用本地 Demo users，实体选择 Administration.Account；本地演示用户切换只用于测试，不等同于正式登录体验。

🧱 二、配置 WorkOrder 的实体访问

打开 WorkOrder > Access rules。先设新成员的默认权限为 None，再逐项开放当前需要的字段，避免以后新增内部备注时自动向所有人公开。

下面是本教程的目标权限。Create、Delete 对普通用户都不开，创建交由下一节的受限服务端动作；客户端不能直接改 Status、Submitter、Assignee。

模块角色 能读取哪些 WorkOrder 客户端能改什么
Requester WorkOrder_Submitter 是当前用户 自己 Draft 的 Title、Description、EstimatedCost、WorkOrder_Department
Technician Submitted 或 WorkOrder_Assignee 是当前用户 自己 InProgress 的 Resolution
Manager 本练习中所有工单 无；审批通过任务完成动作处理
Administrator 所有演示工单 仅按管理需要授予，测试时不用此角色冒充普通用户

Requester 可拆成两条规则：一条允许读取自己的全部工单；另一条限制为自己的 Draft，开放四个可编辑成员。第二条 XPath 为 [Helpdesk.WorkOrder_Submitter = '[%CurrentUser%]'][Status = 'Draft']。提交后，该记录仍可读，但普通字段不再可写。

Technician 的读取约束为 [Status = 'Submitted' or Helpdesk.WorkOrder_Assignee = '[%CurrentUser%]']；另建 [Status = 'InProgress'][Helpdesk.WorkOrder_Assignee = '[%CurrentUser%]'] 的规则开放 Resolution 写权限。

多条匹配的规则会合并授予权限，不存在靠另一条更窄规则自动收回广泛授权的效果。 删除或收紧以前的“所有 User 可写全部”规则，也检查应用用户是否同时带着其他宽权限角色。依据实体访问规则。

Department 给这些业务角色 Name 读取权限，增删改仅给管理员。用户关联只用于身份比较时，不需要把用户目录全部开放；如果页面需要显示他人的姓名，按 Administration 提供的普通使用或 ReadOthersFullName 角色处理，不开放密码及无关账号属性。

🛠️ 三、让服务端创建带身份的草稿

移除第 03 章的普通 Create object 新建按钮和普通删除按钮。新建 ACT_WorkOrder_New，只允许 Requester 从客户端调用，Apply entity access 设为 Disabled，并明确把它限制为下面这一条用途：

  1. Retrieve System.User，以 [id = '[%CurrentUser%]'] 取当前用户，结果命名 CurrentUser；取不到则结束并报告无法识别当前账号。
  2. Create WorkOrder，Status 设为 Draft，WorkOrder_Submitter 设为 CurrentUser。不能接受页面传来的“提交人”参数。
  3. 显式 Commit 这个草稿，再打开 WorkOrder_NewEdit。

这会先保存一个草稿。 用户关闭编辑页后草稿可能仍然存在，这符合“先占一个草稿，再编辑”的本章选择。页面取消只取消未保存修改，不能假装会删除这条已创建的草稿；后续若要清理空草稿，应设计明确的清理规则。

为什么这里关闭 Apply entity access？因为普通客户端没有创建和写入 Submitter 的权限，这条服务端动作负责代为创建。它因此拥有更大的责任：限制调用角色、取运行时身份、只写固定字段，不接收任意成员名或任意用户对象。

不要把 Disabled 当成解决报错的通用办法。 普通查询 Microflow 应启用 Apply entity access；需要特权的动作单独列出并审查。该开关决定数据访问是否按当前用户的实体规则执行，Allowed roles 决定客户端调用入口，二者不是一回事。参见Microflow 属性。

🛑 到这里可以停一次

用小林账号创建草稿，再用第二名 Requester 登录。先确认前者能打开、后者看不到。若还未成立，先修身份关联和实体规则，不要急着接审批。

🔐 四、补上提交动作的授权检查

第 05 章的 ACT_WorkOrder_Submit 现在只允许 Requester 从客户端调用；它要写普通用户无权直接写的 Status，因此作为明确的特权动作处理。

在修改状态前，先确认参数指向已创建的工单，按其标识检索目标，并检查提交人是运行时当前用户、状态仍为 Draft。继续执行标题、费用和部门校验，通过后才更新状态。实体规则已经禁止客户端改写 Submitter 和 Status；不能把这些权限重新开放来图省事。

编辑页保留 Save changes 保存草稿内容，再从已保存的详情或列表调用“提交”，避免把“未保存表单输入”和“读取已保存工单状态”混成一步。页面中的按钮可见条件帮助用户理解，但服务端仍重复检查归属和状态。

本教程不将特权子 Microflow 暴露为通用客户端入口。若其他 Microflow 调用它，调用链仍需检查授权；不要假定某个入口的 Allowed roles 会替整个服务端调用链检查所有业务条件。

🧪 五、用两个账号验证反例

测试 预期结果
小林新增并编辑自己的 Draft 可保存合法输入
第二名 Requester 打开“全部工单” 仍只得到自己的数据
第二名 Requester 尝试操作小林的工单 不能读取或提交，服务端不接受越权状态操作
小林提交后再打开编辑页 仍能查看，草稿字段不再可写
Requester 直接访问部门管理页 无权管理部门
小周登录查看待接单列表 只见符合 Technician 规则的记录

要验证直接操作，使用本地测试环境中的页面入口或测试调用，并核对服务端是否拒绝；“按钮不见了”只验证了外观。两个浏览器窗口若共享登录 Cookie，未必是独立身份；使用不同浏览器配置或明确退出再登录。

✅ 检查点

  1. Production 安全级别是否意味着已经部署上线？
  2. 先给用户全表读权限，再加“只读自己的”规则，能否自动收紧？
  3. 提交人为什么不能让用户自己选择？
  4. 关闭 Apply entity access 后，还能否指望实体规则自动限制检索范围？
查看答案
  1. 不是，它是安全配置级别。
  2. 不能，匹配规则会合并授权，宽规则要主动收紧。
  3. 它是后续归属判断依据，应由服务端从当前会话确定。
  4. 不能。特权动作必须自行验证身份、目标和业务条件。
