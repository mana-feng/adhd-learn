17 · 复杂审批、等待与流程版本

⏱ 阅读约 13 分钟 ｜ Studio Pro 11.12 LTS，动手时间另计

🎯 一句话

多人审批的关键是定义谁必须参与、何时得到最终结果，以及等待中的实例如何继续。 增加几个按钮，并不能自动得到串行审批或会签。

起点：第 10 章 Approve/Reject 两条路径已跑通，使用兼容 11.12 的 Workflow Commons 4.x。本章在独立练习分支复制流程为 WF_WorkOrderApprovalAdvanced，只让新测试工单调用它；保留旧流程定义及在途实例。

🧩 一、三种多人关系不能混为一谈

业务问题 模型选择 本例验收
多名主管任意一人处理 普通 User task，多名目标用户 一人领取并完成即可
主管通过后财务再审核 同意路径串接第二个 User task 第一关未过，第二关无待办
三位评审各投一票 Multi-user task + 完成条件 结果由投票规则决定

先问“每个人都必须处理，还是任何一人处理就够”，再选任务类型。普通 User task 匹配多人不是会签。

🛠️ 二、串行审批先延迟最终业务更新

增加应用角色与 Helpdesk 模块角色 Finance，映射 WorkflowCommons.User 与必要的账户访问。Finance 只读待审工单，不获得客户端修改 Status 的权限；准备独立财务账号。

在复制的流程中，主管 Approve 后先接第二个 User task ReviewFinance，目标数据库筛选使用财务应用角色。为它生成并核验真实任务页，保留 System.WorkflowUserTask 的任务完成接线，不能只传 WorkOrder。

主管通过时暂不调用 SUB_WorkOrder_ApprovalAccepted。财务也 Approve 后才调用原最终批准逻辑；任一 Reject 都调用原拒绝逻辑。于是整个两关审核期间，WorkOrder 保持 AwaitingApproval。

用一张 501 元工单测试：主管同意后仍不能接单，财务同意后才成为 Submitted。再用新单走主管拒绝与财务拒绝，核对后续任务不会继续开放。

🗳️ 三、会签把完成条件写成配置

另复制一份练习流程，替换审核节点为 Multi-user task，目标为三个专用评审账号，保证查询确实只返回这三人。给他们相同的读取权限和任务页权限。

本例选择多数决，不实现“一票否决”：Participant input 设置需要 3 人参与，Decision method 选 Majority，Majority type 选 More than half，Outcomes 为 Approve、Reject，Fallback outcome 选 Reject。Completion moment 选 When outcome is known。属性含义见官方多人任务文档。

投票过程 预期现象 理由
先一票 Approve 继续等待 还不足以确定三票多数
接着一票 Reject 继续等待 1 比 1，需要第三票
第三票 Approve 最终 Approve 2 比 1
新单前两票都 Approve 可提前得出 Approve 选择了结果已知即完成

如果业务要求第三人也必须留下意见，将 Completion moment 改成 When all participants completed their task，并重新测同一组顺序。不能既要求“尽早结束”又声称“所有人都已审过”。

若实际制度是一票否决，可另做 Veto 练习：Outcomes 为 Approve/Reject，Veto outcome 选 Reject，参与人数仍为 3；测试任意一人拒绝即得到拒绝，以及三人全部同意才通过。另需明确零目标用户和无人响应时的处理。不能把本例多数决改名为“一票否决”。

中途停靠： 先把串行与三人多数决分别核验；不要在同一实例上来回更换规则。

⏳ 四、Due date 与真正的超时路径

Due date 是任务的截止信息，不会自动发送提醒。给测试任务附 Timer boundary event，设置相对时长 2 分钟，Interrupting=No；超时路径调用一个写“审批提醒”业务日志的 Microflow，然后结束该旁路。这里先写日志，不连接邮件服务。

保留原用户任务等待，2 分钟后应多出提醒记录，任务仍可由主管完成。把用户任务提前完成，检查不再产生一条无意义的后续提醒。计时由运行引擎调度，观察时记录实际触发时间，不把 2 分钟当成毫秒级承诺。

若改用 Interrupting=Yes，父任务会中止，超时路径接管后续；本例超时路径可调用拒绝逻辑再结束。此时旧任务不能再按原批准按钮完成。两种行为见边界事件与Timer 属性。

普通 Timer 节点放在主路径上会等待后继续；边界 Timer 附着在活动上处理它等待期间发生的事情。选择取决于是否要让原任务保持可用。

🧭 五、更新流程前保留一个等待中的样本

在测试环境准备三个样本：未发起、正在主管审核、已经完成。记录各自实例标识和所在活动。先做一个说明文字变化，部署后核对在途实例的状态；再在练习分支尝试删除当前等待节点，观察兼容性检测结果。

兼容变更可能自动升级实例；冲突会将实例标记 Incompatible 并记录原因。旧版本还可能引用你已删除的页面、Microflow 或角色，因此不能为了清理目录删掉旧依赖。流程版本与冲突文档

🛠️ 六、恢复按原因选择，不盲目重启

先读取实例的冲突原因、活动历史和外部副作用。临时接口失败且操作可安全重试时才 Retry；定义不兼容先修正兼容设计，再采用对应冲突类型允许的恢复方式。

Restart 可能重走已执行步骤，Jump 会跳过某些步骤，Abort 会结束当前实例。哪一种适用取决于冲突类型和业务允许的补偿，不能把所有 Incompatible 都标记“已解决”。管理员操作也要记录工单、操作者、原因和核验结果。

最终验收让旧在途单与新单各走完一条路径，确认业务状态与任务历史一致。多级审批不会自动补齐主线的并发发起保护，仍须按毕业项目 T05 单独测试。

✅ 检查点

  1. 主管同意后为何还保持 AwaitingApproval？
  2. 两票同意是否一定等第三票？
  3. 非中断计时提醒会取消原任务吗？
  4. Incompatible 能直接全部标解决吗？
查看答案
  1. 财务尚未通过，最终批准更新必须放在第二关之后。
  2. 取决于 Completion moment；本例结果已知即完成可以提前结束。
  3. 不会，父任务仍可处理；中断计时才会中止父活动。
  4. 不能，须读取原因，按支持的恢复方式处理并核对已发生的副作用。
