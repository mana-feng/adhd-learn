06 · 为什么改了数据却没保存

⏱ 阅读约 10 分钟 ｜ 用可丢弃的测试工单观察

🎯 一句话

页面看到的值、内存对象的值和数据库已完成事务的值，可能暂时不同。 先确定自己在看哪一层，再判断保存是否成功。

起点： 第 05 章的提交 Microflow 和编辑页；一张已保存、费用为 300 的测试工单。实验前记下标题，避免改错真实记录。

🔍 一、先观察一次保存和取消

打开工单，把费用从 300 改成 350。此时输入框显示 350，说明页面正在编辑对象，不说明其他用户已经能读到 350。

点击 Cancel changes，重新打开同一张工单，预期又看到 300。再把它改为 350，点击 Save changes，关闭并重新检索，预期这次看到 350。

操作 页面当前看到 本实验重新打开时的预期
刚打开已保存记录 300 300
输入 350，尚未保存 350 尚不能据此判断数据库
取消这次未保存修改 返回原值或关闭页面 300
再改 350 并成功保存 350 350

这组比较的前提是没有其他动作提前 Commit，也没有其他用户同时修改该记录。前提变化，结果就需要重新分析。

🧩 二、把几个相似动作分开

Create object 创建一份对象；Change object 改它的值；Commit object(s) 对持久化对象发出保存操作；Rollback object 撤销到对象最近一次 Mendix commit 的状态。页面上的关闭动作只控制页面，不自动等价于这些数据操作。

对持久化对象，Mendix Commit 活动会写数据库，但它不等于立刻完成最外层 SQL 事务。当前 Microflow 及调用它的上层 Microflow 仍可能继续执行；后面的错误按错误处理配置可能触发事务回滚。依据官方 Commit 语义。

因此，调试时经过 Commit 节点，不能直接宣布整个操作最终保存成功。 等操作结束，再从独立会话读取，是不同层次的验证。

🧪 三、做一个最小的 Change 实验

在独立测试 Microflow 中接收一张测试 WorkOrder，使用 Change object 把费用设为 400，Commit 设为 No，然后将对象显示在页面。观察页面能否显示这个修改；再退出本次编辑上下文，从另一个会话重新查询已保存记录。

然后把测试逻辑改为显式 Commit，并让整个操作正常结束，再从另一个会话读取。比较两次结果时，记下是否保存、是否有异常、是否确实开启了另一个用户会话。

不要把同一会话的第二次 Retrieve 自动当成“绕过所有内存状态的全新 SQL 读取”。对象可能已在运行时内存中。这个实验要区分会话、保存动作和事务结束，而不是背诵“刷新一下就一定准确”。

🗃️ 四、持久化与非持久化选什么

WorkOrder 和 Department 需要在下次登录时还能找到，所以是持久化实体。筛选条件、预览表单这类临时状态可以使用非持久化实体。

非持久化对象也可以 Commit，但这是保存其当前内存状态供后续 Rollback 使用，不会因此多出一张数据库表。它不适合保存明天还要继续的审批请求；Workflow 的业务上下文要使用持久化实体。

假如用户按“保存草稿”，就要明确保存的是业务记录；假如按“预览”，通常只计算展示，不应在读者不知情时提交正式工单。按钮名称应该与真实副作用一致。

🩹 五、两类容易误诊的问题

关联到另一个新对象

如果同时新建 Department 和 WorkOrder，然后只显式提交工单，不应依赖平台的 autocommit 替你完成整套业务保存。关联可能引起平台自动保存以维持一致性，但 autocommit 不等同于业务上的显式提交。

本教程先保存 Department，再让工单选择已有部门。需要同时创建多种对象时，明确每个对象何时校验、何时提交、失败时怎样处理。

取消不是任意历史撤销

某个子 Microflow 已 Commit 过对象后，外层页面再点 Cancel changes，不能自动回到本次打开页面以前的任意版本。需要“撤回提交”时，应设计一个新的业务动作并保存记录，而不是把数据 Rollback 当成万能撤销。

✅ 检查点

  1. 输入框显示 350，能证明另一名用户已看到 350 吗？
  2. Commit 非持久化对象会不会把它写进业务数据库？
  3. Microflow 后半段失败，前半段 Commit 是否必然永久生效？
  4. 已保存的提交要撤回，为什么不能只依赖页面取消按钮？
查看答案
  1. 不能，页面值、对象状态与事务对其他会话的可见性要分开。
  2. 不会；它保存的是内存中的提交状态。
  3. 不必然，要看事务边界和错误处理是否触发回滚。
  4. 取消不是任意历史版本恢复；撤回属于有条件、有留痕的业务动作。

走神救援

  • 看见新值，不等于整个保存事务完成。

  • 明确提交每个业务对象，不依赖 autocommit 完成业务流程。
