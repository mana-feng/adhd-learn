18 · 模块拆分与复用

⏱ 阅读约 10 分钟 ｜ Studio Pro 11.12 LTS，动手时间另计

🎯 一句话

模块边界要让业务规则和外部依赖各有归属，并让调用者知道输入、输出和失败行为。 把一个大模块分成十个文件夹，不等于得到十个可复用模块。

起点是第 12 章已有 HelpdeskIntegration 的应用。先抽一个设备查询接口练习，不移动全部工单实体，也不删除旧 Workflow 依赖。

🧩 一、按变化原因确定归属

模块 拥有什么 不应随意承担什么
Helpdesk WorkOrder、部门关联、状态命令与权限 外部设备接口的全部实现细节
HelpdeskIntegration 地址、消息结构、映射、接口调用 决定谁有权关闭工单
Workflow Commons 等依赖 已有任务视图和基础功能 教程自定的 500 元费用制度

供应商换 JSON 字段时，主要改 Integration；维修增加状态时，主要改 Helpdesk。调用方向应让业务层依赖查询接口，查询层不再反向调用工单页面，避免循环依赖。

🛠️ 二、先写一张接口契约

把固定 A100 演示入口抽成 HelpdeskIntegration.SUB_Asset_Lookup，参数 AssetCode String，输出非持久化 LookupResult。LookupResult 包含 Found Boolean、DisplayMessage String、AssetCode String、AssetName String、UnderWarranty Boolean。

输入或情况 返回约定
A100 且有效响应 Found=true，填设备信息
查不到 Found=false，文案“未找到设备”
服务故障 Found=false，文案“设备信息暂不可用”
输入为空或非法字符 不发请求，返回可理解的校验结果

业务层根据 Found 决定显示哪种页面，不从中文提示文案反推业务结果。若需要区分 NotFound 与 Unavailable，再增加结果枚举；不要让调用者解析日志字符串。

🛠️ 三、移动实现，保留受控入口

在 Integration 中使用第 12 章的消息结构和映射，Call REST 后将数据转换为 LookupResult。接口不提交 WorkOrder，不 Show 工单页面，也不依赖 Requester 的页面上下文。

Helpdesk 的 ACT_WorkOrder_LookupAsset 继续接收 WorkOrder，先查库并验证当前人可读，提取 AssetCode，再调用 SUB_Asset_Lookup，最后展示结果。页面调用权限放在 ACT 入口；内部 SUB 不应因此暴露给不需要的客户端角色。

保存后用 Find usages 核对调用处，逐个修正参数与返回值。每次只迁移一个小接口，运行一致性检查，再测试成功、无权限、接口失败三条路径。

模块角色不是应用角色，模块中定义角色后必须映射到实际应用角色。访问级别或“不在导航里”也不能替代实体权限与服务端身份核验。

中途停靠： 设备查询实现可以变化，而工单页面仍使用同一契约，就得到一个可复用边界。

📦 四、导出后在空白应用里验收

右键模块选择 Export module package。若提示引用其他用户模块，使用 Find usages of other user modules 查看原因；在依赖选择中核对必要的 resources、userlib 与 widgets，不把全部无关文件打包。官方导入导出说明

在另一个 Studio Pro 11.12 测试应用中导入，补齐声明过的依赖、模块角色映射和常量。建立一个最小测试页面调用设备查询，核验 A100 与 A404。只在原应用成功，无法证明包可复用。

交付说明记录模块版本、Studio Pro 补丁号、依赖版本、公开入口、输入输出、错误语义、常量、所需权限和测试数据。若仍要求接收方复制一个隐藏页面才能运行，就把这项依赖补进契约。

🔄 五、第三方升级与自有修改分开管理

尽量在自有模块中包装第三方能力，避免直接改其核心页面和逻辑。确需定制时记录差异，升级前备份并在分支中核对新旧依赖、模型冲突和已有配置数据。

11.12 的补丁也存在具体差异：截至本教程核对时，11.12.3/11.12.4 的新 Update from file 流程有影响 native StorageGuids/StableGuids 的已知问题；涉及离线数据时按发布说明采用普通 App > Import module 或 Marketplace 下载流程，并先备份验证。11.12 发布说明

这不是要求升级到另一条主版本。团队仍统一 11.12，选定并记录同一个补丁版本，按已知问题安排升级演练。

🔎 六、用一个破坏性变更判断契约是否清楚

在练习分支把 LookupResult 的 AssetName 重命名，查看哪些调用者受到影响。再恢复名称，改为增加一个可选展示字段，比较两者的迁移成本。

实体移动或重命名可能涉及已有数据、Java 代理与 Workflow 上下文，不是普通文件移动。正式应用需要验证迁移前后对象、关联和在途实例，不能只看模型图变得整齐。

✅ 检查点

  1. 模块边界按什么确定？
  2. 设备接口为何不直接关闭工单？
  3. 如何证明导出包可复用？
  4. 模块不在导航中就安全吗？
查看答案
  1. 按业务责任和变化原因，避免双向循环依赖。
  2. 查询模块不拥有工单身份和状态规则。
  3. 在另一个干净应用按声明依赖导入并测试。
  4. 不是，仍需要调用权限、实体访问和服务端检查。
