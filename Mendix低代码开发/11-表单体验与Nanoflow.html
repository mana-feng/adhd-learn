11 · 表单体验与 Nanoflow

⏱ 阅读约 10 分钟 ｜ Studio Pro 11.12 LTS，动手时间另计

🎯 一句话

让用户在出错的位置知道怎么改，同时让服务端继续守住业务规则。 这一章把“保存失败”改成“标题不能为空，请先填写问题”。

起点是第 08—10 章的在线响应式应用：Requester 能编辑自己的 Draft，提交与费用审批由服务端执行。这里只改编辑体验；离线另见第 21 章。

🧩 一、先确定三种反馈发生在哪里

小林输入只有空格的标题，预计费用填成 −1。理想结果是：标题和费用各出现一条解释；原输入保留；没有工单进入 Submitted，也没有审批任务产生。

位置 本例做什么 为什么还需要其他层
页面输入控件 必填、长度及格式提示 其他入口可能不经过这张页面
Nanoflow 提交前即时检查并定位字段 在客户端执行，不能证明有权操作
服务端 Microflow 核验身份、最新状态、业务字段后提交 拒绝过期页面或越权请求

不要给 Title 直接加实体级“必填”后就结束：第 05 章的新建操作会先保存空草稿，这样会被你新加的规则挡住。当前设计允许空草稿，业务提交时才要求完整；若决定草稿也必须完整，就要同时重做新建和取消策略。

🛠️ 二、做一个可返回结果的客户端检查

在 Helpdesk 新建 Nanoflow VAL_WorkOrder_Form，参数 WorkOrder，返回 Boolean。创建 Boolean 变量 IsValid，初始 true。这里的 VAL 是命名约定，不是系统关键字。

  1. 加 Decision，条件为 trim($WorkOrder/Title) = ''。true 路径用 Validation feedback，Variable 选 WorkOrder，Member 选 Title，静态文案“请填写问题标题”；再把 IsValid 改为 false。
  2. 合并路径后继续判断 $WorkOrder/EstimatedCost < 0。错误路径定位 EstimatedCost，文案“预计费用不能小于 0”，并把 IsValid 改为 false。
  3. 对 WorkOrder_Department 做 Retrieve by association；结果 empty 时把反馈定位到该关联，文案“请选择报修部门”。
  4. 三项检查全部完成，End 返回 IsValid。不要第一项失败就结束，否则用户每次只能发现一个错误。

编辑页上的标题、费用与部门必须绑定到这个 WorkOrder 对象的对应成员，反馈才有可定位的控件。Nanoflow 的 Validation feedback 使用静态消息；可用范围和属性见官方反馈动作说明。

🛠️ 三、把“保存”和“业务提交”接清楚

保留原来的保存按钮，增加 ACT_WorkOrder_SaveAndSubmit Nanoflow 作为“保存并提交”按钮入口。参数也是当前编辑对象。

  1. 调用 VAL_WorkOrder_Form，false 就结束，保留页面与输入。
  2. true 时 Commit 当前 WorkOrder，让用户有权修改的草稿字段先保存。提交失败时显示“保存未完成，请检查错误后重试”，结束这一条路径。
  3. 保存成功后 Call microflow ACT_WorkOrder_Submit，传 WorkOrder。沿用原来的服务端查库、所有者核验和状态判断。
  4. 成功后重新打开工单详情核对状态；原 Microflow 如果已经处理页面跳转，就不再额外关闭一次页面。失败仍保留这张草稿，提示根据实际失败分支显示。

Nanoflow 中在 Commit 与 Call microflow 动作配置 Custom without rollback，分别连接失败提示和 End；不要把它当成服务端的 Custom with rollback。客户端错误不会自动撤销之前的对象改动，$latestError 在这里是字符串，详见 Nanoflow 错误处理。

这里有两个服务端操作边界。 保存草稿成功、业务提交失败时，草稿仍然保存着。提示应是“草稿已保存，提交未完成”，不能说“全部没保存”。服务端事务与回滚参见Microflow 错误处理。

为了区分正常拒绝与运行异常，可以让提交 Microflow 返回 Boolean：校验失败的正常出口返回 false，实际提交成功返回 true；原有其他调用处同步处理返回值。不要在 false 出口之后显示成功消息，也不要捕获异常后无条件返回 true。

如果用户等了很久，另一个窗口已提交该单，服务端应该拒绝再次提交并提示刷新。按钮禁用或加载提示只能减少重复点击，不能代替服务端检查，也不能解决并发竞争。

中途停靠： 先让空标题与负费用同时显示正确反馈，再继续调整页面。现在无需修改 Workflow。

🎨 四、让页面本身帮助用户理解

编辑页用两个明确区域：“报修内容”放 Title、Description、Department；“费用与进度”放 EstimatedCost 与只读 Status。标题上方有可见标签，说明文字不只写进 placeholder。

费用旁写“演示币种：元；超过 500 需主管审批”。Status 显示中文枚举标题，但保存的枚举值继续使用第 09—10 章的名称。不要把 AwaitingApproval 和 Submitted 都显示成“已提交”，否则读者无法区分等审批和等接单。

手机上让字段自然纵向排列，确认按钮与取消按钮的文案分开。取消返回列表；因为草稿已提前保存，文案可以写“返回，保留草稿”，不要承诺删除。

空列表至少说明一种原因与可行下一步：Requester 没有工单时显示“还没有报修记录，可以新建”；筛选为空时显示“当前条件无结果，可以清除筛选”。这两种情况不应都报“系统错误”。

🔎 五、用四次操作验收

操作 预期 去哪里核对
空格标题、费用 −1，点保存并提交 两处反馈，仍留在编辑页 字段下方、数据库仍是 Draft
标题完整、费用 500、部门已选 保存并进入待接单 状态 Submitted，无新审批
同样字段改成 501 进入待审批 AwaitingApproval 和一条流程实例
两窗口同时打开，先提交一个再操作旧窗口 旧窗口不能再次正常提交 服务端提示与流程实例数量

最后一次是顺序过期页面测试；真正同时发起的并发测试要另做，不能由它推断“绝不会重复”。用键盘 Tab 走完表单，确认错误反馈不依赖红色本身，且能读出字段名称。

✅ 检查点

  1. 为什么不直接把 Title 设为实体必填？
  2. 客户端检查通过后还需要检查身份吗？
  3. 草稿保存成功而提交失败，应该告诉用户什么？
  4. 匹配错误反馈需要哪两项？
查看答案
  1. 当前新建会先提交空草稿，实体必填会与这一策略冲突。完整性在业务提交时核验。
  2. 需要，服务端重新检查所有者、状态与业务字段。
  3. 草稿已保存，业务提交未完成；不能显示整体成功或整体回滚。
  4. 反馈指向的对象和成员，要与页面控件实际绑定一致。
