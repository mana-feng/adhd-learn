19 · 性能、队列与可靠重试

⏱ 阅读约 12 分钟 ｜ Studio Pro 11.12 LTS，动手时间另计

🎯 一句话

先测量瓶颈，再把需要等待的工作移入后台；后台任务必须容得下重复执行。 用户看到“已受理”，不能被写成“外部系统已完成”。

起点：第 12 章查询与第 14 章日志可用。本章先优化工单列表，再用一个不修改外部系统的查询任务练习队列。

🔎 一、先取得可以比较的基线

准备 100 张与 1000 张虚构工单两个数据规模，字段长度相近、角色一致。分别记录首次打开列表和刷新列表的时间，至少重复数次；记录环境、过滤条件与返回条数。

现象 可能原因 对照实验
返回条数越多越慢 大量传输或控件渲染 同条件只显示一页
每多一行就多一次查询 循环查询关联，即 N+1 批量取所需对象再关联
某个过滤始终很慢 查询条件与索引不匹配 查看查询并比较索引前后
页面等待外部接口 网络和对方处理耗时 单独测接口耗时

分页要在数据源侧限制范围，不是把全部工单取回客户端再隐藏。避免每行渲染时调用一个慢 Microflow；索引依据真实过滤和排序选择，增加索引也会增加写入成本。官方性能排查

🛠️ 二、把长操作建成可观察的对象

在 HelpdeskIntegration 建持久化 IntegrationJob：RequestKey String80、AssetCode String40、Status 枚举 Pending/Succeeded/NeedsReview、ResultText String无限制、CreatedAt/FinishedAt DateTime，以及 Job_Requester 到 System.User 的单值关联。

RequestKey 是业务请求标识，用户刷新时继续追踪同一次请求。它不等于“随便每次生成一个新 ID”；同一业务操作重试应继续用原来的键。

普通人只读自己任务的状态与结果，不能客户端写 Status、RequestKey、Job_Requester，也不能访问所有失败任务；管理员具有受控排查入口。

🛠️ 三、真正把调用送入 Task Queue

在模块中新增 Task queue AssetJobs，练习设较小并发度，先用 1 个工作线程观察。新建 SUB_AssetJob_Run，参数为持久化 IntegrationJob，返回 Nothing。

创建入口 ACT_AssetJob_Request：核验登录与输入，创建 Pending 对象，设置 RequestKey 和请求人并 Commit；再用 Call microflow 调用 SUB_AssetJob_Run，启用 Execute this Microflow in a Task Queue，并在 Select Task Queue 选择 AssetJobs。调用参数使用已提交的持久化对象，不传页面临时对象。

队列任务要等发起事务成功结束才会进入可执行队列。后台读取的是持久化数据，不能认为它会保留浏览器当时未提交的状态。Task Queue 文档

入口完成后打开任务状态页，文案“查询已受理”。后台重新取得任务并检查状态，Succeeded 则直接结束；否则用 AssetCode 查询练习服务，成功写 ResultText、Succeeded、FinishedAt 并 Commit。用户刷新状态页后才看到结果。

把第 12 章查询包装为明确结果或异常两种方式时要统一：如果查询把故障转成 Found=false，队列不会自动把它当执行异常。当前练习对这种结果写 NeedsReview，让管理员看见可处理的失败。

中途停靠： 能区分 Pending 与 Succeeded，并看到队列完成后页面更新，就完成后台主线。

🔁 四、重试必须保留不确定状态

练习入口固定只做 GET 查询；对 A503 写 NeedsReview，管理员恢复 A100 的测试任务后可从受控“重试”入口重新入队。重试前查状态与参数，记录操作者，不能由任意用户批量重跑任务。

平台支持失败重试，但只有抛出的失败才能触发相应机制；吞掉异常后正常结束可能被记录为成功。启用固定延迟或递增延迟前，按 11.12 所用调用方式检查重试设置，并给定次数上限。不要让循环无间隔重试占满工作线程。

如果以后改为“创建采购单”，请求已到对方、响应未回本地时会出现不确定结果。再次发请求要使用对方支持的同一幂等键，或先查询外部订单。只检查本地 Status 不能防住“外部已完成、本地提交失败”这条缝隙。

一个队列线程也不代表全系统永远无并发：可能有多个节点、其他队列、重复入口或管理员重试。数据库约束、业务幂等和外部去重共同决定边界。

⏰ 五、计划事件是定时触发器

需要每晚清理旧暂存行时，新增 Scheduled event 调用受控 Microflow；测试先选择短周期，记录运行时区和实际触发时间。事件只筛选已结束且超过保留期的数据，先日志预览，不把仍编辑中的上传或在途流程删掉。

计划事件并不保证某个业务副作用恰好发生一次。运行环境也可能限制计划事件，例如 Free App 的能力不同；本地可运行不等于云环境已启用。Scheduled Events 文档

✅ 六、验收性能与可靠性两件事

比较优化前后同一数据规模、同一角色的列表耗时，并确认权限筛选和行数未变。后台分别测试成功、503、重复请求、任务完成后再次重试，以及服务停止再恢复。

观察 Pending 积压、最老等待时间、NeedsReview 数量与处理耗时。只看队列线程还活着不能说明业务没有卡住；只看页面更快也不能说明结果已经产生。

✅ 检查点

  1. 客户端隐藏多余行等于分页优化吗？
  2. 入口成功能显示查询完成吗？
  3. 吞掉异常会自动触发队列失败重试吗？
  4. 单线程能代替幂等吗？
查看答案
  1. 不是，需要数据源限制范围，避免先取回全部数据。
  2. 不能，只能显示已受理，后台成功后才是完成。
  3. 未必，正常结束可能被视为成功，应明确故障状态或继续抛出。
  4. 不能，重复入口、其他节点和外部副作用仍可能造成重复。

走神救援

  • 性能先测同条件基线，再检查数据量、查询和等待。
