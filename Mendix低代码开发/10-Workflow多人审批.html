10 · Workflow：做一个真正的多人审批流程

⏱ 阅读约 20 分钟 ｜ 按准备、任务页、联调三个阶段完成

🎯 一句话

Workflow 保存流程实例和人工任务；工单作为上下文，把审批过程与业务数据连接起来。 “把 Status 改成已批准”本身不会替主管生成待办。

起点： Studio Pro 11.12 LTS；第 08 章的 Requester、Technician、Manager、Administrator 角色及独立账号；第 09 章的工单闭环。直接跳读者先核对 WorkOrder 字段、提交人和处理人关联、受保护的 Status，以及服务端提交动作。

本章的“多人”指提交人与主管交接工作。最小实现只有一个主管审批 User task；需要所有主管分别投票的会签，使用后面介绍的 Multi-user task，不把“多个人能看到同一待办”当成会签。

🧭 一、先看这次会发生的变化

原先合法草稿直接变成 Submitted。现在把“费用超过 500 元”的工单送给主管，批准后才进入待接单列表。

场景 本章预期行为
预计费用 300 元 直接 Submitted，不产生审批任务
预计费用恰好 500 元 直接 Submitted，因为规则是“大于 500”
预计费用 800 元 AwaitingApproval，主管得到审批待办
主管同意 任务完成，工单变成 Submitted，维修人员可接单
主管拒绝 任务完成，工单变成 Rejected，不允许接单

这里的 500 元是教程自定的演示阈值；币种沿用第 02 章的单一币种假设。先保持规则固定，跑通以后再考虑配置表、组织层级和授权额度。

看左侧旁路：低费用工单不启动 Workflow；只有中间的人工任务会等待主管。 这张图合并展示提交 Microflow 与审批 Workflow 的业务关系，不是让你把所有节点都放进同一种编辑器。

🧰 二、安装与 11.12 匹配的 Workflow Commons

保存当前项目版本。在 Marketplace 中选择 Workflow Commons 4.x 且最低 Studio Pro 要求不高于 11.12 的版本；同时记录准确模块版本。检查依赖的 Administration、Atlas Core、Atlas Web Content、Data Widgets、Nanoflow Commons，以及当前 Web 客户端兼容性。

在 App Settings > Workflows 中，将 User entity 设为 Administration.Account。为普通业务应用角色映射 WorkflowCommons.User；管理员映射 WorkflowCommons.Administrator，并按模块要求提供 Administration 的姓名读取权限。

给业务用户添加模块提供的 Task Inbox 导航入口，给管理员添加 Workflow Admin Center。在导入模块中搜索页面并选择实际文档，不凭中文菜单名创建一张同名空页面。列表没有数据时也要能正常打开。

11.12 与旧教程的关键区别： Workflow Commons 4.x 使用 View Entities；已结束任务由 System.WorkflowEndedUserTask 承载，通过 WorkflowCommons.WorkflowUserTaskView 统一查看。不要再为它接旧的 Workflow state change / User task state change 回调，4.x 不再需要那套设置。依据官方 Workflow Commons 安装与迁移说明。

本章是新建 11.12 学习应用，不是迁移生产流程。已有 10.x 项目应按官方迁移步骤单独处理历史任务，不可以仅替换模块包就认为历史数据已迁移。

🗃️ 三、把 WorkOrder 选为流程上下文

在 ENUM_WorkOrderStatus 增加 AwaitingApproval（待审批） 和 Rejected（已拒绝）。不要删除第 02 章已有值。第 08 章 Requester 的只读规则仍允许查看自己的这些记录，写规则仍限于 Draft。

右击 Helpdesk 模块，选择 Add workflow，命名 WF_WorkOrderApproval，Workflow context 选择持久化实体 Helpdesk.WorkOrder。新流程的 $WorkflowContext 就是启动时传入的那张工单。

对象或定义 负责什么
WF_WorkOrderApproval 定义 规定有哪些任务和分支
某次启动产生的 Workflow 实例 记录这一次审批执行到哪里
WorkOrder 上下文对象 保存标题、费用、提交人和业务状态
WorkflowUserTask 记录当前人工待办、目标用户与实际处理人

同一个流程定义可以有很多实例，不同实例通常对应不同工单。流程实例结束不等于工单已维修完成：主管同意后工单只是 Submitted，维修闭环仍由第 09 章处理。

👤 四、创建主管人工任务

从 Workflow Toolbox 添加 User task，接在 Start event 后，名称设为 ApproveCost，Caption 写“主管：审批维修费用”。在 Targeted users 中按下表设置。

属性 本章设置 检查点
Target User(s) 本例直接确定目标账号
Source Database 从配置的用户实体筛选
XPath constraint [System.UserRoles = '[%UserRole_Manager%]'] Manager 是第 08 章的应用角色 Name
Auto-assign when targeting results in one user 启用 仅匹配一人时自动分配
Outcomes Approve、Reject 分别对应同意与拒绝
Task name 审批维修费用 在任务列表中能辨认

令牌要用编辑器选择实际应用角色，不能误选同名模块角色。目标用户列表为空会导致流程失败；先确认主管账号存在并匹配条件。当前练习假设一个组织，所有 Manager 都可审批；按部门或金额授权时，需要增加对应模型和筛选规则。

目标用户不等于已经认领的处理人。 多名主管被匹配时，他们可能都有资格看到同一项任务；只有实际分配到的用户能够完成任务。本例是“其中一名主管处理”，不是“每名主管都要同意”。参见User task 的目标与分配。

🪟 五、生成一个能完成任务的页面

在 ApproveCost 的 Page 属性中新建页面，使用当前 Workflow Commons 提供的 User Task 模板，例如 User Task Extended，命名 WorkOrderApproval_Task。保留模板生成的任务容器和获取业务上下文的连接。

业务内容只读显示 Title、Description、EstimatedCost 和 Department。主管要批准的是提交时的金额，因此在 AwaitingApproval 状态不允许提交人继续改费用，也不让主管顺手修改费用后批准另一个数额。

核对“同意”“拒绝”两个按钮：它们应执行 Complete user task，分别对应 Approve、Reject。动作要作用在实际 System.WorkflowUserTask 对象上；WorkOrder Data view 仅用于展示业务内容，不能把工单对象传给任务完成动作。

如果模板外围采用 WorkflowUserTaskView，继续沿它提供的连接取活动任务，不要把视图实体强行改成旧版 UserTaskView，也不要删掉模板必要容器来让页面变短。

任务页由 Task Inbox 的打开任务动作进入，核对 Show user task page 的自动分配设置，或使用模块的认领操作。默认只有已分配用户能完成任务；手工新建一个普通 Show page 按钮可能绕过必要的任务打开逻辑。参见任务打开与完成事件。

🛑 任务页完成后可以停

保存并检查一致性错误。此时你已有流程定义、任务、目标用户与任务页，但还没有完成提交入口和结果接线。下一次从下面两节继续，不要把“图已画好”记为“审批已跑通”。

🔀 六、让两种任务结果更新业务数据

在 Approve 分支添加 Call microflow，选择新建的 SUB_WorkOrder_ApprovalAccepted；参数类型为 WorkOrder，将 $WorkflowContext 传入。它验证 Status 仍为 AwaitingApproval，通过后改为 Submitted 并显式 Commit，然后流程走到 End event。

Reject 分支同样调用 SUB_WorkOrder_ApprovalRejected，验证同一旧状态，改为 Rejected，Commit 后结束。拒绝也可以正常结束流程，并不意味着引擎执行失败。

这些是内部工作流动作，不作为用户直接调用的审批捷径。业务更新由受控内部动作执行，任务完成仍通过引擎的分配和授权机制；如果状态不符合预期，报告错误供管理员排查，不悄悄把任意状态覆盖成 Submitted。

需要写 WorkOrderLog 时标记为“流程结果更新”，不要把后台执行身份伪装为审批人。真实审批人的记录从 Workflow 任务历史核对；后续要汇入业务审计时，再明确传递和保存真实任务执行者。

▶ 七、从提交 Microflow 启动

回到 ACT_WorkOrder_Submit，保留第 08 章的身份、归属、Draft 状态和内容校验，把原先直接设为 Submitted 的成功路径改为按费用判断：

  1. EstimatedCost <= 500：仍设置 Submitted，写提交日志，Commit 后结束，不调用 Workflow。
  2. EstimatedCost > 500：先针对当前 WorkOrder 用 Retrieve workflows 检查是否已有本流程实例；本练习不做重提，已有实例则拒绝再次启动。
  3. 无实例时，设置 AwaitingApproval 并 Commit，再用 Call workflow 选择 WF_WorkOrderApproval，Context 传这张 WorkOrder。
  4. 让调用正常完成后提示“已发起审批”，随后到流程管理页核验实例状态。不要提示“审批成功”，因为主管尚未操作。

启动检查、状态更新和调用放在同一提交操作中，保持失败可见；不要吞掉启动异常后仍留下成功提示。引擎后续执行失败则可能在发起请求返回后出现，需要在管理页和日志中排查。

顺序重复提交会被 Draft 状态与已有实例检查拦住，但这些检查本身不是并发唯一性保证。两个请求同时启动的竞争、外部通知重试和补偿，仍属于上线前的专项验证范围。

🧪 八、按角色完成一轮联调

测试步骤 预期观察
小林提交 300 元工单 Submitted，主管无这张工单的审批任务
小林提交 500 元工单 同样直接待接单，验证阈值边界
小林提交 800 元工单 AwaitingApproval，生成一个审批实例
小周查看待接单列表 暂时看不到这张 800 元工单
小陈进入 Task Inbox 并打开任务 看见对应标题和 800 元费用
小陈选择 Approve 待办结束，工单变成 Submitted
小周重新检索并接单 状态变 InProgress，继续第 09 章闭环
另一张超额工单选择 Reject Rejected，不进入待接单列表
AwaitingApproval 工单再次尝试提交 拒绝；不应顺序生成第二个实例

“任务从待办消失”还不够，必须同时核对业务工单状态和任务历史。Mendix 11 的已结束任务与活动任务存储不同，从 Workflow Commons 的统一历史视图查看，不把活动任务表中找不到记录当成数据丢失。

🩹 九、卡住时按位置找原因

现象 优先核对
没有流程实例 是否真的调用 Call workflow；费用是否进入高费用分支
实例失败、主管没有待办 目标筛选是否匹配账号；上下文和服务端日志
待办存在、打开后没有工单内容 任务页上下文连接、WorkOrder 读取权限
按钮报不能完成任务 是否已分配给当前用户、按钮是否拿到实际活动任务
点击后工单状态没变 Outcome 分支是否接了更新 Microflow、更新是否失败
配了 Due date，却没有自动邮件 截止日期本身不是邮件提醒或超时自动批准

🧠 十、复杂审批在这个基础上怎样扩展

需要“主管同意后财务再同意”，把第二个 User task 接在同意路径上，再接最终业务更新；这是串行审批。需要“多人分别投票”，使用 Multi-user task 并定义完成条件、拒绝优先级和未响应处理；普通 User task 匹配多人不是会签。

人员经常进出团队时，11.12 还可以使用 Workflow group(s)；与创建任务时固定目标用户不同，组成员变动有其动态语义，需按实际组织规则选择。单人示例先跑通，再读多人任务和用户任务目标机制。

最后，修改流程定义时还要考虑已有实例停在哪里。练习可以用新测试工单重新发起；生产不能随意删历史实例消除冲突，应检查Workflow 版本与冲突处理。

✅ 检查点

  1. WorkflowContext 是流程定义、任务，还是业务工单？
  2. 主管同意后，工单应该是 Submitted 还是 Closed？
  3. 给普通按钮设置 Status=Submitted，为什么不能代替 Complete user task？
  4. 多名主管看见同一 User task，是否意味着每人都必须审批？
  5. 11.12 使用 Workflow Commons 4.x，还要配置旧状态变更回调吗？
查看答案
  1. 本例是持久化的 WorkOrder 对象，作为这次流程的业务上下文。
  2. Submitted，表示获准进入待接单阶段，维修工作还没有完成。
  3. 它没有通过任务分配和完成机制，不会让引擎沿任务结果继续执行。
  4. 不是。普通 User task 是由实际分配的用户完成；会签要单独定义多人任务规则。
  5. 不需要。4.x 的视图与任务历史机制已经改变，不能照搬旧接线。
