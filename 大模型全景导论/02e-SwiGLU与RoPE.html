02e · SwiGLU 与 RoPE

⏱ 80 分钟 ｜ ⭐⭐ 一处让 FFN 凭空多出一个矩阵，一处让上下文能撑到 100 万

🎯 一句话

这两处改动都不是「换个更好的公式」，而是给一个具体的死结解绑。 SwiGLU 让 FFN 能对不同的 token 走出不同的行为，代价是三个矩阵要塞进两个矩阵的预算里； RoPE 把位置从「加上去的一串数」改成「转过的一个角度」，于是「隔了几个词」变成了几何送的，不花一个参数。

🚪 接着上一章

上一章 02b 那两处改动（Pre-LN 和 RMSNorm）有个共同点：它们修的是「训练稳不稳、跑得快不快」，不改模型能做什么。 换回去，模型还是那个模型，只是更难训、更慢。

这一章的两处不一样：

   SwiGLU：同样的参数量，模型学到的东西不一样了
   RoPE  ：换掉它，模型的【上下文长度上限】就锁死了

🔑 两节彼此独立，可以只挑一处看。 想读懂 LLaMA 的 FFN 代码 → 第一到五节； 想搞清「上下文怎么从 2K 撑到 100 万」→ 直接跳第六节。

🧩 一、FFN 怎么突然多出了一个矩阵

先从一个你迟早会撞上的现象说起。翻开任意一份 LLaMA 系模型的前馈网络，是三个投影矩阵：

self.gate_proj = nn.Linear(hidden_size, intermediate_size, bias=False)
self.up_proj   = nn.Linear(hidden_size, intermediate_size, bias=False)
self.down_proj = nn.Linear(intermediate_size, hidden_size, bias=False)

而所有讲 Transformer 的材料里，FFN 都是两个——升维、激活、降维，一条路走到底：

$$\text{FFN}(x) = W_2 \cdot \text{ReLU}(W_1 x)$$

第 2 章讲过 FFN 的职责（「每个 token 单独深加工」、参数量的大头），但没打开它看里面。现在打开：里面就是两个矩阵，中间把维度放大 4 倍。

先把老的账算清楚，后面全靠它：

   W₁: d × 4d = 4d²      ← 升维
   W₂: 4d × d = 4d²      ← 降维
   ────────────────────
   合计 8d²              ⭐ 记住这个数，第四节要拿它算一笔账

于是问题很具体：多出来的那个矩阵干什么用？多一个矩阵，参数量不就白涨了吗？

第三、四节回答这两句。中间先补一格——在多出第三个矩阵之前，还发生过一次更小的改动。

🌊 二、为什么没人再用 ReLU 了

原始 Transformer 用 ReLU，GPT-2 / GPT-3 / BERT 换成 GELU，LLaMA 这一代的门控用 Swish（PyTorch 里叫 SiLU，同一个东西）。

三者差别只在负半轴。下面的数字是实跑的（PyTorch 2.13，F.relu / F.gelu / F.silu）：

输入 x ReLU GELU SiLU（Swish）
−2.0 0.0000 −0.0455 −0.2384
−0.1 0.0000 −0.0460 −0.0475
0.5 0.5000 0.3457 0.3112
2.0 2.0000 1.9545 1.7616

ReLU 在负半轴是一条死平线，GELU / SiLU 留了一点点。 那「一点点」为什么值钱：

   ReLU 在 x < 0 时输出是 0，【导数也是 0】
   → 神经元一旦被推到负区，拿到的梯度就是 0
   → 它再也不会被更新，等于永久死了 💀（这叫"死 ReLU"）

   GELU / SiLU 在负区输出很小但不是 0，导数也不是 0
   → 还有机会被拉回来；而且处处光滑可导，优化器走得更顺

⭐ 一句话记住区别：ReLU 是「大于 0 全放，小于 0 一刀切」，GELU 是「按这个值有多大，按概率放过一部分」——写成公式就是 $\text{GELU}(x) = x \cdot \Phi(x)$，$\Phi$ 是标准正态的累积分布函数，那个乘数就是"概率"。Swish 把 $\Phi$ 换成更便宜的 sigmoid：$\text{Swish}(x) = x \cdot \sigma(x)$。

⚠️ 代价：GELU 要算 erf（或 tanh 近似），比 ReLU 贵。FLOPs 上不算什么，但它是逐元素算子，和 RMSNorm 一样卡在显存带宽上——所以框架都会把它和相邻算子融进同一个 kernel。

（🔗 激活函数为什么必须非线性、不加激活为什么等于一层，在《ML 基础》第 7 章。）

🎚️ 三、多出来的那一路是干什么的

那三个矩阵不是「三层」，而是两路并行 + 一路收口。

先不看公式，想一个具体的画面：

   内容路算出 h 个数字，这是"我想往下传的东西"
   闸门路算出 h 个数字，每个都在 0 附近到 1 附近之间

   然后【一一对应地相乘】：
     第 37 个闸门 = 0.98 → 第 37 个内容几乎原样通过
     第 51 个闸门 = 0.02 → 第 51 个内容被掐掉了 ⭐

⭐ 关键在于闸门是算出来的，不是固定的。 同一个 FFN，喂进「猫」和喂进「因此」，闸门那一路给出的开合模式完全不同——相当于对每个 token 动态地选一组子通道。

这是纯加权和做不到的事。 老式 FFN 里每个输出通道拿到的是输入的加权和再过激活，本质是加法组合，权重训练完就固定、对所有 token 一视同仁。门控引入了乘法交互：两路输出相乘，其中一路可以按内容把另一路逐维度关掉。

写成公式这就是 GLU（Gated Linear Unit），闸门那一路的激活选成 Swish 就叫 SwiGLU：

$$\text{SwiGLU-FFN}(x) = W_{\text{down}} \Big( \text{Swish}(W_{\text{gate}}\,x) \odot (W_{\text{up}}\,x) \Big)$$

（$\odot$ 是逐元素相乘。再强调一次：$W_{\text{up}}$ 那一路没有激活函数。）

⚠️ 一个常见的记混点：SwiGLU 不是一个激活函数，它是一整个 FFN 的结构。 「Swish」才是激活函数。你没法像换 nn.ReLU() 那样把 SwiGLU 换进去——它改的是矩阵的个数。

⚖️ 四、多一个矩阵，参数量不就白涨了吗

这是全章最该想明白的一步，也是面试问「2/3 是怎么来的」时想听的答案。

先算笔账，看看什么都不改会发生什么：

   三个矩阵的中间维度还用 4d 的话：
     W_gate: d × 4d ， W_up: d × 4d ， W_down: 4d × d
     合计 3 × 4d² = 12d²        ← 老式是 8d²，多了整整 50% 💀

   💀 那这个对比就【作弊】了：
      它效果好，可能只是因为它更大，而不是因为门控有用

要让它公平，就得把中间维度调小到参数量持平。设中间维度为 $h$：

$$3 \times d \times h = 8d^2 \quad \Longrightarrow \quad h = \frac{8d}{3} = \frac{2}{3} \times 4d$$

⭐ 这就是那个 2/3 的全部来历：不是什么神秘常数，就是「三个矩阵要装进两个矩阵的预算里」。

LLaMA-7B 的 11008 是怎么来的

   d      = 4096
   4d     = 16384
   × 2/3  = 10922.67          ← 不是整数，GPU 不喜欢
   向上对齐到 256 的倍数 → 11008   ⭐ 这就是 LLaMA-7B config 里的 intermediate_size

⚠️ 为什么要对齐：GPU 的矩阵乘单元（tensor core）按固定块大小吃数据，维度不是 128/256 的倍数时会补零空转，利用率掉一截。

下面这段单独复制到空文件就能跑（PyTorch 2.13 CPU 实跑）：

import torch
import torch.nn as nn
import torch.nn.functional as F

class SwiGLU(nn.Module):
    """LLaMA 式 FFN：三个矩阵，不是两个。"""
    def __init__(self, dim: int, hidden: int):
        super().__init__()
        self.w_gate = nn.Linear(dim, hidden, bias=False)   # ⭐ 闸门那一路
        self.w_up   = nn.Linear(dim, hidden, bias=False)   # ⭐ 内容那一路（无激活）
        self.w_down = nn.Linear(hidden, dim, bias=False)

    def forward(self, x):
        return self.w_down(F.silu(self.w_gate(x)) * self.w_up(x))   # ⭐ 逐元素相乘 = 门控

def llama_hidden(dim: int, multiple_of: int = 256) -> int:
    h = int(2 * (4 * dim) / 3)                                   # ⭐ 4d 先乘 2/3
    return multiple_of * ((h + multiple_of - 1) // multiple_of)   # 再向上对齐

print("intermediate_size =", llama_hidden(4096))

ffn = SwiGLU(4096, llama_hidden(4096))
p_new = sum(p.numel() for p in ffn.parameters())
p_old = 2 * 4096 * (4 * 4096)
print(f"SwiGLU {p_new/1e6:.1f}M ｜ 老式 {p_old/1e6:.1f}M ｜ 比值 {p_new/p_old:.3f}")
print("形状不变：", ffn(torch.randn(2, 5, 4096)).shape)

实跑输出：

intermediate_size = 11008
SwiGLU 135.3M ｜ 老式 134.2M ｜ 比值 1.008
形状不变： torch.Size([2, 5, 4096])

⭐ 比值 1.008——只多 0.8%，那点零头全部来自「向上对齐到 11008」。这就是「公平比较」四个字的具体含义。

🪞 五、诚实的部分：它到底为什么更好

「怎么做」讲完了。「为什么这样更好」——诚实的答案是：没人说得清。

提出这个改动的论文（Noam Shazeer, GLU Variants Improve Transformer, 2020）在做完一堆同参数量的对照实验、确认 SwiGLU / GeGLU 确实更好之后，结尾写了一句圈内很出名的话，大意是：我们对这些架构为什么 work 不提供解释，把它的成功归于神的恩赐。

⭐ 这句话值得记住，不是因为它幽默，而是因为它诚实。 深度学习里有相当一部分架构选择就是这样：大量对照实验证明它好，但没有令人满意的理论解释。 正确的态度是「知道它在同参数量下经过了公平比较」，而不是硬编一个说得通的故事—— 你在网上看到的那些「因为门控增强了表达能力所以……」，大多是事后附会。

⚠️ 上一节那个「乘法交互」的说法也要这样看待：它是一个能说通的直觉，不是被证明的机制。它解释了「为什么门控可能有用」，没解释「为什么实测就是好这么多」。

代价那一栏必须一起看：

代价 说明
多一次矩阵乘 三次 GEMM 而不是两次。参数量持平，但 kernel 启动和访存次数都变多
维度不好对齐 $8d/3$ 基本不会是漂亮的数，必须手动向上取整到 128/256 的倍数（11008 就是这么来的）
训练峰值显存变高 要为 gate 和 up 两路各存一份中间激活给反向传播用。🔗 这属于「激活显存」这一类问题，《AI基础设施》第 9 章有梯度检查点等七件武器

🛑 读到这里可以停 —— SwiGLU 讲完了（约 28 分钟）。 你已经拿到：三个矩阵是「两路并行 + 一路收口」、闸门是算出来的（乘法交互）、2/3 来自「三个矩阵装进两个矩阵的预算」、11008 的完整算法，以及论文自己承认解释不了它为什么更好。 后半章讲 RoPE：位置为什么改成「转角度」· 相对位置怎么自己冒出来 · 转速为什么每个平面都不同 · 长上下文外推到底卡在哪。 这一节可以独立读，回来直接从下一节接着看就行。

🌀 六、上下文从 2K 撑到 100 万，靠的是什么

第二处改动。先看一组你在模型卡上天天见的数字：

   BERT (2018)     ：512
   GPT-3 (2020)    ：2048
   LLaMA-2 (2023)  ：4096
   现在的主流       ：128K，长文版本 100 万 ⭐

这条曲线的陡峭程度，不是「显卡变好了」能解释的。 显存和算力这几年涨了大约一个量级，上下文涨了三个量级。中间那两个量级，一大半来自位置编码换了一种做法。（另一半在注意力的算法和显存布局：🔗 《AI基础设施》第 8 章 FlashAttention。）

旧做法：把位置「加」进去

原始 Transformer 算一堆不同频率的 sin/cos，加到输入 embedding 上，只在第 0 层加一次。GPT-2 换成可学习的位置向量，做法一样，也是加在输入。

两个毛病，第二个是致命的：

   毛病一：加法会被稀释
     位置信息和语义信息挤进【同一组数字】里，往上传几十层、
     经过几十次注意力混合和 FFN 变换，还剩多少是位置？
     没人说得清 —— 它从来没有被单独保护过

   毛病二：换长度就废 💀
     可学习位置编码：训练时只见过 0~511 号位置
       → 第 512 号位置的向量【压根不存在】，不是效果差，是没有这个东西
     正弦位置编码：理论上能外推，实际一超出训练长度就崩

⭐ 毛病二决定了上限：在这套做法下，「支持多长上下文」是训练时就写死的，事后加不了。

🧭 七、先别看公式：位置是一根指针

RoPE 的核心一句话是：把位置编成「转过的角度」，而不是「加上去的向量」。 要读懂它只需要两个几何概念——都很简单，但没人挑明的话，读公式时一定会卡住。

「平面」是什么：$q$ 是一串数字，比如 128 个。把它们从头两两配对，第 0 和第 1 一对、第 2 和第 3 一对……一共 64 对。每一对就是一张纸上的一个点：一个数当横坐标，一个数当纵坐标。这张纸就是数学里说的「二维平面」。于是 128 维的向量被看成 64 个平面上的 64 个点。

「旋转」是什么：把这个点绕原点转一个角度。转的时候长度不变，只是方向变了——就像时钟的指针，长度永远一样，只有指向在变。

⚠️ 它作用在哪里，是它和旧方案最大的不同：

   旧方案：位置向量【加】在第 0 层的输入 embedding 上，只加一次
   RoPE ：位置角度【转】在【每一层】注意力的 Q 和 K 上 ⭐

每层都转一次，所以不会被深层稀释——毛病一当场解决。 而 V 不转：V 是要被加权取回来的内容，给它加位置信息没有意义；打分的是 Q·K，位置只需要影响打分。

🔁 八、为什么「隔了几个」自己就冒出来了

这是 RoPE 最漂亮的地方，也是面试最爱问的一句。先看图，再看公式。

图看懂了，公式就只剩一行：

   把 q 转 m·θ，把 k 转 n·θ，然后算内积

   内积 = |q| · |k| · cos( 原来的夹角 + (m − n)·θ )
                                        ↑
             ⭐ m 和 n 只以【差】的形式出现，绝对位置消失了

长度那两项为什么不受影响：旋转不改变长度（上一节那句「指针长度始终不变」就是为这里准备的）。所以旋转之后 $|q|$、$|k|$ 还是原值，位置只从 cos 那一项进来。

🔑 这就是那句标准答案的完整含义： RoPE 用绝对位置的方式实现（每个 token 独立地转一个只跟自己位置有关的角度，不需要知道别人在哪）， 却得到相对位置的效果（注意力分数只依赖两者之差）。 而且不用像 T5 那样为每个相对距离额外学一张偏置表——相对性是几何送的，不花参数。

别信它，自己跑一遍

下面这段单独复制到空文件就能跑。它把同一对 $q$、$k$ 放在三组不同的绝对位置上，但位置差都是 3：

import torch

def build_rope_cache(seq_len: int, head_dim: int, base: float = 10000.0):
    # ⭐ θ_i = base^(−2i/d)：i 越大转得越慢。head_dim/2 个平面，每个一个转速
    inv_freq = 1.0 / (base ** (torch.arange(0, head_dim, 2).float() / head_dim))
    angles = torch.outer(torch.arange(seq_len).float(), inv_freq)   # (seq_len, d/2)
    return angles.cos(), angles.sin()

def apply_rope(x, cos, sin):
    """x: (batch, heads, seq, head_dim)。两两配对，在每个平面上转一下。"""
    x1, x2 = x[..., 0::2], x[..., 1::2]
    cos, sin = cos[None, None], sin[None, None]
    out1 = x1 * cos - x2 * sin                   # ⭐ 就是二维旋转矩阵，没有别的
    out2 = x1 * sin + x2 * cos
    return torch.stack((out1, out2), dim=-1).flatten(-2)

cos, sin = build_rope_cache(seq_len=64, head_dim=16)
torch.manual_seed(0)
qv, kv = torch.randn(16), torch.randn(16)        # 同一对 q/k，只换绝对位置

def score(m, n):
    qm = apply_rope(qv.view(1, 1, 1, 16), cos[m:m+1], sin[m:m+1])
    kn = apply_rope(kv.view(1, 1, 1, 16), cos[n:n+1], sin[n:n+1])
    return (qm * kn).sum().item()

for m, n in [(2, 5), (12, 15), (40, 43), (2, 6)]:
    print(f"位置 ({m:>2},{n:>2})　差 {n-m} 　→ 分数 {score(m, n):.6f}")

实跑输出：

位置 ( 2, 5)　差 3 　→ 分数 -3.160643
位置 (12,15)　差 3 　→ 分数 -3.160645
位置 (40,43)　差 3 　→ 分数 -3.160644
位置 ( 2, 6)　差 4 　→ 分数 -1.315803

⭐ 前三行的差异在小数点后第 6 位，那是 float32 的舍入误差。 位置差是 3 就是同一个分数，差一变成 4 分数立刻变了。旋转矩阵那四行代码，就是全部的机制。

⚠️ 一个真实的坑：上面用的是「相邻两个配对」（0::2 和 1::2），而 HuggingFace 那套实现用「前半段和后半段配对」，因为那样的张量操作更快。两种配对方式不通用，权重不能混用——这是加载别人权重时一类经典的、不报错但输出乱码的故障。

🛑 第二个歇脚处 —— RoPE 的核心机制讲完了（约 44 分钟）。 你已经拿到：位置＝角度、只转每层的 Q 和 K（V 不转）、相对位置是几何送的（内积只剩 (m−n)θ）。 剩下的是「为什么能撑长」：转速为什么每个平面不同 · 外推到底卡在哪一头 · PI/NTK/YaRN 动的是什么。 回来的时候不用重读，直接从下一节接着看就行。

⏰ 九、为什么每个平面转速都不一样

如果所有平面都转同一个 θ，RoPE 就废了：转满一圈就绕回来，位置 0 和位置「一圈」长得一模一样。所以每个平面有自己的转速：

$$\theta_i = \text{base}^{-2i/d}, \qquad \text{base 通常取 } 10000$$

💡 一个好用的类比：钟表。

   秒针（高频，i 小）：转得快，能分辨"差了几秒"，但转一圈就绕回来 → 分不清远距离
   时针（低频，i 大）：转得慢，一天才走半圈，能区分"上午还是下午" → 但分不清秒

   ⭐ 一起看，才能唯一确定一个时刻

RoPE 就是这样：高频那些平面负责精细的邻近关系，低频那些负责粗糙的长距离关系，合起来才唯一地标出一个位置。

这个类比可以量化。 下面这段算的是「每个平面转满一圈要跨多少个 token」：

import math
import torch

head_dim, base, train_len = 128, 10000.0, 4096          # LLaMA-2 的头维度就是 128
inv_freq = 1.0 / (base ** (torch.arange(0, head_dim, 2).float() / head_dim))

print(f"一共 {head_dim // 2} 个平面。i 越大转得越慢：")
for i in (0, 32, 48, 63):
    theta = inv_freq[i].item()
    lam = 2 * math.pi / theta                   # ⭐ 转满一圈要跨多少个位置
    print(f"  平面 {i:>2}：转一圈要 {lam:>9.1f} 个位置 → 4096 个位置里转了 "
          f"{train_len / lam:>8.3f} 圈")

实跑输出：

一共 64 个平面。i 越大转得越慢：
  平面  0：转一圈要       6.3 个位置 → 4096 个位置里转了  651.899 圈
  平面 32：转一圈要     628.3 个位置 → 4096 个位置里转了    6.519 圈
  平面 48：转一圈要    6283.2 个位置 → 4096 个位置里转了    0.652 圈
  平面 63：转一圈要   54410.1 个位置 → 4096 个位置里转了    0.075 圈

⭐ 看最后一行：最慢的那个平面，在整个 4096 的训练长度里只转了 0.075 圈（27 度）——它连一圈都没走完。这个数字是下一节的全部关键。

🧯 十、训练时只见过 4096，喂进 32768 会怎样

RoPE 不是天生就能外推。（「外推」= 拿比训练时更长的输入去跑一个已经训好的模型。）答案是输出崩坏，但原因和大多数人第一反应想的不一样。

   最慢的平面 63：
     训练走到 4096，它才转了 27 度 —— 模型只见过 0°~27° 这一小段
     喂进 32768，它转到 217 度 💀 —— 训练时【从没出现过的角度】

   最快的平面 0：
     训练时已经转了 651.9 圈，0°~360° 每个角度都见过无数遍
     → 单看它，任何位置都是"见过的角度" ⭐

⭐ 所以卡住外推的是【低频】那一头，不是高频。 这个方向搞反了，下面三个方法为什么那么设计就全讲不通。

（严格说高频也有一份责任：所有平面的角度组合在一起才唯一标定一个位置，而位置 20000 的那个组合是全新的。但可以被针对性修复的病灶，是那些连一圈都没转完的低频平面。）

三种解法动的是同一个旋钮：每个频率的指针该转慢多少。区别只在调得均不均匀。

方法 做法 直觉 代价
PI（位置插值） 把位置索引统一除以 s（比如 8） 所有指针一律转慢 8 倍，32768 个位置被压回 4096 的角度范围内，全落在见过的区间 一刀切：高频本来不用管也被压慢了 → 相邻位置的角度差变小，精细分辨率变差
NTK-aware 不均匀缩放：高频几乎不动、低频缩得多（等价于把 base 从 10000 调大） 「高频本来就能外推，别动它；低频没转完一圈，缩它」 比 PI 温和得多，但仍需少量微调才最优
YaRN NTK 的精细版：按「训练长度内转了几圈」把平面分成三档区别对待，同时调低注意力温度 上一节那张实跑表就是它的分档依据 实现最复杂，效果最好

⭐ 实践里最简单粗暴的一招：把 rope_theta 从 10000 改成 1000000，再在长数据上继续训一小段。用上一节的口径就能说清它为什么管用：base 这么一改，最慢那个平面转一圈要跨的位置数从 54410 涨到约 506 万——所有指针都转慢了，同样多的位置被压进更小的角度范围。本质就是 NTK 的思路，只是不做分频段处理。LLaMA 3、Qwen 的长文版本都做了这件事。

⚠️ 别漏掉「继续训一小段」：改 base 只是把角度挪进了更安全的范围，模型仍然没在那个范围上训练过。纯改配置不续训，效果通常会掉。

🔗 第 3 章问的「上下文窗口是怎么撑到 100 万的」，位置编码这一侧的答案就在这里；而那一章同时提醒你另外半句：窗口撑大了不等于有效——大海捞针能过，不代表长文推理能过（「中间迷失」）。

🧰 十一、看 config 时补两句

上一章 02b 第二节那张 config.json 速查表里，intermediate_size、rope_theta、rope_scaling 三行指向的就是本章。读完这一章，那三行补两个判据：

⚠️ 「比值 ≈ 2.67 就是 SwiGLU」有反例，别当铁律。 2/3 只是最初那一版的取法，后来的模型经常按自己的训练预算另定这个数（LLaMA 3 / Mistral 这一代把 4096 配到了 14336，比值 3.5）。⭐ 可靠的判据是看权重名：出现 gate_proj（或同时出现 w1 和 w3 两个升维矩阵）就是 GLU 家族；只有一个升维矩阵才是老式两矩阵 FFN。

⭐ rope_theta 是一条时间线索：等于 10000 多半是 2023 年那一代的原始配置；是 500000 或 1000000，说明这个模型专门为长上下文调过，而且大概率还在长数据上续训过——没续训的话那个数字是白改的。

✅ 检查点

  1. LLaMA 的 FFN 里那三个矩阵分别叫什么、各自干什么？哪一路没有激活函数？
  2. ReLU 的「死神经元」具体是怎么发生的？GELU / SiLU 靠什么避开它？
  3. 门控引入了什么「纯加权和」做不到的东西？为什么说「闸门是算出来的」这一点才是关键？
  4. 中间维度为什么要乘 2/3？不乘的话参数量变成多少，为什么那样的对比不公平？LLaMA-7B 的 intermediate_size 是多少，从 4096 出发完整算一遍。
  5. SwiGLU 到底为什么效果更好？提出它的论文怎么说的？
  6. RoPE 作用在哪些张量上、在第几层？V 为什么不转？
  7. 「相对位置自动出现」是怎么回事？为什么内积里的 $|q|$、$|k|$ 两项不受位置影响？
  8. 一共有多少个「平面」？为什么每个平面的转速要不一样？用钟表类比说一遍。
  9. 训练长度 4096、直接喂 32768 会崩，卡住的是高频平面还是低频平面？用「转了几圈」这个数字说明。
  10. PI / NTK-aware / YaRN 动的是同一个旋钮，是什么？实践里最简单的一招是什么，为什么不能只改配置不续训？
👀 答案
  1. gate_proj（闸门路）、up_proj（内容路）、down_proj（降维收口）。前两个都是 d → h 并行走，输出逐元素相乘之后才进 down_proj。⭐ up_proj 那一路没有激活函数，激活（SiLU）只加在 gate_proj 那一路上。
  2. ReLU 在 x < 0 时输出是 0、导数也是 0；神经元一旦被推到负区，梯度就是 0，再也不会被更新。GELU / SiLU 在负区输出很小但不为 0，导数也不为 0（实测 GELU(−0.1) = −0.0460、SiLU(−0.1) = −0.0475），还有机会被拉回来，而且处处光滑可导。
  3. 乘法交互。老式 FFN 每个输出通道拿到的是输入的加权和再过激活，是加法组合，权重训练完就固定、对所有 token 一视同仁。⭐ 关键在于闸门是从当前输入算出来的：喂「猫」和喂「因此」，开合模式完全不同——相当于对每个 token 动态选一组子通道，闸门≈0 的通道直接被掐掉。
  4. 因为矩阵从两个变成了三个：中间维度还用 4d 就是 3 × 4d² = 12d²，比老式的 8d² 多 50%，那它效果好可能只是因为它更大。令 3 × d × h = 8d² 得 h = 8d/3。LLaMA-7B：4096 → 16384 → ×2/3 = 10922.67 → 向上对齐到 256 的倍数 = 11008（对齐是因为 tensor core 按固定块吃数据，不对齐会补零空转）。实跑核对：135.3M vs 134.2M，比值 1.008。
  5. 没人说得清。 提出它的论文（Shazeer 2020）做完一堆同参数量对照实验后，结尾说不对这些架构为什么 work 提供解释，把成功归于神的恩赐。⚠️「乘法交互」只是能说通的直觉，不是被证明的机制。
  6. 作用在每一层注意力的 Q 和 K 上（旧方案只加在第 0 层输入 embedding 上，所以会被深层稀释）。V 不转：V 是要被加权取回来的内容，位置只需要影响打分，而打分的是 Q·K。
  7. q 转 m·θ、k 转 n·θ 之后，二维内积 = |q|·|k|·cos(原夹角 + (m−n)θ)——m 和 n 只以「差」的形式出现，绝对位置抵消了。|q|、|k| 不受影响是因为旋转不改变向量长度。⭐ 这个相对性是几何送的，不像 T5 那样要额外学一张相对距离偏置表。实跑可验：位置差同为 3 的 (2,5)/(12,15)/(40,43) 分数都是 −3.16064（差别只在第 6 位小数，是 float32 舍入），差变成 4 时是 −1.3158。
  8. d/2 个（head_dim=128 → 64 个平面）。转速都一样的话转满一圈就绕回来，远处的位置会和近处撞车。θᵢ = base^(−2i/d)。钟表类比：秒针（高频、i 小）能分辨"差了几秒"但一圈就绕回来；时针（低频、i 大）能区分上午下午但分不清秒。高频管精细的邻近关系，低频管粗糙的长距离关系，合起来才唯一确定一个位置。
  9. ⭐ 卡住的是低频那一头。 实跑（base=10000、head_dim=128）：最慢的平面 63 转一圈要 54410 个位置，4096 内只转了 0.075 圈＝27 度；喂到 32768 它转到 217 度，是训练时从没出现过的角度。而平面 0 在 4096 内已转了 651.9 圈，每个角度都熟。（高频也有一份责任——所有平面的角度组合是全新的——但可修复的病灶在低频。）
  10. 都在动「每个频率的指针该转慢多少」。PI 一刀切转慢 s 倍，代价是高频本来不用管也被压慢、精细分辨率变差；NTK-aware 高频几乎不动、低频缩得多（等价于调大 base）；YaRN 按「转了几圈」分三档，还调低注意力温度。最简单的一招是把 rope_theta 从 10000 改成 1000000——最慢平面一圈从 54410 涨到约 506 万。⚠️ 必须在长数据上续训一小段：改 base 只把角度挪进了更安全的范围，模型仍然没在那个范围上训练过。

🛑 可以停在这里

⚡ 走神救援

上一章那两处只管「训练稳不稳」，这两处改的是模型能做什么。③FFN → SwiGLU：LLaMA 的 FFN 是 gate_proj / up_proj / down_proj 三个矩阵，老式只有两个（升到 4d 再降回来，合计 8d²）。中间先有一次小改动 ReLU → GELU/SiLU：ReLU 在负区输出 0、导数也是 0，神经元被推进去就永久死掉；实测 GELU(−0.1)=−0.0460、SiLU(−0.1)=−0.0475，留一点就能被拉回来。三个矩阵不是三层，是两路并行 + 一路收口：闸门路过 SiLU、内容路不过激活，两路逐元素相乘。⭐ 门控带来乘法交互——老式 FFN 是加法组合、权重对所有 token 固定，而闸门是从当前输入算出来的，闸门≈0 的通道直接被掐掉，相当于每个 token 动态选一组子通道。⭐2/3 的来历就是「三个矩阵要装进两个矩阵的预算里」：还用 4d 就是 3×4d²=12d²，比 8d² 多 50%，对比就作弊了；令 3×d×h=8d² 得 h=8d/3。LLaMA-7B：4096 → 16384 → ×2/3 = 10922.67 → 向上对齐 256 得 11008，实跑 135.3M vs 134.2M，比值 1.008。⚠️ 为什么更好？论文自己说给不出解释，把成功归于神的恩赐——「乘法交互」只是直觉，不是被证明的机制。④绝对位置 → RoPE：旧方案把位置加在第 0 层输入上，毛病是往上传几十层被稀释、以及换长度就废（第 512 号位置的向量压根不存在）。RoPE 把 d 个数字两两配对成 d/2 个二维平面（128 维 → 64 个平面），位置 m 让每个点转 m·θᵢ，⭐只作用在每一层的 Q 和 K 上，V 不转。⭐相对位置自动出现：内积 = |q||k|·cos(原夹角 + (m−n)θ)，m、n 只以差的形式出现；|q|、|k| 不受影响是因为旋转不改长度。实跑验证：位置差都是 3 的 (2,5)/(12,15)/(40,43) 分数都是 −3.16064，差变成 4 就是 −1.3158。⚠️ 配对方式有两种（相邻 vs 前后半段），不通用，权重混用会输出乱码。θᵢ = base^(−2i/d) 让每个平面转速不同，像钟表的秒针和时针：高频管精细邻近、低频管粗糙长距。💀 外推为什么崩——卡住的是【低频】不是高频：最慢的平面 63 转一圈要 54410 个位置，4096 内只转了 0.075 圈＝27 度，喂到 32768 转到 217 度，是从没见过的角度；而平面 0 在 4096 内已转了 651.9 圈。PI / NTK / YaRN 动的是同一个旋钮——每个频率该转慢多少：PI 一刀切（高频精度陪葬）、NTK 高频少动低频多缩（等价于调大 base）、YaRN 按转圈数分三档并调低注意力温度。⭐ 最简单的一招是把 rope_theta 从 10000 改成 1000000（最慢平面一圈涨到约 506 万），⚠️但必须在长数据上续训一小段。看 config：⚠️「比值 ≈2.67 就是 SwiGLU」有反例（LLaMA 3 / Mistral 是 4096→14336，比值 3.5），⭐可靠判据是权重名里有没有 gate_proj。
