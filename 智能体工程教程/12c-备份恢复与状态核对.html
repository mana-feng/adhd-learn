12c｜备份恢复与状态核对：旧数据库能打开，还能直接用吗？

⏱ 阅读约 28 分钟 · 动手实践另计

本章保留教学代码、路径说明与历史验证结论；完整实验工程和运行记录未随本站及公开仓库分发。命令用于说明调用方式，复现需自行准备对应实现、数据与环境。

一句话：先取一致备份，再恢复到全新隔离副本，最后核对业务状态；每一步通过，都不自动产生上线许可。

你已在 12b：持久化审批与故障恢复 看过审批记录如何跨重启保留。现在考虑另一个问题：今天撤销了一个账号，晚上却恢复到昨天的数据库。数据文件可以完整打开，但昨天有效的 token、读者名单和审批可能一起回来。

本章用原创语料与标准库观察这个风险。数据库在临时目录创建，输出只有脱敏 JSON、摘要和错误类别；不用你的工作数据库练习。

停止点：读完第三节，能解释为什么不能只复制主文件，就可暂停。完整跑完后，能解释一个撤权漂移表，就是本章的验收。

走神救援：回来时只找这三个动词：备份、隔离、核对。文件完好对应第一个问题；权限是否过期对应第三个问题。两种结论分别记录。

1. 先分清三个成功条件

备份确认已提交快照，隔离恢复验证新文件能打开，状态核对报告当前业务差异。记录结论时标明完成了哪一步。

阶段 本章实际检查 通过后的含义
在线备份 backup API、完整性、外键、目标字节摘要 快照可用于后续检查
隔离恢复 新文件、摘要、schema、重新打开 inspection_only
全表核对 schema、行数、行多重集合摘要 一致快照，或 quarantined

文档数量可能没变，读者名单却变了。数量通过、权限失败应分别记录；可读、授权有效、引用当前版本各需证据。

输出始终写着 service_activation 为 false，明确区分检查与启用。线上切流、凭证来源及外部副作用等证据，要另行验证。

检查点 1｜文件完好时，可以直接恢复服务吗？

不能。先建立隔离副本，再核对权限、版本与审批等状态。当前实验没有恢复服务入口。“备份有效”与“允许上线”属于不同判断。

2. WAL 里的已提交内容也属于数据库

SQLite 的 WAL 模式会把一些已提交修改放在旁边的日志中，之后才通过 checkpoint 合并到主文件。看见一个 .sqlite 文件，并不等于已经拿到当时的全部已提交内容。如果在线直接复制它，副本可能缺少刚写入的记录。

本章调用 SQLite 的在线 backup API，源连接使用 mode=ro。Python 的 Connection.backup 文档 和 SQLite 在线备份说明 提供接口依据；本地实验另外记录实际 Python、SQLite 版本。

demo 保持真实写连接打开，关闭自动 checkpoint，插入第一条并提交，插入第二条不提交。另一只读连接执行 backup，副本应有第一条、没有第二条。检查时写连接仍在。

提交表示业务已接受记录；未提交修改仍可能回滚。实验结束会回滚第二条并关闭连接，清理临时夹具。

检查点 2｜未提交记录为什么不该出现在备份里？

它还没有进入其他连接可见的已提交快照。这里检查的是事务可见性，而不是把源目录的每个字节都搬过去。WAL 大于零只说明日志存在，还要验证恢复后的行内容符合这两个预期。

3. 备份清单要引用目标的真实字节

backup_database 的 output 必须是不存在的新目录。已有目录、与源相同的路径、缺失源和目录源都会拒绝。这样不会在上次结果里混入一次新实验，也不会把数据库本身当输出目录写坏。

复制后，仅将新目标改为普通日志模式，检查 integrity_check 与 foreign_key_check。源不执行 checkpoint 或改业务表；结构与外键都通过才保存成功清单。

manifest 记录目标文件 hash、schema hash、页数、字节数、结束时间与运行版本。这里的文件 hash 来自 backup.sqlite 的实际字节，不能换成 source.sqlite 的 hash，因为主文件可能尚未包含 WAL 中已提交的数据。

读取清单时检查字段、类型、重复键、嵌套解析失败和固定文件名。清单不能以绝对路径或 ../ 引导读取别处数据库。校验或输出 I/O 失败只返回固定错误类别，不记录凭证、用户路径或完整异常字符串。

小暂停：找报告的 manifest，确认它记录备份文件。缺少成功清单时，不要凭文件名判定可用。

检查点 3｜hash 一致能证明备份来自可信管理员吗？

不能。hash 能发现相对这份清单的字节变化，但清单没有签名。能同时替换文件和清单的人可以重新计算 hash；来源鉴别与存储权限仍需独立控制。

4. 恢复目标必须是全新文件

restore_for_inspection 选择“现有父目录中的全新文件”作为目标契约。目标文件或目录已经存在，就拒绝；硬链接、相同路径与旁边遗留的写日志也不能成为覆盖旧数据的理由。先验证备份，再独占创建目标，不需要你确认“覆盖继续”。

恢复后重新打开该文件，再查完整性、schema 与行摘要。返回 inspection_only，数据库暂时留在隔离检查范围内。这个函数不修改配置、不切换服务连接，也不调用 workflow.execute。即使备份里有待审批任务，恢复也只保留记录。

为什么仍要检查 pending？用户可能把“恢复任务”误解为“继续所有任务”。旧副本有 pending，只能说明当时任务还在等待；它没有代替当前审批人作决定。demo 会核对 runs 中状态仍为 pending，tickets 数量仍为零。

恢复本地记录不能证明远端效果没发生。真实外部工单仍需按幂等键与查询契约核对，SQLite 副本不能替它回滚。

检查点 4｜旧副本的 approved 能当成当前批准吗？

不能自动沿用。动作内容、批准期限、账号权限和当前取消记录都可能变了。隔离恢复保留历史记录，状态核对报告差异；本章没有自动续期或重放执行的代码。

5. 为什么核对全部用户表

compare_state 分别开启只读事务，为两端各固定一个读取快照。随后从 SQLite 实际 schema 枚举全部用户表，比较表定义、索引定义、行数和行摘要。表名来自数据库并安全引用，不把外部字符串直接拼成 SQL 标识符。

documents 带着读者与删除状态，chunks 带着版本，credentials 带着撤销标记，runs/events 带着审批过程。tickets/jobs 及未来 quota 表也核对。sqlite_sequence 自增高水位另纳入：插入再删除后，业务行相同，下次分配 ID 仍可能不同。

一张表缺失或多出、schema 改变、行数改变、行内容改变都形成 mismatch。对每行，程序先把空值、文本、整数、浮点数和二进制值编码成带类型的形式，再做摘要。排序的是行摘要，所以插入顺序不会误报；重复行仍重复参与，不能当集合去重后漏掉数量变化。

报告只保存表名、数量、hash 与变化类别，不保存正文、审批人或 token。两份文件的字节 hash 不同，也可能只是行插入顺序不同；业务核对应看行摘要。schema 使用实际定义，保守报告定义差异，不声称能证明任意 SQL 在语义上等价。

两端各自稳定，不代表共享同一瞬间。持续写入系统还需要停写或协调窗口，两个读取快照不是一次全局原子切换。

检查点 5｜文档数一样，为什么仍可能 quarantined？

同一条文档记录的 readers 或 status 改了，数量可以完全不变，行摘要会变。审批取消与 token 撤销同样如此。只比较 documents 的 count 会漏掉这些业务状态。

6. 观察撤权、删除与审批漂移

demo 从已验证快照分别创建全新临时 current 文件，各做一种变更，观察哪张表变化。原始基线保留供最后核对；额外用自增表插入再删除，验证下一次 ID 的漂移。

备份后的动作 当前检查 旧副本带回的风险
清空读者名单 visible_chunks 不再返回旧证据 旧 ACL 仍允许读取
撤销本地 token verify_token 返回 None 同一个 token 在旧副本有效
取消待审批任务 runs 成为 cancelled 旧副本仍是 pending
提升文档 revision 旧 chunk 不再匹配当前版本 旧证据版本被带回
删除文档 tombstone 保留，chunk 删除 旧副本仍有原记录

token 与 ACL 场景用真实 workflow.verify_token 和 core.visible_chunks 检查，不只看 SQL 中是否改了一列。公开报告写布尔检查结果，不写 token；token 只在临时进程内存中用于同值验证。

这些结果都应为 quarantined。当前拒绝结果保留，旧副本继续隔离；不能改回撤销标记来凑一致，也不自动合并旧权限。

五个旧副本都可以打开，却可能违反今天的决定。删除与权限更新对索引的影响，见 11g：缓存与索引一致性。

检查点 6｜隔离后没有发现漂移，就能自动上线吗？

也不能。snapshot_consistent_inspection 只说明这次读到的用户表状态一致。它没有验证当前账号授权来源、外部服务、切流窗口或后续写入，也没有生成上线许可。

7. 复跑并只留下脱敏结果

以下展示示例项目目录中的调用方式。如果已有 Python 环境，先运行限定测试，再跑 demo。下面的输出目录必须全新；重新运行换一个名字，避免覆盖前一次失败记录。

python -m unittest discover -s . -p test_backup_lab.py -v
python backup_lab.py --output .runtime/backup-first

默认不传 --output 时，会生成带时间的 .runtime/backup 目录；命令行没有指定用户数据库的参数。demo 只把 report.json 留在输出目录，临时的源、备份和恢复文件在结束时全部关闭并清理。报告里的 manifest 是脱敏元数据，不是数据库备份本身。

本次 Windows、Python 3.12.14、SQLite 3.53.1 环境，19 项测试与16项真实场景通过。单次用时描述小夹具，不代表生产恢复速度。

打开 report.json，先看 status 和 passed，再看 token_revocation 的 changed 表；其中应有 credentials 摘要变化，没有明文凭证。manifest 标明字节、页数与运行版本。

检查点 7｜如果命令因为目录已存在而失败怎么办？

换一个新输出名再运行，保留原目录。不要删除旧记录来制造“第一次就通过”的印象。这个拒绝保护的是历史结果；它也不意味着必须恢复任何用户数据库。

8. 把边界写进结论

程序限制单文件及 WAL 合计 64 MiB、最多 128 张用户表、总计十万行、规范编码累计 32 MiB。超过限制明确拒绝；复杂 view、trigger 与虚拟表也拒绝，不偷偷运行它们后再声称已核对所有语义。

备份默认期限十秒，可设置到最多六十秒。布尔值、NaN、无穷大、负数或巨大参数不能绕过期限；锁等待和 SQL 扫描也有进度检查。普通系统调用耗时仍受机器与存储环境影响，因此它不是硬实时承诺，更不是断电容错证明。

最终记录可以这样写：“在线备份包含本次已提交 WAL，隔离恢复可重新打开；全表核对发现 token 撤销漂移，副本保持隔离。”如果没有差异，改写为“读取快照一致，仍仅用于检查”。不要省掉最后的状态限制。

真实上线还需备份来源、当前授权、索引、外部效果与切流核对。继续读 容器化与部署；本章没有测试真实断电、云容灾或进程崩溃。

离开前：挑一个 quarantined 场景，用一句话说清“文件检查通过，但哪项当前决定不能被旧副本覆盖”。这就是学习验收。

检查点 8｜这章最终交付的是什么？

一套可复跑的在线备份、全新文件恢复、全表漂移检查，以及脱敏实验记录。它提供验证恢复风险的证据，不提供自动上线、旧权限回灌或真实灾难恢复保证。
