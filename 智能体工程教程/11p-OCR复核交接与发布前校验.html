OCR复核交接与发布前校验

⏱ 阅读约 28 分钟 · 动手实践另计

本章保留教学代码、路径说明与历史验证结论；完整实验工程和运行记录未随本站及公开仓库分发。命令用于说明调用方式，复现需自行准备对应实现、数据与环境。

本章保留第十三批的交接规则与待复核记录。后续11q · 中文文档纠错到入库演示原创参考驱动的独立教学库，不改变本章的人工复核与发布门槛。

一句话带走：交接时要锁定“哪张原图、哪份候选、哪版修订、哪些必查项”；清单完整只表示材料能继续核对，发布仍需可信人工验收。

先选一个可以停下的地方

先看第1节的交接包，就可停下；继续到第4节，辨认“旧复核不能批准新文字”；最后运行离线演示，比较真实候选与合成记录。走神后回到：原图 → 候选 → 修订与清单 → 逐项复核 → 外部验收。动手时间另计。

本章承接中文文档解析与字段复核，解决“候选产生后，怎样把待办交给下一位复核者”。复用既有校验，不重新识别图片；表格分块仍等待可信结构。

1. 交接包要让接收者找到同一份材料

想象你把“拆伯”改成了“拆卸”，随后只发出一份文字。接收者不知道这是哪个页面，也不知道修改前的输出是什么，更无法判断复核意见是否针对当前版本。把 reviewer 填成某个姓名，并不能补齐这些信息。

实验用五件材料完成交接：原始 PNG、保存的候选、修订记录、必查清单、复核记录。候选保留当时引擎配置和原TSV；修订另存，不覆盖候选。清单声明这次必须核对哪些字段、哪些页的表格行，以及尚未解释的问题。

输出 handoff-manifest.json 记录每件文件的路径、字节数和 SHA-256，并列出阻断项、待复核项、下一步。接收者可以据此重新核对文件；哈希只识别内容，无法证明材料来自可信机构或某人真的读过图片。

检查点 1：交接时最容易遗漏的材料是什么？

除了原图和文字，还容易漏掉“本次检查范围”。没有必查清单，删掉难核对的一行也可能让剩余项目全部勾满。清单自身需要绑定并保存；其范围是否充分，仍由可信复核过程判断。

2. 先运行不需要OCR环境的演示

以下以 knowledge-assistant 为示例工作目录。本章只需 Python 标准库；不需要 Tesseract、语言包、模型服务或网络。对应 Python 命令为：

python -X utf8 -m unittest test_ocr_handoff_lab -v
python -X utf8 fixtures/ocr-handoff/demo.py --output .runtime/handoff-first

输出目录必须全新。演示会调用真正的交接 CLI，保存每次输入、退出码、stdout、stderr、交接清单与汇总。它读取两份按字节保存的历史中文 OCR 候选，同时运行另外15个合成案例；两组计数独立。

历史文件来自第十二批原创公开检修卡与参数表，并非生产扫描件。本次不重跑其 OCR，也不填写真实人工意见。原示例 saved-source-provenance.json 记录原保存位置和副本哈希。两张实际 PNG 仍在 fixtures/chinese-documents。

检查点 2：演示退出码为0，为什么真实候选仍可能待复核？

demo 的0表示所有预期边界都被观察到，包括应该阻断的负例。单次 check 的0只表示记录结构完整；1表示待复核或阻断，2表示输入读取失败、格式拒绝或输出目录已存在。三者都不授权发布。

3. 原图搬家可以，旧候选不改写

旧候选保存了作者电脑的绝对路径。把材料复制到另一台机器后，该路径通常不存在。不要把旧 JSON 里的路径改成自己的路径再沿用原哈希；这会改变候选内容，旧复核也失去绑定。

交接 CLI 要求显式 --image，先检验实际PNG及其哈希，再与候选里的原图哈希比较。原记录路径与当前核验路径会一同留在清单。只移动文件且字节相同可以继续；换图、损坏PNG或文字被改写，都不能借用旧绑定。

现有中文候选与基础OCR模块使用不同的JSON封印格式。新模块先核对中文候选原封印，再建仅在内存中的校验视图，复用 ocr_lab.validate_review 的五项检查。原候选没有被重写或“升级”为新OCR结果。

检查点 3：新路径能打开一张看起来一样的图片，就足够吗？

不够。重新压缩、重新截图甚至一个像素的变化，都可能产生新文件。校验只接受与原候选绑定的字节；新图片要作为新证据走完整流程。外观相似不能替代内容绑定。

4. 修订正文与复核范围必须一起绑定

revision-template.json 带有修订编号、原候选/图片绑定、全文、字段和表格行。准备模板时只复制候选文字作为待改起点，字段value/unit保持null，不从参考答案中自动填写。review-template.json 的五类检查、逐字段检查和逐行检查均从未填写开始。

新复核额外绑定整个修订和清单的哈希。改正文、换修订编号、删除清单里的压力项，再拿旧复核来检查，都会得到 stale_handoff_review。即使内容变化只有一个否定词，也必须重新对照原图。

准备新模板不会继承旧记录中已勾选的检查。原复核文件保留，manifest保存其哈希；新版本的复核者、勾选和说明重新留空。否则程序复制一次，就可能把“看过旧候选”误当作“看过新修订”。

检查点 4：自己重新计算哈希，是否等于完成重新复核？

不是。重新绑定只表达“记录声称针对这份材料”，没有身份或语义保证。生产接收者还要通过可信流程核对身份、检查范围和原图。本教学脚本没有签名系统，任何结构完整结果都保留外部验收要求。

5. 数字、单位和字段标签不能拆开过关

清晰卡必查型号、压力、电流、状态。修订中的数字以字符串保存，例如 0.0500，避免序列化成浮点数后丢掉尾零。数值字段必须同时有数字和单位；null表示尚待填写，缺键、空单位或非法数字则阻断。

字段不能只检查关键词存在。修订写“压力：9 MPa”，另一个段落写“0.65 MPa”，不能支持结构化字段“压力=0.65 MPa”。实验复用完整标签行匹配；重复同名标签也不给分。字段集合必须与清单一致，删除未完成字段不会缩小分母。

这里的匹配只核对“结构化值和修订文字一致”。两者若一起写错仍可能一致，因此还需要人对照原图；单位是否适用、否定词是否遗漏，也不由正则表达式决定。统一的 numbers_units 勾选之外，每个要求的字段还有独立说明。

检查点 5：字段字面匹配通过，可以认为压力数值正确吗？

只能认为两份记录相互一致。若原图写0.65，两份记录都写9，程序的一致性检查无法证明真伪。测试故意保留这种边界，结果中的 semantic_correctness 仍为null。

6. 表格关系必须逐行说明，未决问题不能消失

表格第2页清单要求 r03 对应页2的ZX-43、r04 对应页2的ZX-44。每行分别保存page、row_label、value、unit；修订全文中要出现完整的一行三元组。页面错配、行被删掉、值和单位分属不同记录，都不能只靠总勾选放行。

这是一种有界的交接格式：正文行采用 型号 | 数值 | 单位，没有页码或行ID。因此，整份清单的行标经过NFKC与去空白后必须唯一；同页或跨页重名均阻断，即使数值不同。否则两页同值可能借用唯一的一行正文；两页异值也无法在此格式中明确各自归属。跨页同名应保留更清晰的页/行证据格式，不能修改型号来绕过限制。

脚本不会从像素发现单元格，也不推断跨页关系。逐行检查的备注需要说明核对了什么，但“备注非空”仍不证明核对真实发生。

第2页的 ZX-45/ZX-46 合并末行，只有“待复核、共用上限”，没有明确数字或单位；它保存在 unresolved_questions。两条明确行不能代表全页，末行也不能复制上一行的MPa。此处维持blocked，等待来源澄清与人工处理。

检查点 6：把未决问题删除后，程序还一定能发现原图的歧义吗？

旧复核会因清单变化失效。但若有人重新编造整套记录并绑定，脚本没有理解像素的能力，无法保证发现遗漏。因此可信接收过程必须独立审查清单范围；哈希不是防伪签名，不能替代这一步。

7. 读实际结果时分开三个状态

2026-10-13，本批对保存的候选和合成记录执行交接 CLI，结果如下。29项新测试通过；与既有OCR/中文模块定向回归共65项通过，其中旧中文smoke实际运行，但不计入本章交接样本分母。

输入组 结构完整 待复核 阻断 实际含义
两份历史OCR候选 0 1 1 清晰卡待填；表格还存在未决关系
15个合成边界案例 1 1 13 检验改图、过期复核、缺项及重复行标等门槛

唯一结构完整的夹具特别使用一张没有文字的2×1像素PNG，却配有作者编写的中文修订。这不是可用OCR样本，恰好证明“哈希一致、表格字段齐全、reviewer非空”仍不能证明文字来自图片。它只检验校验器的结构行为。

所有结果都保留 publication_allowed=false、identity_authenticated=false、human_acceptance=null。结构完整时下一步为外部身份与语义复核；存在pending时回到原图逐项填写；存在blocked时先修复错配或澄清来源。没有自动入库、模型复核或发布。

检查点 7：为什么要保留一个“图文不符却结构完整”的夹具？

它让能力边界可复现。若教材只展示漂亮勾选表，很容易把结构校验当成验收。合成夹具不参加真实人工通过率统计；本轮真实人工复核数量为0。

8. 接手下一次复核时先做三件事

先打开manifest指出的原图、候选与清单，确认范围和版本；再逐项解释缺什么证据，修订文件另存；最后在可信身份和人工流程下复核当前版本，并保存新记录。接收方应重新运行校验，不能只看发件人截图中的绿色状态。

想单独体验清晰卡，可使用下面命令。它只生成待填材料，预期退出码1；若想再次运行，换一个新输出目录。填好的真实复核需要由负责的人对照图片完成，本章没有提供自动填表指令。

python -X utf8 ocr_handoff_lab.py prepare --candidate fixtures/ocr-handoff/saved-clean.candidate.json --image fixtures/chinese-documents/clean.png --review fixtures/ocr-handoff/saved-clean.review-template.json --checklist fixtures/ocr-handoff/real-clean.checklist.json --output .runtime/handoff-clean

本章沿用语雀106/112的解析和表格选题；此前只看到PDF附件入口，附件正文未读。这里的交接格式、夹具、代码和结果均为本项目原创，不引用其附件中的流程或准确率。

当前停止点：说清“为何清晰卡待复核、为何表格阻断、为何合成结构完整也不能发布”，即可结束。走神救援：只打开 summary.json，先分清 saved_real_ocr 和 synthetic_fixture 两个分母，再回到原图。

检查点 8：这一章完成后，还缺哪些真正的发布条件？

还缺可信身份、原图来源与范围审查、独立人工语义和表格关系确认，以及业务系统自己的发布授权。本工具只交付可重新核对的材料；输入校验期间被改写也会拒绝生成核验清单。
