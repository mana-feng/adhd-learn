15d｜多租户隔离矩阵与负向验收：同名资料会串吗？

⏱ 阅读约 22 分钟 · 动手实践另计

本章保留教学代码、路径说明与历史验证结论；完整实验工程和运行记录未随本站及公开仓库分发。命令用于说明调用方式，复现需自行准备对应实现、数据与环境。

一句话：隔离验收要同时放入“应当看见”的正例和“绝不能看见”的负例，并在检索、引用、会话三个公开入口核对实际状态。

星灯设备助手为不同企业保存 XR-200 手册。租户 A 与 B 都把文档命名为 manual，用户也都叫 alex，查询都写 coolant。如果只用唯一名字测试，键混用和过滤遗漏很可能藏起来。本章用相同标识制造冲突，再用真实的 core.ingest/retrieve/validate_citations 和 SessionStore 公共调用观察结果。测试身份由可信实验代码直接构造；这里没有演示登录、令牌验证或身份来源的可信性。

停止点：完成检查点 3 可先停；完成检查点 6 再停一次。阅读与手动预测约 20 分钟，程序运行约数秒。

走神救援：始终问两句：“这个身份本来能看见什么？”“权限变化后旧证据还有效吗？”

1. 先把隔离分成可测层

层 本章公开入口 正向控制 负向控制
文档与检索 ingest、retrieve A/B 同名文档各自命中 跨租户、同租户未授权读者、缺少读 scope
引用 validate_citations 当前授权片段通过 外租户片段、撤权与旧版本片段拒绝
会话 SessionStore 同一 session_id 分别保存三个身份的文本 陌生用户、缺 scope、旧版本写入拒绝

每层都放正例。若实现把所有请求都返回空、都拒绝，负例会“通过”，但服务已经不能用。expected 是运行前固定的预期；observed 是当次公开调用结果；passed 只是两者是否一致。

检查点 1｜只有“跨租户查不到”就算通过吗？

不算。A 与 B 各自必须能查到自己的资料，才排除“整个索引为空”或“全部拒绝”的假通过。

2. 制造有意冲突的资料

公开 fixture evaluation/isolation-cases.json 放三份虚构文档：A 与 B 的 doc_id=manual、标题 XR-200、查询词 coolant 相同，但正文分别有 A-only、B-only 标记。第三份属于 A 的 shared，只授权 blair，提供同租户其他读者的正例。实验把它们写到临时目录，以真实 ingest 发布到临时 SQLite。临时数据库在程序结束时删除，公开证据只有状态和哈希。

core.visible_chunks 在 SQL 查询中用租户约束，再用文档 readers 列表筛选 subject；retrieve 的 BM25 只能排列已可见片段。A 与 B 两次 coolant 查询都返回 evidence，且正文标记与片段 ID 不同。同租户 blair 对 A 的 manual 得到 insufficient_evidence，但对授权的 sharedpump 得到 evidence。缺少 knowledge:read scope 返回 scope_denied。

检查点 2｜`insufficient_evidence` 表示文档不存在吗？

不能这样推断。它只表示这个身份和查询在当前可见集合中没有可用上下文，可能是 ACL、租户、词匹配或资料本身的原因。

3. 先运行，再读逐项状态

示例命令以父项目目录为工作目录。显式输出目录必须尚不存在；示例名已用于本站证据，自己练习时换一个新名字。

& ./examples/knowledge-assistant/.venv/Scripts/python.exe -X utf8 -m unittest discover -s examples/knowledge-assistant -p test_isolation_lab.py -v
& ./examples/knowledge-assistant/.venv/Scripts/python.exe -X utf8 examples/knowledge-assistant/isolation_lab.py demo --output examples/knowledge-assistant/.runtime/isolation-reader-01

在示例 knowledge-assistant 目录内，Python 3.10+ 的对应命令为 python -X utf8 -m unittest test_isolation_lab -v 和 python -X utf8 isolation_lab.py demo --output .runtime/isolation-reader-01；先建 .runtime，输出子目录保持不存在。

本次固定运行返回 {"status":"passed","total":35,"passed":35}，11 个限定 unittest 均通过。summary.json 给总数、哈希与范围说明，rows.json 给每项 id/layer/expected/observed/passed。没有 SQLite、原始会话或真实用户资料。输入错误为固定 JSON、exit 2；内部错误为固定 JSON、exit 1；输出目录已存在返回 output_exists，不会覆盖旧结果。

检查点 3｜35/35 就能说“永不串租户”吗？

不能。它只说明本次合成样本、这三个公开接口和当前代码版本的预期与观察一致。

4. 引用也要按当前权限重查

检索阶段的片段 ID 不是永久通行证。validate_citations 用当前身份重新读取可见片段，再核对 chunk_id、修订号和 quote 是否在正文里。A 的当前引用、B 的当前引用都为 valid；把 B 的片段交给 A，返回 citation_not_current_or_permitted。同租户 blair 引用只授权给 alex 的片段，也得到同一拒绝码。缺 scope 先返回 scope_denied。

之后管理员把 A 的 manual 发布为修订 2，并把读者从 alex 改为 blair。A 的原查询转为 insufficient_evidence；blair 可查到 current A，其当前引用通过。A 的旧引用因撤权拒绝；即使 blair 现在有权，修订 1 的旧片段也因版本不当前而拒绝。这里验证的是结构与来源，不证明引用文字逻辑上支持最终回答。

检查点 4｜新读者能否沿用旧片段的引用 ID？

不能。修订 2 重建片段；当前身份、片段 ID、修订号和原文 quote 都要重新核对。

检查点 5｜撤权后检索为空，就不必测旧引用了吗？

仍要测。引用校验是独立入口，已有回答可能保存了旧 ID，不能把检索层的正确结果当作引用层证据。

5. 会话 ID 相同，也要看复合身份

实验用 A/alex、B/alex、A/blair 三个身份都创建 same-dialogue，各追加一轮不同标记。三次读取都为版本 2，分别只含自己的文本。三个 first 操作 ID 也相同，仍各自得到 applied:v2。这实际触达 SessionStore.create/append_user_turn/read，而不是直接查看表结构。

没有创建会话的 A/charlie 读取返回 session_not_found；缺 scope 返回 knowledge_read_required。A/alex 用过期预期版本 1 再写返回 version_conflict；随后读取仍是版本 2、一轮文本。这是并发版本门槛的负例，不等于测过所有并发时序。会话状态机制详见 06b：会话状态与并发更新。

检查点 6｜同一 `session_id` 能在多个租户存在，是冲突吗？

不是。会话键包含租户、subject、会话 ID；相同可见字符串对应三个独立状态。

6. 自己改一格，再确认正负例

复制 fixture 到练习目录并自行改代码载入路径，或在临时测试里多发布一份 readers=["*"] 的 A 文档：先预测 A/alex 与 A/blair 都能否读，再测 B/alex。另一项练习是先保存修订 1 的引用，再发布修订 2，分别用旧、新读者校验。每次都记录四列：身份、操作、预期、观察；不能只写“安全”。

检查点 7｜负例通过但正例失败，该怎么记？

记为验收失败，先检查样本是否真的入库、查询词是否命中、授权是否按预期配置，不能把空结果算隔离成功。

检查点 8｜本实验还能宣称哪些隔离？

仅能描述本次数据、引用和会话公共调用的结果。配置隔离、CPU/GPU 配额、进程与网络隔离、外部认证、生产审计和合规均未测量。

本站的入库修订规则见 11b：文档入库与数据治理，引用结构边界见 11n：结构化回答与证据校验，服务层身份传递见 17d：企业助手服务层实战。语雀原文《对话系统的多租户隔离方案》提供数据、配置、资源分层和同名标识测试方向；本章设备案例、代码、数据与 35 项结果为本站原创。来源链接见 语雀文章。
