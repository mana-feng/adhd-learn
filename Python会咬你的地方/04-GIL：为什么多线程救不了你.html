🎯 一句话

本章首先讨论启用 GIL 的 CPython 解释器：同一解释器中通常只有一个线程执行 Python 字节码。阻塞 I/O 和某些明确释放 GIL 的原生计算可以并发；“用 C 实现”本身不保证释放 GIL。free-threaded 构建需另查实际运行状态。

🧩 一、GIL 是什么：同一解释器内的锁

GIL 全称 Global Interpreter Lock，全局解释器锁。它的规则用一句话讲完：

⭐ 在本章启用 GIL 的 CPython 中，同一解释器里，同一时刻只有一个线程能执行 Python 字节码。 这里的 100 个线程共享同一解释器；操作系统即使把它们分配到不同的核上，它们仍要排队抢同一把 GIL。

先看你的解释器现在是什么形状：

# 你的解释器现在是什么形状：启动方式 + GIL 在不在
import multiprocessing as mp, sys

if __name__ == "__main__":
    print("平台          :", sys.platform)
    print("默认启动方式  :", mp.get_start_method())
    print("本平台可选    :", mp.get_all_start_methods())
    print("GIL 还在吗    :", getattr(sys, "_is_gil_enabled", lambda: "该版本没有这个函数")())
    print("线程切换间隔  :", sys.getswitchinterval(), "秒")

本机（8 核 Windows 11 / CPython 3.13）输出：

对照

本平台可选 : ['spawn']

GIL 还在吗 : True

线程切换间隔 : 0.005 秒

⭐ 最后那行 0.005 秒是解释器线程切换的目标（理想）间隔，不是固定交锁周期：长时间运行的内部函数或方法可能使实际间隔更长。它既不保证每 5 毫秒交还 GIL，也不保证此时操作系统完成一次线程切换；接下来哪个可运行线程获得调度，由操作系统决定，解释器没有自己的线程调度器。在本章同一解释器内，持有 GIL 执行 Python 字节码的线程仍是轮流跑，不是同时跑。

为什么会有这么一把锁：CPython 用引用计数管内存，每个对象身上挂着一个「有几个名字指着我」的计数器（这就是 01 章里那些「标签」的实现）。这个计数器几乎每执行一条字节码都会被加减一次。如果两个线程同时改同一个计数器，就会出现「都以为自己是最后一个」于是重复释放，或者「都以为对方还在用」于是永远不释放。

⭐ 给每个对象配一把锁在技术上可行，但代价是给每一次加减都加锁——单线程程序会因此显著变慢。GIL 是「一把大锁换掉几亿把小锁」的工程折衷：单线程最快，多线程受罚。

🔎 可选深入：交还 GIL，不等于操作系统完成一次切换

⭐ 把层次分开：进程提供地址空间与资源，线程是其中的一条执行流；同一进程的线程共享地址空间和许多资源，各有寄存器上下文、栈和线程局部状态。这里说普通 CPython 的原生线程：Windows 以线程参与调度，现代 Linux 的内核调度实体也包含这些原生线程；协程或 GIL 不是 OS 的调度单位。

一次 OS 切换要处理应用里能怎样理解
保存/恢复执行现场保存当前线程所需寄存器状态、栈与续跑位置，再恢复下一线程；具体寄存器和保存路径依架构/内核
更新调度状态当前线程可能等待资源或时间片结束；调度器选择可运行线程，并更新相关队列/状态
处理地址空间上下文同进程线程通常共享地址空间；换到不同地址空间还可能换页表上下文，并影响 TLB/缓存的复用

这解释了“进程切换通常更贵”的一个来源，但不是永远更慢的定理；硬件地址空间标签、缓存是否命中、跨核迁移及内核路径都会影响代价。不能说每次换进程都清空全部 TLB，也不能用后文的 pickle/进程启动耗时替代一次上下文切换耗时。

本节原来的 CPython 切换间隔只帮助理解解释器竞争，不等于 OS 调度时间片。这里只补读 Python 并发例所需的边界，不展开 PCB、CFS 或调度算法清单。

依据：Windows 进程/线程上下文、Linux pthreads、Linux v6.6 context_switch 源码及x86 TLB 文档。这些是机制依据，不是本轮 Linux/Windows 调度实测。

🧩 二、纯 Python 的 CPU 活：线程一点忙都帮不上

先把最常见的期待打掉。8 核机器，4 份一模一样的计算活：

# 纯 Python 的 CPU 活：串行 / 4 线程 / 4 进程
import math, time
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def burn(n=3_000_000):
    s = 0.0
    for i in range(n):
        s += math.sqrt(i)
    return s

if __name__ == "__main__":          # ⭐ Windows 上少这一行，多进程直接炸，见第五节
    t = time.perf_counter()
    [burn() for _ in range(4)]
    print("串行   %.2f s" % (time.perf_counter() - t))

    t = time.perf_counter()
    with ThreadPoolExecutor(4) as ex:
        list(ex.map(burn, [3_000_000] * 4))
    print("4 线程 %.2f s" % (time.perf_counter() - t))

    t = time.perf_counter()
    with ProcessPoolExecutor(4) as ex:
        list(ex.map(burn, [3_000_000] * 4))
    print("4 进程 %.2f s" % (time.perf_counter() - t))

要点

串行 0.56 s

4 线程 0.73 s

4 进程 0.38 s

⭐ 看中间那一行：开了 4 个线程，比串行还慢。慢的那部分不是错觉，是抢锁和切换的开销——活一点没少干，还多干了「排队」这件事。

⚠️ 线程那一档在不同机器、不同轮次之间会在「和串行持平」到「比串行慢三成」之间摆动（我这台机器上三轮分别是 0.57 / 0.60 / 0.75 s，对应的串行是 0.56 / 0.62 / 0.86 s）。要看的不是绝对数，是它从来不会接近 4 倍。

⚠️ 而进程那一档也只快了 1.5 倍，不是 4 倍——因为起进程本身要钱：

# 起进程本身要多少钱
import time
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

def noop(x):
    return x

if __name__ == "__main__":
    t = time.perf_counter()
    with ThreadPoolExecutor(4) as ex:
        list(ex.map(noop, range(4)))
    print("起 4 个线程 + 跑 4 个空任务  %.3f s" % (time.perf_counter() - t))

    t = time.perf_counter()
    with ProcessPoolExecutor(4) as ex:
        list(ex.map(noop, range(4)))
    print("起 4 个进程 + 跑 4 个空任务  %.3f s" % (time.perf_counter() - t))

对照

起 4 个线程 + 跑 4 个空任务 0.002 s

起 4 个进程 + 跑 4 个空任务 0.387 s

⭐ 0.002 s 对 0.387 s，差了近 200 倍。 这 0.39 秒是净开销，从并行省下的时间里扣。任务总时长如果不到一秒，多进程大概率是亏的。

⭐ 三、真正的分界：这个操作放不放 GIL

上一节容易让人得出「CPU 密集就用进程」的结论。那个结论太粗，而且恰好在最常见的两个场景上给出相反的建议。

关键在于：GIL 可以在不访问 Python 对象或 Python C API 的原生工作区段主动释放，再于需要时取得。扩展可使用 Py_BEGIN_ALLOW_THREADS 等机制实现这种分区；这给其他线程执行的机会，是否在不同 CPU 核上并行仍取决于可运行工作、调度和资源，不能只凭放锁或加速倍数断言核心归属。

同样是「CPU 密集」，两个库的选择不一样：

# 同样是「CPU 密集」，线程池管不管用取决于这个操作放不放 GIL
import json, time
import numpy as np
from concurrent.futures import ThreadPoolExecutor

arrays = [np.random.rand(8_000_000) for _ in range(4)]
blob = json.dumps([{"id": i, "v": [i, i + 1, i + 2]} for i in range(300_000)])
blobs = [blob] * 4
print("JSON 大小 %.1f MB" % (len(blob) / 1e6))

def timed(fn):
    t = time.perf_counter(); fn(); return time.perf_counter() - t

def np_serial():  [np.sort(a) for a in arrays]
def np_thread():
    with ThreadPoolExecutor(4) as ex: list(ex.map(np.sort, arrays))
def js_serial():  [json.loads(b) for b in blobs]
def js_thread():
    with ThreadPoolExecutor(4) as ex: list(ex.map(json.loads, blobs))

for name, f in [("np.sort  串行", np_serial), ("np.sort  4线程", np_thread),
                ("json     串行", js_serial), ("json     4线程", js_thread)]:
    print("%s  %.2f s" % (name, min(timed(f) for _ in range(3))))   # ⭐ 取最小值，理由见 05 章

⭐ 这里限定启用 GIL 的 CPython：要核对具体操作、数据类型与实现是否释放 GIL，不能只背库名。例如 NumPy 的 object dtype 操作不释放 GIL；上面的 float 排序实验不能推广到所有数组操作。释放 GIL 也不保证加速，还要看数据共享、内存带宽与调度开销。

numpy / scipy 中已确认释放 GIL 的具体操作与数据类型；不能泛化到 object dtype 纯 Python 的循环、字符串拼接、字典操作
PyTorch 中已确认释放 GIL 的具体算子，按版本与实现核对 json.loads / json.dumps
压缩解压（zlib / gzip / bz2） re 正则匹配（不放）

⭐ 站内有一处正好卡在这条分界线上。AI全栈 03 · 后端骨架 讲 async 服务时说：真 CPU 活——解析 50 MB JSON、本地算 embedding——async 救不了，只能扔线程池或独立进程。 那句话把这类活指向了两个选项，而没说什么时候该选哪个。⭐ 这一章补的就是那个判据：在启用 GIL 的 CPython 中，本地 embedding 若具体操作与类型已确认释放 GIL，可先评估线程池；普通 JSON 解析可评估进程池，但也要计入进程启动和数据搬运成本。仅凭 numpy / torch 的库名不能断言线程池管用。

🚦 四、三种并发怎么选

在启用 GIL 的 CPython 中，把「具体操作是否释放 GIL」和「在等还是在算」交叉，可得到选择起点；数据共享、带宽与开销还会改变结果，答案不是唯一的：

你的活 选什么 为什么
在等网络 / 磁盘 / 数据库，而且库是 async 的 ⭐ async 异步 I/O 可在事件循环中交错推进可挂起的等待；这不是按 GIL 释放或固定连接数保证容量，CPU/阻塞回调仍可能挡住循环。
在等，但手上的库是同步的（requests、老的数据库驱动） ⭐ 线程池 若该同步库在阻塞等待时释放 GIL，可先评估线程池；仍需核具体 API、并发安全与资源上限，不能只凭“同步 I/O”保证效果。
在算，具体操作与数据类型已确认释放 GIL ⭐ 线程池 可先评估线程池，避免进程启动与序列化成本；仍须防止共享写入争用，核对带宽和线程开销，不承诺加速
在算，纯 Python 代码（解析、循环、正则） ⭐ 进程池 本章普通单解释器示例用进程池，让各进程拥有独立的解释器与 GIL
在算，纯 Python，但数据非常大 ⚠️ 先算账，见第六节 搬数据的钱可能超过并行省下的钱

「在等」那一档的效果是最好看的——因为等待期间 GIL 是放开的，8 个任务能挤在一起等：

# 等待类的活：线程和 async 都能赢，因为等待的时候 GIL 是放开的
import asyncio, time
from concurrent.futures import ThreadPoolExecutor

def wait_io(_):                 # 假装是一次网络请求
    time.sleep(0.25)

async def wait_io_async(_):
    await asyncio.sleep(0.25)

async def gather_all():
    await asyncio.gather(*(wait_io_async(i) for i in range(8)))

if __name__ == "__main__":
    t = time.perf_counter(); [wait_io(i) for i in range(8)]
    print("串行     %.2f s" % (time.perf_counter() - t))

    t = time.perf_counter()
    with ThreadPoolExecutor(8) as ex:
        list(ex.map(wait_io, range(8)))
    print("8 线程   %.2f s" % (time.perf_counter() - t))

    t = time.perf_counter(); asyncio.run(gather_all())
    print("async    %.2f s" % (time.perf_counter() - t))

对照

串行 2.00 s

8 线程 0.25 s

async 0.27 s

⭐ 原等待负载记录为 2.00 → 0.25，正好 8 倍，线程和 async 在这组结果中接近；不能由此设定“几千连接”才有差别的固定分界。原文所述线程几百 KB 到几 MB 的栈、协程几 KB 是实现相关的量级示意，容量与收益还取决于任务、平台和调度，应在目标负载评估。

🧩 五、进程模型：fork 和 spawn 是两件不同的事

先运行 multiprocessing.get_start_method() 并记录 Python 版本，不要只凭操作系统猜：CPython 3.13 的 Linux 等非 macOS POSIX 平台通常默认 fork；3.14 起，在支持 forkserver 的非 macOS POSIX 平台改为默认 forkserver，fork 不再是任何平台的默认。Windows 默认 spawn；macOS 在这里对照的 3.13/3.14 中默认 spawn。程序也可显式选择可用的上下文。下表只比较机制，不代替本机检查。参见 3.13 文档与3.14 文档。

选了进程之后，第二类坑就来了：子进程是怎么诞生的。这里对照 fork / spawn 两种造法，行为差得很远。另有 forkserver：先启动服务进程，由它接受请求并 fork 子进程；它不是直接复制当前应用进程，不能套用下表 fork 的全部父进程状态直觉。

fork（如 CPython 3.13 的 Linux 默认；3.14 需显式选择） spawn（Windows 默认；macOS 3.13/3.14 默认）
怎么造 把当前进程整个复制一份 从零启动一个新的 Python 解释器
子进程能看见什么 父进程 fork 那一刻的全部内存（写时复制） ⭐ 什么都看不见，只有被 pickle 传过去的东西
启动开销 小 大（要重新 import 一遍所有模块）
顶层代码 不会重跑 ⭐ 会重跑一遍
线程 / 锁 ⚠️ 只复制调用 fork 的那个线程，别的线程持有的锁会永远锁着 干净，没这个问题

⭐ spawn 会把你的主模块重新 import 一遍，这是 Windows 上所有多进程怪事的根源：

# spawn 会把这个模块【重新 import 一遍】：守卫外面的代码，每个子进程都会再跑一次
import os, time
from concurrent.futures import ProcessPoolExecutor

print("[模块顶层] pid=%d 我被执行了" % os.getpid())

STATE = {"loaded_at": time.time()}      # 守卫【外面】：每个子进程都会重新造一份

def who(_):
    return "pid=%d ｜ STATE 里有 %d 个键 ｜ EXTRA=%r" % (
        os.getpid(), len(STATE), STATE.get("EXTRA"))

if __name__ == "__main__":
    STATE["EXTRA"] = "主进程加上去的"    # 守卫【里面】：子进程看不见
    print("[主进程] pid=%d" % os.getpid())
    with ProcessPoolExecutor(2) as ex:
        for line in ex.map(who, range(2)):
            print("[子进程]", line)

⭐ 两条结论都在这段输出里：

  1. [模块顶层] 打了三次——两个子进程各把这个文件重新执行了一遍。所以顶层写的任何耗时代码（加载模型、连数据库、读大 CSV）都会被乘以进程数。
  2. 子进程的 EXTRA 是 None。守卫里面改的那次修改，子进程完全不知道。进程之间不共享对象——这是 01 章全部「共享」直觉失效的地方：那一章说「赋值只是贴标签，两个名字指同一个对象」，跨进程之后连对象都是两个。

⚠️ 报错还没完，主进程那边收到的是另一条完全不指向根因的消息：

concurrent.futures.process.BrokenProcessPool: A process in the process pool was

💀 这就是为什么它难查：你在终端里看到的第一屏是 BrokenProcessPool，字面意思是「池子里有个进程突然死了」，读起来像资源不足或者环境问题；真正的 RuntimeError 被埋在一大堆 multiprocessing/spawn.py 的栈帧中间。而在 Jupyter / IDE 里，子进程的 stderr 常常根本不显示，你只会看到那句 BrokenProcessPool，然后开始怀疑人生。

📋 规矩：任何会用到多进程的脚本，一律把可执行代码放进 if __name__ == "__main__":。 顶层只留 import、常量和函数/类定义。这条在 Linux 上也照做——你写的脚本迟早会有人在 Windows 或 macOS 上跑。

🔎 可选深入：worker 结束了，资源也收完了吗？

沿着本节的 worker 看一个简化生命周期：创建 → 就绪 → 运行 → 等待 IO/锁 → 再就绪 → 结束。运行被抢占可回到就绪，等待的条件满足才回到就绪；这是解释模型，不是把所有 OS 状态字母硬配成同一张表。

问题在本页程序里的边界
线程“崩溃”Python Thread.run 的普通未捕获异常通常交给 threading.excepthook，使该线程结束；join 不自动把它重新抛到调用线程。原生致命错误/进程终止则可能结束整个进程，不能把两类故障混说
最多能开多少线程没有跨平台固定数：栈/地址空间、内存与系统限额都约束创建。Linux 还可能受用户线程数资源限额、threads-max、pid_max 限制；不要靠无限创建去测生产上限
Linux 中的僵尸子进程已终止，但等待者尚未收取退出信息；保留少量记录供 wait/waitpid 回收，并非仍在运行的 Python worker
Linux 中的孤儿父进程先退出；子进程由相应 init/subreaper 接管，可能还在运行。孤儿与僵尸描述不同关系，不能互当同义词

Linux 上可先用 ps -eo pid,ppid,stat,comm 观察 PID/父 PID/状态；STAT 首字母 Z 指向僵尸，再查父进程为何未回收。它已经结束，不能靠“再杀一次这个僵尸”让父进程补做 wait。R、S、D 等是具体 Linux 状态，别直接照搬成 Windows 的进程状态名。

在 Python 层保留 worker 句柄，按任务协议接收结果并调用适当的 join/进程池收尾；线程句柄等待、子进程回收和业务结果消费是不同动作。这里不运行僵尸/致命故障负例，也不承诺强制终止后未完成的数据会自动一致。

依据：Python 线程异常、pthread_create 资源限额、wait 的回收语义、Linux 状态字段。命令仅说明诊断入口，本轮未在 Linux 上执行。

⚠️ 六、pickle 的账：搬数据的钱可能比省下的还多

跨进程传参数和收结果，走的是 pickle：对象序列化成字节 → 通过管道传给子进程 → 子进程再反序列化成对象。这一来一回的钱经常被忽略。

# 进程间传参要 pickle：大对象搬过去的钱，可能比并行省下的还多
import pickle, time
import numpy as np
from concurrent.futures import ProcessPoolExecutor

def cheap(a):                       # 活很轻：只求个和
    return float(a.sum())

if __name__ == "__main__":
    arrays = [np.random.rand(8_000_000) for _ in range(4)]   # 每份 64 MB
    blob = pickle.dumps(arrays[0])
    t = time.perf_counter(); pickle.dumps(arrays[0]); pk = time.perf_counter() - t
    print("单份大小 %.0f MB ｜ pickle 一次 %.3f s" % (len(blob) / 1e6, pk))

    t = time.perf_counter(); [cheap(a) for a in arrays]
    print("串行         %.3f s" % (time.perf_counter() - t))

    t = time.perf_counter()
    with ProcessPoolExecutor(4) as ex:
        list(ex.map(cheap, arrays))
    print("4 进程       %.3f s" % (time.perf_counter() - t))

对照

单份大小 64 MB ｜ pickle 一次 0.055 s

串行 0.036 s

4 进程 0.870 s

💀 4 个进程比串行慢了 24 倍。 256 MB 的数据被序列化、塞进管道、再反序列化，而真正的计算只花了 36 毫秒。

⭐ 一条需要端到端测量的经验判断：

“计算时间达到 pickle 时间的 10 倍”只能作为经验启发，不是官方阈值，也不是多进程必然划算的条件。本轮没有复跑上面的原基准；其数字只描述原环境。应在同一任务与输入下比较串行和进程池的端到端耗时，计入启动/导入、双向序列化、传输、返回结果、任务粒度与池复用；fork、spawn、forkserver 以及 Python 版本会改变这笔账。上例 pickle 与计算的局部计时只提示搬运可能压过收益，不能单靠一个比率决定。

⚠️ 还有三个连带的坑：

坑 长什么样
不是所有东西都能 pickle lambda、局部函数、打开的文件句柄、数据库连接、threading.Lock 都不行，报 PicklingError 或 TypeError: cannot pickle ...
返回值也要 pickle 子进程返回一个 2 GB 的 DataFrame，回程的开销和去程一样贵
内存被乘以进程数 4 个子进程各持一份 64 MB 的副本，峰值是 5 份而不是 1 份（怎么量峰值内存见 05 章）

📋 避开办法：别传数据，传「去哪拿数据」。把 4 个进程各自要读的文件路径 / 行号区间 / 分片编号传过去，让它自己读。大数组还可以放进 multiprocessing.shared_memory 共享一块内存，只传名字。

🔎 可选深入：不搬大数组，仍要传控制消息

后文建议“传路径或共享内存名字”，并不表示进程间天然共享任意 Python 对象。先看载荷与控制各走哪条路：

方式适合传什么必须另管什么
管道/队列字节流或序列化的消息；Python multiprocessing.Queue 常用于传小任务和结果边界/协议、背压、退出与异常；不要把大对象反复塞回去又说没有拷贝
共享内存让不同进程访问同一块字节，减少大载荷反复序列化/传输数据布局、同步和生命周期；首次填充、转换视图仍可能拷贝，不是整个任务自动零拷贝
socket同机或跨机的消息/流连接、序列化、失败/重试协议；跨机不能直接用本机内存名字
OS signal通知某类异步事件不是通用对象消息队列；Python 的处理器在主解释器主线程执行，不能代替线程间消息传递

SharedMemory 用完要关闭各自句柄，并约定谁负责释放；POSIX 风格下由指定一方按协议 unlink，Windows 则在全部句柄关闭后删除，unlink 不起同样作用。Python 3.13 的 track/resource-tracker 行为还受进程启动关系影响，独立启动的程序应按官方文档确定谁记账，不能各自抢着清理仍有人在用的块。

信号量不是 signal：它以计数表达可用许可，acquire/release 协调多少任务能进入；OS signal 表达异步通知。共享数据需要的锁、事件或队列不会因为“发了个 signal”就自动安全。

依据：Python 3.13 共享内存、进程消息传递、signal 与线程。这里只比较与现有进程池直接相连的接口，不演示跨机部署。

🧯 八、GIL 不等于线程安全

最后一个反直觉的地方：GIL 保护的是解释器自己的内部状态，不是你的代码。

「同一时刻只有一个线程在跑字节码」不等于「你的一行 Python 是一个整体」。total = plus_one(total) 是读 → 调用 → 写回三步，中间任何一步都可能被换下去：

# GIL 不等于线程安全：读—改—写中间只要有一次函数调用，就有换线程的机会
import sys, threading
sys.setswitchinterval(1e-6)     # 默认 0.005 秒，这里调到百万分之一秒，把概率放大

def plus_one(x):
    return x + 1                # ⭐ 一次函数调用 = 一个可以被换下去的点

total = 0
def bump(n=50_000):
    global total
    for _ in range(n):
        total = plus_one(total)   # 读 total → 调用 → 写回，三步不是一个整体

ts = [threading.Thread(target=bump) for _ in range(8)]
[t.start() for t in ts]; [t.join() for t in ts]
print("应该是 400000，实际是", total, "  丢了", 400_000 - total)

要点

应该是 400000，实际是 123085 丢了 276915

💀 丢了 27 万次更新，占七成。 三次运行分别是 123085 / 116319 / 115419，每次都不一样——这正是并发 bug 最难受的特征：不确定、不复现、不报错。

⚠️ sys.setswitchinterval(1e-6) 那一行是为了把概率放大到肉眼可见。默认的 5 毫秒下，同样的代码在 CPython 3.13 上我连跑三次都没丢过一次——这才是真正危险的地方：你本地测不出来，它在生产的负载下才出现。

📋 规矩：只要有两个线程会写同一个东西，就上锁（threading.Lock），或者干脆用 queue.Queue 让它们只通过队列通信。⚠️ 不要因为「我看了 CPython 源码，这个操作是原子的」就省掉锁——那是实现细节，换个版本、换个解释器就变。

🔎 可选深入：锁保护状态，队列把完成交回主线程

前面的读改写例已经说明 GIL 不保护业务不变量。再按用途选机制：

机制本页需要区分的语义
Lock / RLock互斥访问共享状态；RLock 允许同一线程重入，但仍须配对释放。Lock 不因此变成“再拿一次也没事”
Condition拿着关联锁检查条件，wait 时释放它，醒来后重新拿锁并循环检查；收到通知不等于业务条件永久成立
Event / SemaphoreEvent 保留一个通知标志，不计每次脉冲；Semaphore 维护许可计数，适合限制并发数量
Queue把数据和交接同步放在一处，适合 worker 完成通知；不同 worker 的结果要保留任务身份
# Python 3.13/3.14：worker 发送结果，主线程接收后调用方法
from queue import Queue
from threading import Thread, current_thread, main_thread

def worker(done):
    try:
        result = sum(range(4))
    except Exception as exc:
        done.put(("error", type(exc).__name__))
    else:
        done.put(("ok", result))

def on_done(value):
    assert current_thread() is main_thread()
    print("main received", value)

def main():
    done = Queue()
    thread = Thread(target=worker, args=(done,))
    thread.start()
    kind, payload = done.get(timeout=5)  # 本小例等待界限，不是业务 SLA
    thread.join()
    if kind != "ok":
        raise RuntimeError(payload)
    on_done(payload)

if __name__ == "__main__":
    main()
# 预期 main received 6；不在 worker 内直接调用 on_done

join 是等待，不是把回调搬到主线程。小例由主线程取消息，再显式执行 on_done；若用 Future 回调，也不能仅凭“注册了回调”就断言它在主线程运行。若题目实际指子进程而非子线程，则改用进程间队列/管道协议，不能拿普通 queue.Queue 跨进程共享。

死锁先看等待关系：线程 A 持有互斥资源 L1、等待 L2；B 持有 L2、等待 L1。四个必要条件是互斥、持有并等待、不可抢占、循环等待。对于 OS 支持的互斥锁，这个等待环也会让对应原生线程无法前进；本例只画等待关系，不实际挂死程序。

本章已有的 POSIX 多线程 fork 警告是另一条具体链路：子进程只保留调用线程，却继承锁状态，原持锁线程不在子进程中，后续获取该锁可能永远等待。须按目标平台的 fork/线程约束选择启动上下文与收尾路径，不能把“换个 GIL”当解法。

处理时先确认等待链：统一取锁顺序、缩短持锁区属于预防；超时后必须按协议释放已持资源并撤销未完成动作，不是“有 timeout 就自动解锁”。若只能终止/重启隔离 worker，应先承认可能丢失未提交工作并安排恢复；不要强放别人的锁来跳过未完成的不变量。这里不扩展成内核锁实现或完整死锁检测专题。

依据：threading 同步原语、线程队列、fork 平台约束、OSTEP 并发问题与死锁条件。

🗓️ 九、GIL 会消失吗（这一节会过期）

PEP 703 给 CPython 加了一个可选的 free-threaded 构建（俗称 no-GIL），3.13 起作为实验特性提供，3.14 起转为官方支持但仍非默认。装的是那个构建时，sys._is_gil_enabled() 会返回 False，纯 Python 的多线程才能真正吃满多核。

⚠️ 今天不要按「GIL 快没了」来做设计决策，三个理由：

理由 说明
默认装的还不是它 python.org 的默认安装包仍是带 GIL 的。你得专门装 free-threaded 版本（本机 sys._is_gil_enabled() 返回 True）
C 扩展要重新适配 大量第三方轮子还没有 free-threaded 版本，装不上或者掉回兼容模式
⭐ 本章的账不会全部作废 GIL 没了，pickle 的开销、进程启动的开销、spawn 重新 import 这些依然在；而第八节的「线程安全要自己保证」会变得更重要，因为原来靠 GIL 侥幸没出问题的代码，那层侥幸没有了

📋 把本章规则当作选择起点：在启用 GIL 的 CPython 中，结合等待/计算、具体操作是否释放 GIL、共享争用及启动/搬运成本评估线程或进程；不按“放锁用线程、不放锁用进程”作唯一答案。free-threaded 构建须重新评估这些条件与同步责任，不能沿用受 GIL 约束的选型结论。

✅ 检查点

  1. GIL 用一句话说是什么规则？为什么 CPython 需要它（和哪个内存管理机制有关）？
  2. 8 核机器上，4 份纯 Python 的 CPU 活开 4 个线程，实测结果是什么？为什么会这样？
  3. 为什么「CPU 密集就开进程」太粗？应结合哪些操作、类型、GIL 与成本条件？原 float np.sort 和 json.loads 负载的实测倍数分别是多少，为什么不能直接推广？
  4. 本章 sleep(0.25) 与 asyncio.sleep(0.25) 等待示例中，线程和 async 怎样交错等待？原记录 8 个任务串行和 8 线程分别是多少？为什么不能据此规定固定连接数分界？
  5. spawn 和 fork 的三个关键区别是什么？为什么在 Windows 上「顶层加载模型」这件事特别贵？
  6. 少写 if __name__ == "__main__" 会怎样？为什么这个错误难查（你在终端里先看到的是哪条消息）？
  7. 什么情况下 4 个进程会比串行慢？本章那个例子慢了多少倍？给出一条能算的规矩，以及避开的办法。
  8. 既然有 GIL，为什么 total = plus_one(total) 还会丢更新？实测丢了多少？为什么这个 bug 在本地特别难复现？
  9. DataLoader(num_workers=4) 在 Notebook 里卡死，根因是什么？persistent_workers=True 省掉的是哪一笔钱？
  10. free-threaded 构建普及之后，本章哪些结论会作废、哪些不会？
👀 答案
  1. 在启用 GIL 的 CPython 中，同一解释器里，同一时刻只有一个线程能执行 Python 字节码。 它存在是因为 CPython 用引用计数管内存——几乎每条字节码都要加减对象上的计数器，两个线程同时改会导致重复释放或永不释放。给每个对象配锁在技术上可行，但会让单线程程序显著变慢，GIL 是「一把大锁换掉几亿把小锁」的折衷。sys.getswitchinterval()（原记录为 0.005 秒）给出目标切换间隔，实际间隔可能更长；它不保证每 5 毫秒交锁或发生 OS 切换，后续调度由操作系统决定。同一解释器内执行 Python 字节码仍是轮流跑。
  2. 串行 0.56 s、4 线程 0.73 s、4 进程 0.38 s —— 开线程比串行还慢，慢的是抢锁和切换的净开销，活一点没少干。进程那档只快 1.5 倍而不是 4 倍，因为起 4 个进程本身就要 0.387 s（同样的空任务开 4 个线程只要 0.002 s，差近 200 倍）。
  3. 在启用 GIL 的 CPython 中，要按具体操作、数据类型和实现核对计算期间是否释放 GIL；“有没有构造 Python 对象”不是等价判据。原记录中，np.sort 排 800 万个 float：串行 0.80 s → 4 线程 0.25 s（3.2 倍）；json.loads 解析 13.7 MB：1.51 s → 1.45 s（1.04 倍）。这些仅是该次负载的计时，不证明全程锁状态，也不推广到 object dtype 或其他实现。
  4. 在本章 time.sleep 等待示例中，阻塞等待区段释放 GIL，任务可以重叠等待；asyncio.sleep 由事件循环挂起和恢复任务。原记录串行 2.00 s、8 线程 0.25 s（正好 8 倍）、async 0.27 s，只描述这组负载。不能规定“几千连接”才出现区别；原文线程几百 KB 到几 MB 的栈、协程几 KB 是实现相关量级，实际容量仍须测量。
  5. ① fork 是复制当前进程、spawn 是从零启动一个新解释器；② fork 的子进程能看见父进程的全部内存，spawn 的什么都看不见，只有被 pickle 传过去的东西；③ spawn 会把主模块重新 import 一遍，所以顶层代码会重跑。Windows 与这里对照的 macOS 3.13/3.14 默认 spawn（原 Windows 3.13 记录中 get_all_start_methods() 只有 ['spawn']）；Linux 等 POSIX 的默认值须区分 3.13 的 fork 与 3.14 支持条件下的 forkserver，先查本机上下文。因此顶层写的加载模型 / 连数据库 / 读大 CSV 会被乘以进程数 —— 本章那个例子里 [模块顶层] 打了 3 次（1 个主 + 2 个子）。
  6. 子进程重新 import 主模块时会再次执行创建进程池那一行，无限递归。CPython 会抛 RuntimeError: An attempt has been made to start a new process before the current process has finished its bootstrapping phase。⚠️ 难查是因为你在终端里先看到的是 BrokenProcessPool: A process in the process pool was terminated abruptly —— 字面像资源不足，真正的 RuntimeError 被埋在一堆 multiprocessing/spawn.py 栈帧中间；在 Notebook / IDE 里子进程的 stderr 常常根本不显示。
  7. 当搬数据的钱超过并行省下的钱时。本章例子：4 份 64 MB 数组只求个和，串行 0.036 s、4 进程 0.870 s，慢了 24 倍（pickle 一份就要 0.055 s，而计算只要 0.009 s）。“10 倍”仅是未经本轮基准验证的经验启发，不是通用门槛；实际比较要计入启动、导入、双向序列化、传输和任务/池复用的端到端成本。避开办法是 别传数据，传「去哪拿数据」（文件路径、行号区间、分片编号），大数组可以用 multiprocessing.shared_memory 只传名字。
  8. 因为 GIL 保护的是解释器自己的内部状态，不是你的代码。total = plus_one(total) 是读 → 调用 → 写回三步，函数调用处就是一个可以被换下去的点。实测 8 个线程各加 5 万次，应该是 400000，实际 123085（丢了 276915，约七成），三次运行 123085 / 116319 / 115419 每次都不一样。⚠️ 难复现是因为那是靠 sys.setswitchinterval(1e-6) 把概率放大出来的；默认 5 毫秒下连跑三次一次都没丢 —— 本地测不出来，生产负载下才出现。
  9. DataLoader(num_workers>0) 就是一个进程池，spawn 要重新 import 主模块，而 Notebook 没有可 import 的「主模块文件」。修法是把 Dataset 类和训练循环挪进 .py 再 import，或者在 Notebook 里用 num_workers=0。persistent_workers=True 省的是 每个 epoch 重建 worker 的进程启动钱（本机 4 个空进程就要 0.39 s，import torch 之后更贵）。
  10. 会作废的：第二节「纯 Python 的 CPU 活开线程没用」——free-threaded 构建下线程能真正吃满多核。不会作废的：pickle 的开销、进程启动的开销、spawn 重新 import 主模块，这些和 GIL 无关；而第八节「线程安全要自己保证」会变得更重要，因为原来靠 GIL 侥幸没出问题的代码，那层侥幸没有了。今天默认装的仍是带 GIL 的构建（本机 sys._is_gil_enabled() 返回 True）。

⚡ 走神救援

⭐ 在本章启用 GIL 的普通单解释器运行方式下，同一时刻只有一个线程能执行 Python 字节码。 它存在是因为 CPython 用引用计数管内存，几乎每条字节码都要加减计数器——拿一把大锁换掉几亿把小锁。

⚠️ 实测 4 份纯 Python 的 CPU 活：4 线程比串行还慢（慢的是抢锁和切换的净开销），4 进程只快一点点（起进程本身就很贵，而开线程几乎免费）。

⭐ 在启用 GIL 的 CPython 中，具体操作与类型确认释放 GIL 时，CPU 计算可评估线程池；Python 对象操作所需的锁与调用中的可释放区段要分别核对，还要看共享争用和开销。原 np.sort / json.loads 倍数只是本章负载记录，不是库名或锁状态的通则。

选择起点：异步 I/O 可评估 async，同步 I/O 可评估线程池；在启用 GIL 的 CPython 中，CPU 计算须核具体操作、类型与实现是否释放 GIL，不能按 numpy / torch / 压缩 / 哈希库名直接决定。纯 Python CPU 工作可评估进程池，并计入启动与搬运成本。原等待实验的结果及线程/async 差异只适用于记录的负载，不设固定连接数分界。

选了进程之后第二类坑是进程怎么诞生：Windows 与这里对照的 macOS 3.13/3.14 默认 spawn；Linux 等 POSIX 须区分 3.13 的 fork 与 3.14 支持条件下的 forkserver，先查本机。spawn 从零启动新解释器并把主模块重新 import 一遍——⭐ 进程之间不共享对象，第 01 章那套「两个名字指同一个对象」在这里全部失效。

⚠️ 少写 if __name__ == "__main__" 会无限递归，而真正的 RuntimeError 被埋在栈中间，你先看到的是 BrokenProcessPool——字面像资源不足，于是你会去查错地方。

💀 pickle 的账更贵：几份大数组只求个和，4 进程比串行慢二十多倍。⭐ 不要背固定倍数门槛：在目标 Python 版本和启动上下文下，实测串行与进程池的端到端成本，区分启动/导入、双向序列化、传输、计算和池复用。
